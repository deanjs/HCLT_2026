## §1. 트랜스포머 — 이 연구에 필요한 만큼만, 정확하게

step3은 모델 **내부**를 직접 편집한다. 그러려면 "내부"가 정확히 무엇인지 합의가 필요하다.
여기서 쓰는 기호는 문서 전체에서 동일하다.

### 1.1 전체 그림 — 잔차 스트림(residual stream)

입력 토큰 `t_1 … t_n` 각각이 벡터 하나(`d_model` 차원)를 갖고 출발한다. 이 벡터가 층을 지나며
**계속 더해져 나가는 통로**를 잔차 스트림이라 부른다. 층은 이 통로를 갈아치우지 않고 **읽고 더한다**.

```
위치 j 의 잔차 스트림
  x_j^(0)  ─┬─► [층 0: 어텐션] ──(+)──┬─► [층 0: FFN] ──(+)──┐
            └────────────────────────┘                      │
  x_j^(1)  ◄──────────────────────────────────────────────────┘
            ... 층 1, 2, …, L-1 반복 ...
  x_j^(L)  ──► 마지막 LayerNorm ──► 출력 임베딩(unembedding) ──► 어휘 로짓
```

한 층 ℓ은 두 부품으로 되어 있고, **각각 잔차에 더해진다**:

```
x' = x + Attn_ℓ(LN1(x))      ← 다른 위치에서 정보를 "가져오는" 부품 (위치 간 통신)
x'' = x' + FFN_ℓ(LN2(x'))    ← 그 위치 안에서만 계산하는 부품 (위치 내 변환)
```

- **어텐션**만이 **위치 사이**로 정보를 옮긴다. "문맥의 `split_config`가 지금 쓰는 이름에 영향을 준다"는
  경로는 **반드시 어텐션을 통과**한다. ← step3이 어텐션의 입력(K/V)을 건드리는 이유.
- **FFN(=MLP)**은 위치 하나 안에서 그 벡터를 변환한다. 우리는 FFN을 **직접 건드리지 않는다.**
  다만 층 ℓ에서 우리가 바꿔 넣는 Value는 "층 ℓ 이전까지의 어텐션+FFN이 그 위치에 쌓아 올린 결과"이므로,
  **FFN이 만든 내용을 통째로 갈아끼우는 셈**이다(§5.7).

### 1.2 Query / Key / Value — 세 벡터의 역할 분담

층 ℓ의 어텐션은 각 위치 j의 입력 `x_j`에서 세 벡터를 만든다(가중치 행렬 `W_Q, W_K, W_V`):

```
q_j = W_Q x_j     "나는 무엇을 찾고 있나"      (질문)
k_j = W_K x_j     "나는 어떤 표지를 달고 있나"  (색인/이름표)
v_j = W_V x_j     "나를 읽으면 무엇이 실려 오나" (내용물)
```

지금 이름을 쓰려는 위치(마지막 위치 `n`)의 출력은:

```
        exp(q_n · k_j / √d_head)
a_nj = ────────────────────────────      (softmax, Σ_j a_nj = 1)
        Σ_m exp(q_n · k_m / √d_head)

out_n = Σ_j a_nj · v_j        ──► W_O 를 거쳐 잔차에 더해짐
```

여기서 **연구의 두 축**이 갈린다:

| 축 | 기호 | 뜻(쉬운 말) | 무엇이 결정하나 |
|---|---|---|---|
| **축 A** | `a_nj` | **얼마나 보나** (어텐션 질량) | `q_n`과 `k_j` — **Key** 쪽 |
| **축 B** | `v_j` | **무엇이 실려 오나** (내용) | **Value** 쪽 |

`out_n = Σ_j a_nj v_j` 이므로 **둘의 곱이 실제 기여**다. 그래서 "지침을 더 보게 만들자"(어텐션 증폭 =
축 A만 키우기)는 접근은, 정작 `v_j`에 필요한 내용이 없으면 **아무것도 못 고친다**. 이것이 우리 반박의
수학적 뼈대다.

> **항등식(관측 지표의 근거):** `a`는 스칼라이고 0 이상이므로 `‖a_nj · v_j‖ = a_nj · ‖v_j‖`.
> step2/step4의 `‖av‖` 지표는 근사가 아니라 **정확한 분해**다(`attention_probe.py` 머리말).

### 1.3 head — 여러 개의 병렬 어텐션

위 계산은 `d_model` 전체가 아니라 **head 단위**로 쪼개서 병렬로 여러 번 일어난다.
`d_model = H_q × d_head` (예: 2048 = 16 × 128). head마다 자기 `W_Q, W_K, W_V`가 있고,
결과를 이어 붙여(`concat`) `W_O`로 섞는다. head마다 "보는 대상"이 다르다 —
어떤 head는 구문, 어떤 head는 바로 앞 토큰, 어떤 head는 같은 종류의 이름을 본다.

**우리는 head를 고르지 않는다.** step3은 전 head를 한꺼번에 바꾼다(§5.5). head 단위 국소화는
이 연구의 범위 밖이고, "층 단위 국소화"까지가 우리 주장이다.

### 1.4 GQA(Grouped Query Attention) — Key/Value가 head보다 적다

최신 모델은 메모리를 아끼려고 **Query head 수(`H_q`)보다 Key/Value head 수(`H_kv`)를 적게** 둔다.
`group_size = H_q / H_kv`개의 query head가 **하나의 K/V를 공유**한다.

```
query head:  q0 q1 q2 q3 | q4 q5 q6 q7      (H_q = 8)
              \  \  |  /     \  \  |  /
KV   head:      kv0            kv1           (H_kv = 2, group_size = 4)
```

**이것이 CLAUDE.md §3의 "치환은 KV group 단위" 규칙의 정체다.** KV 캐시의 실제 모양은
`[batch, H_kv, seq, d_head]`이므로, 우리가 `kv0`을 하나 바꾸면 **그 그룹의 query head 4개가 전부**
바뀐 값을 읽는다. "head 하나만 바꿨다"고 착각하면 안 된다.

- `H_kv == H_q`이면 GQA가 아니라 일반 MHA(그룹 크기 1).
- 코드: `ModelHandle.gqa_info()` → `GQAInfo(num_attention_heads, num_key_value_heads, head_dim)`,
  `group_size` 속성. 노트북 셀 ④가 실행 시작 시 이 값을 출력한다.
- 관측 계열(step2/4)에서는 `a`(query head별)와 `‖v‖`(KV head별)의 개수가 달라서
  `av[h,j] = a[h,j] · ‖v[h // group_size, j]‖`로 **query head를 자기 그룹의 KV head에 매핑**한다
  (`attention_probe.span_metrics`, "방법 A: repeat 후 정렬").

### 1.5 RoPE — 위치 정보는 Key에만 들어간다 (★ step3 해석에 결정적)

이 모델들(Qwen2 / Llama / DeepSeek-Coder / StableLM 계열)은 **회전 위치 인코딩(RoPE)** 을 쓴다.
절대 위치 임베딩을 더하는 대신, `q`와 `k`를 **위치에 따라 회전**시킨다:

```
q̃_j = R(j) q_j ,   k̃_j = R(j) k_j        (R(j) = 위치 j의 회전 행렬)
q̃_n · k̃_j  는 상대 거리 (n − j) 에만 의존한다.
v_j 는 회전하지 않는다.  ← Value에는 위치 정보가 없다
```

HuggingFace 구현에서 **KV 캐시에 저장되는 Key는 이미 회전이 적용된(post-RoPE) 상태**다.
따라서:

- **Value 치환**: 위치와 무관한 순수 "내용" 이식. 깨끗하다.
- **Key 치환**: 내용뿐 아니라 **공여 토큰의 위치 위상까지 함께 이식**된다. 공여 프롬프트와 위반
  프롬프트의 토큰 수가 다르면(camel/snake는 실제로 다르다) 위상이 어긋난다.

→ **Key 조건은 구조적으로 약간 불리한 채로 측정된다.** 우리 결론("내용 > 어텐션")에 유리한 방향의
편향이므로, 논문에서 **반드시 한계로 명시**해야 한다(§8.2).

### 1.6 KV 캐시 — 우리가 손대는 바로 그 자료구조

자기회귀 생성은 토큰을 하나씩 만든다. 매번 앞 문장을 통째로 다시 계산하면 낭비이므로,
**각 층·각 위치의 `k_j`, `v_j`를 저장해 두고 재사용**한다. 이것이 KV 캐시(`past_key_values`)다.

```
past_key_values
 ├─ layer 0 : keys [B, H_kv, seq, d_head]   values [B, H_kv, seq, d_head]
 ├─ layer 1 : keys …                        values …
 └─ layer L-1 …
```

**핵심 성질:** 캐시의 층 ℓ 항목은 "위치 j가 층 ℓ에서 **남들에게 읽히는 형태**"다.
= 그 위치가 층 ℓ에서 문맥으로 **내보내는 신호**. 우리는 정확히 이걸 바꿔치기한다.

**⚠️ 대칭이 아니다:** 층 ℓ의 캐시를 바꿔도, **그 위치의 층 ℓ+1, ℓ+2… 캐시는 원본 그대로**다
(이미 계산돼 저장돼 있고, 다시 forward하지 않으므로). 그래서 우리 개입은
**"읽는 쪽(read-side)만, 한 층만"** 이다. 이 성질이 §5.8·§8.1의 해석 전부를 좌우한다.

### 1.7 로짓과 로그확률

마지막 층을 지난 잔차는 LayerNorm → 출력 임베딩을 거쳐 어휘 크기의 **로짓**이 되고,
`log_softmax`로 로그확률이 된다. 여러 토큰으로 쪼개지는 이름의 확률은 **조건부 확률의 곱**이므로,
**로그확률의 합**이다:

```
log P("removeDuplicates" | 프롬프트) = Σ_k log P(tok_k | 프롬프트, tok_<k>)
```

코드: `intervention.sum_logprob`, `model._preference_context.logp_candidate`.

## §2. 실험 논리 — 관측이 아니라 인과를 주장하려면

### 2.1 관측(step2)의 한계

step2는 camel 이름 그룹과 snake 이름 그룹의 어텐션·‖v‖·‖av‖를 **비교**했다. 차이가 보여도
그건 **상관**이다. "그 차이가 실제로 모델의 이름 선택을 만들어냈다"는 보장이 없다
(부수 현상일 수 있다).

### 2.2 인과를 주장하는 표준 도구 — 반사실 개입(counterfactual patching)

인과추론의 기본형은 **"다른 건 다 고정하고 그것만 바꿔서 결과가 바뀌는지 본다"** 이다.
언어모델 해석 분야에서는 이를 **activation patching / causal tracing**(ROME 계열),
**path patching**, **attention knockout** 등으로 부른다. 우리 방법은 그 계보에서
**"KV 캐시를 단일 층에서 패칭한다"** 는 변종이다.

세 상태를 만든다:

| 상태 | 기호 | 만드는 법 | 뜻 |
|---|---|---|---|
| **깨끗(clean)** | `S_clean` | 문맥 12개를 **전부 camel**로 렌더 | 방해가 없을 때의 천장 |
| **위반(base)** | `S_base` | 문맥 12개 중 6개를 **snake**로 렌더 (실제 조건) | 방해가 있을 때의 바닥 |
| **개입(int)** | `S_int` | **텍스트는 위반 그대로**, 그 6개 이름의 **층 ℓ KV만** 깨끗 쪽 값으로 덮음 | 속만 고친 상태 |

> 우리 설계에서 "깨끗"은 정확히 "그 위반 6개를 camel로 고쳐 쓴 것"과 같다.
> 문맥 12개 = 준수 6 + 위반 6이고, 위반 6개를 목표 표기로 바꾸면 전부 camel이 되기 때문이다
> (`runner._preference_setup`의 `comp_text = render_preceding([(s, target) …])`).
> **즉 `S_clean`은 임의의 이상적 상태가 아니라, 우리가 KV로 흉내 내려는 그 반사실 그 자체다.**

### 2.3 되돌림(회복률) — 왜 차이가 아니라 비율인가

```
                 S_int − S_base
회복률 recovery = ──────────────────
                 S_clean − S_base
```

- `0` = 개입해도 위반 상태 그대로 (아무 효과 없음)
- `1` = 텍스트를 실제로 고쳤을 때와 **똑같은 수준**까지 회복
- **비율로 쓰는 이유 ①**: 모델·묶음마다 `S`의 절대 크기가 제각각이라 차이값은 비교가 안 된다.
  분모로 나누면 "이 조건에서 가능한 최대 변화의 몇 %인가"로 **정규화**된다.
- **비율로 쓰는 이유 ②**: `S`에 실린 상수 편향(예: 후보 두 이름의 토큰 길이 차이로 생기는 고정 오프셋)이
  분자·분모에서 **동시에 상쇄**된다(§4.3).
- 분모가 0에 가까우면(= 문맥을 바꿔도 모델이 안 흔들림) 비율이 발산하므로 **판정 불가**로 뺀다
  (`intervention.recovery_rate`가 `None` 반환, 노트북은 `GAP_MIN = 1.0`).

코드: `src/harness/intervention.py::recovery_rate`.

### 2.4 통제 조건 — 각 통제가 죽이는 대안 가설

"KV 바꿨더니 회복됐다"만으로는 부족하다. 반드시 나올 반론들을 미리 막는다.
step3은 **공여자(donor)를 3종**으로 돌린다.

| 공여자 | 무엇을 덮어쓰나 | 죽이는 대안 가설 | 기대 |
|---|---|---|---|
| `compliant` (같은 이름 camel판) | `split_config` ← `splitConfig` | — (주 실험) | 회복 큼 |
| `unrelated_camel` (**다른** camel 이름) | `split_config` ← `serializeStream` | **"그 이름을 외운 것"** — 특정 단어 기억이 아니라 *형태*가 옮겨지는가? | 주 실험과 **비슷해야** 함 |
| `unrelated_snake` (**다른** snake 이름) | `split_config` ← `serialize_stream` | **"아무거나 덮으면 흔들린다"** — 단순 교란(노이즈) 효과인가? | **낮아야** 함 |

- `unrelated_camel`이 `compliant`와 비슷하면 → Value가 나르는 것은 **이름별 암기가 아니라
  "camelCase라는 이전 가능한 형태 특징"**. (일반화 주장)
- `unrelated_snake`가 낮으면 → 효과는 **표기에 특정적**. (트리비얼 아님, 음성 통제 통과)

두 통제 모두 **같은 분모(`S_clean − S_base`)** 로 정규화되므로 세 곡선을 그대로 겹쳐 볼 수 있다.

### 2.5 왜 Key / Value / 둘다 세 갈래인가

§1.2의 두 축을 **인과적으로 분리**하기 위해서다.

| 조작 | 수식에서 바뀌는 것 | 해석 |
|---|---|---|
| **Key만** (`kind="key"`) | `a_nj` (softmax 전체가 재정규화됨) | "**얼마나 보는지**만" 준수 쪽으로 |
| **Value만** (`kind="value"`) | `v_j` (어텐션 분포는 그대로) | "**무엇이 실려 오는지**만" 준수 쪽으로 |
| **둘다** (`kind="key_value"`) | 둘 다 | 상한 |

읽는 법:

- Value만으로 회복 ≫ Key만 → **신호는 내용에 있다.**
- 둘다 ≈ Value만 → **어텐션은 잉여(redundant).** 내용이 이미 충분(sufficient).
- Value만 ≈ 0인데 Key만 큼 → 우리 가설 기각, 어텐션 증폭 접근이 옳음.

> **Key 치환의 부작용 하나:** softmax는 정규화되므로, 6개 위치의 Key를 바꾸면 그 위치들의 어텐션
> 질량뿐 아니라 **나머지 모든 토큰의 어텐션도 같이 재분배**된다. Value 치환에는 그런 파급이 없다.
> 즉 Key 조건은 "더 국소적"이 아니라 오히려 "더 광범위한" 개입이다 — 그런데도 효과가 작았다는 것이
> 결과의 무게를 키운다.

### 2.6 왜 생성이 아니라 점수인가

생성(greedy decoding)으로 이름을 뽑아 camel/snake를 세는 방법도 있다(`mode='intervene_generate'`).
step3 본실험이 **점수 방식**을 쓰는 이유:

1. **분해능.** 생성은 0/1이라 42묶음×전 층×3방식에서 곡선이 계단처럼 튄다. 점수는 연속값이라
   층별 미세한 봉우리가 보인다.
2. **비용.** 생성은 층마다 최대 24토큰을 순차로 뽑아야 한다. 점수는 후보 토큰 수만큼의
   forward 1회면 끝난다.
3. **혼입 제거.** 생성은 모델이 과제를 한 단어로 축약하거나(`clamp`) 다른 형태를 쓰면
   `other`로 빠져 판정 불가가 된다(stepA-1/A-2에서 실제로 겪었고, 그래서 두 단어가 강제되는
   과제로 교체했다 — `tasks.GENERATION_TASKS` 주석).

대신 점수 방식은 "**후보 두 개 중 상대 선호**"만 말한다. 절대 준수율은 step1이 담당한다.

## §3. 자극(입력) 형식 — 실제로 모델에게 무엇을 주는가

### 3.1 프롬프트 구조

두 개의 메시지로 된 chat 대화다. 모델의 chat 템플릿(`tokenizer.apply_chat_template`)을 통과한 뒤,
**`"def "` 네 글자를 강제로 이어 붙인다**(teacher forcing). 그러면 모델이 다음에 예측할 토큰이
**반드시 함수 이름의 첫 조각**이 된다.

```
[system]  You are helping extend an existing Python module.
          In this project we generally write function names in camelCase.
          Every function name uses one of two styles only: camelCase or snake_case.

[user]    Here is the current module:

          ```python
          def split_config(value):      ← 위반(snake) ①
              return value

          def decodeNode(value):        ← 준수(camel)
              return value
          … (총 12개, 준수 6 + 위반 6, 배치 순서는 seed 42가 섞음) …
          ```

          Add a function that removes duplicate items from a list, preserving order.

[여기서 chat 템플릿의 assistant 시작 표지] + "def "     ← ★ 다음 토큰 = 이름의 첫 조각
```

생성 코드: `prompt.build_instruction_text` (system) · `prompt.user_message_with_preceding` (user) ·
`model._preference_context.prefix` (템플릿 + `forced_prefix="def "`).

### 3.2 자극 설계의 통제들 — 왜 이렇게까지 밋밋한 함수인가

`tasks.NAME_PAIR_POOL`의 모든 함수는 **본문·매개변수가 완전히 동일**하다:

```python
def <이름>(value):
    return value
```

**의도된 통제다.** 선행 함수들 사이에서 변하는 것을 **오직 이름 표기 하나로** 못 박는다.
본문이 서로 다르면 "어텐션 차이가 이름 형태 때문인지, 본문 내용 때문인지" 구분할 수 없다.
(step2 관측과 자극을 공유하므로 이 통제가 step3에도 그대로 필요하다.)

| 통제 항목 | 값 | 이유 |
|---|---|---|
| 이름 어휘 | 동사 50 × 명사 50 → **504개** | 효과가 특정 단어의 우연이 아님을 보이기 위한 표본 |
| 묶음 | 12개씩 **42묶음**, 중복 없이 504 전부 커버 | 묶음 = 반복 표본. 모든 곡선의 오차막대가 여기서 나온다 |
| 표기 대비 | 모든 이름이 **두 단어 이상** | 한 단어면 camel == snake라 대비가 사라진다 |
| 문맥 비율 | 준수 6 / 위반 6 | 균형. 한쪽으로 치우치면 어텐션 비교가 오염됨 |
| seed 42 | **배치 순서만** 섞는다 (`random.Random(seed).shuffle`) | 어느 이름을 쓰는지는 묶음이 정한다. seed는 위치·이웃 변주만 |
| 생성 과제 어휘 | `remove/count/merge`, `duplicates/vowels/dicts` — **풀과 겹치지 않음** | 문맥에 정답 이름이 있으면 베끼기 혼입 |

### 3.3 채점 후보 두 개 (닫힌 선택지)

생성 과제 1번(`remove duplicates`)의 두 표기가 고정 후보다:

```
준수 후보 candidate_compliant = "removeDuplicates"
위반 후보 candidate_violation = "remove_duplicates"
```

지침에도 `Every function name uses one of two styles only: camelCase or snake_case.`를 넣어
**선택지를 두 개로 닫는다**. (부정형 지침이 긍정형과 논리적으로 등가가 되려면 필수 —
"snake로 쓰지 마라"가 "camel로 써라"가 되려면 제3의 선택지가 없어야 한다. `conditions.Instruction`
docstring 참조. step3은 긍정형만 쓰지만 자극 형식은 공유한다.)

### 3.4 공여(donor) 프롬프트 3종의 실제 모습

| donor | 공여 프롬프트 | 공여 이름 |
|---|---|---|
| `compliant` | **12개 전부 camel**로 렌더한 같은 문맥 (= clean 프롬프트 재사용) | `splitConfig`, `filterSession`, … (같은 이름의 camel판) |
| `unrelated_camel` | 이 묶음에 **안 쓰인** 풀 이름 **6개**로 만든 별도 프롬프트 (전부 camel) | `serializeStream`, `materializeHeader`, … |
| `unrelated_snake` | 위와 **같은 6개 이름의 snake판**으로 만든 별도 프롬프트 | `serialize_stream`, `materialize_header`, … |

- `compliant`일 때는 **clean 캐시를 그대로 공여자로 재사용**한다(추가 forward 없음 —
  `_preference_context`의 `donor_messages is None` 분기).
- `unrelated_*`는 공여 이름을 `prompt.unrelated_specs(condition, n)`이 뽑는다. 이 묶음이 이미 쓴
  인덱스를 제외한 나머지에서 `seed + 10007`로 표본추출 → **문맥 이름과 절대 겹치지 않는다.**
- ⚠️ 공여 프롬프트는 함수가 **6개뿐**이라 위반 프롬프트(12개)와 길이·구성이 다르다.
  Value에는 위치 정보가 없어 문제가 없지만, **Key에는 §1.5의 위상 어긋남**이 생긴다(§8.2).

## §4. 측정량 — 준수 선호 점수 S와 그 성질

### 4.1 정의

```
S = log P(준수 후보 | 문맥) − log P(위반 후보 | 문맥)
  = log P("removeDuplicates" | …) − log P("remove_duplicates" | …)
```

- **양수** = 지금 이 상태에서 camel을 더 선호. **음수** = snake를 더 선호.
- 로그확률 차이 = **로그 오즈비(log odds ratio)**. 두 후보만 놓고 본 상대 선호이므로 스케일이 안정적이다.
- 코드: `intervention.preference_score`, 후보 확률은 `sum_logprob`.

### 4.2 채점 forward의 구조 (여기가 은근히 까다롭다)

```
프롬프트 토큰:  [ ................ prefix[:-1] ................ ][ last ]
                └─ 한 번만 forward해서 KV 캐시로 저장 ─┘         │
                                                                 ▼
채점 forward:   입력 = [ last , cand_0 , cand_1 , … , cand_{m-2} ]   (캐시를 붙여서)
                로짓  =   ↓        ↓        ↓              ↓
                        cand_0   cand_1   cand_2   …    cand_{m-1} 예측
                log P = Σ_k  log_softmax(logits[k])[cand_k]
```

- 마지막 프롬프트 토큰을 캐시에 넣지 않고 남겨 두는 이유: 그 토큰이 **첫 후보 토큰을 예측**해야 하기 때문.
- 후보를 넣어 forward할 때마다 **캐시를 깊은 복사**한다(`_clone_cache`). 안 그러면 캐시가 후보 토큰만큼
  길어져서 다음 측정이 오염된다. 층 스윕에서 같은 캐시를 수백 번 재사용하므로 필수.
- 코드: `model._preference_context.logp_candidate` / `S`.

### 4.3 알아야 할 성질 세 가지

**① 토큰 길이 편향은 회복률에서 (1차 근사로) 상쇄된다.**
`removeDuplicates`와 `remove_duplicates`는 토크나이저에 따라 조각 수가 다르다. 로그확률 합은
조각이 많을수록 낮아지므로 `S`에 오프셋 `c`가 실린다. 이 `c`가 세 상태에서 같다고 보면
`(S_int + c − (S_base + c)) / (S_clean + c − (S_base + c))` → 소거된다.
⚠️ 다만 로그확률은 상태 의존이라 **`c`가 세 상태에서 정확히 같다는 보장은 없다 — 상쇄는 근사다**
(`docs/step3/구조적결함.md` C2). 어느 쪽이든 **절대 `S`값은 모델 간 비교에 쓰면 안 되고,
회복률만 비교한다.**

**② fp16 격자 잡음.** 모델을 `float16`으로 돌리므로 `S`가 이산적인 값에 붙는다
(실제 결과 JSON에 `S_base = -0.796875` 같은 값이 보인다 — 2의 거듭제곱 격자).
따라서 회복률 `6.96e-09` 같은 값은 **0으로 읽어야 한다**(수치 잡음).

**③ 판정 불가 기준.** `|S_clean − S_base| < 1.0`이면 그 묶음은 제외한다(노트북 `GAP_MIN`).
분모가 작으면 회복률이 폭발한다. — step3에서는 **4모델 × 3종 모두 제외 0개**였다
(문맥이 선호를 확실히 흔들었다는 뜻이며, 이것 자체가 RQ1의 방증이다).

## §5. ★ KV 치환의 해부 — 어디서 뽑아 어디에 어떻게 덮는가

이 절이 이 문서의 심장이다. "KV 치환"이라는 한 단어를 여섯 단계로 쪼갠다.

```
① 세 프롬프트를 만든다        (위반 / 깨끗 / 공여)
② 각각 한 번씩 forward → KV 캐시 3개 확보
③ 바꿀 자리를 찾는다          (문자 위치 → 토큰 인덱스)
④ 위반 쪽 자리 ↔ 공여 쪽 자리를 짝짓는다 (mean-pool)
⑤ 층 ℓ의 K/V만 덮어쓴다      (KV group 단위)
⑥ 점수를 재고 → 원상 복구 → 다음 층
```

### 5.1 ② K와 V는 어디서 나오나

**모델을 한 번 돌리면 부산물로 나온다.** 따로 훅(hook)을 걸지 않는다.

```python
out = self.model(viol_ids[:, :-1], use_cache=True)
viol_cache = out.past_key_values      # 층별 (keys, values), 각 [B, H_kv, seq, d_head]
```

- `use_cache=True`가 KV 캐시를 반환하게 한다. **step3은 `output_attentions`가 필요 없다** —
  어텐션 가중치 행렬을 안 꺼내므로 step2/4보다 훨씬 가볍고, `attn_implementation='eager'`
  강제도 불필요하다(노트북 셀 ④ 주석: "KV 바꿔치기라 어텐션 안 꺼내도 됨(빠름)").
- transformers 버전마다 캐시 레이아웃이 달라 접근을 한 곳에 격리했다 — `model._cache_kv`:

  | 버전 | 접근 경로 |
  |---|---|
  | 신형(4.54+) `DynamicCache` | `cache.layers[ℓ].keys` / `.values` |
  | 구형 `DynamicCache` | `cache.key_cache[ℓ]` / `cache.value_cache[ℓ]` |
  | legacy tuple | `cache[ℓ][0]` / `cache[ℓ][1]` |

  반환은 **원본 텐서 참조**다(복사 아님) → 여기에 대입하면 캐시가 실제로 바뀐다.

### 5.2 ③ 바꿀 자리 찾기 — 문자에서 토큰으로

이름은 토크나이저가 어떻게 쪼갤지 미리 알 수 없다(`split_config` → `split`+`_config`? `sp`+`lit`+…?).
그래서 **문자 위치를 먼저 잡고 토큰으로 변환**한다.

```
1) 프롬프트 문자열에서 "def split_config(" 를 찾는다        ← find_char_spans
2) 앞 4글자("def ")와 끝 1글자("(")를 떼어 이름 구간만 남긴다  ← s+4, e-1
3) 토크나이저의 offset_mapping과 겹치는 토큰을 전부 수집한다   ← (ts < e and te > s)
```

- `return_offsets_mapping=True`로 토큰별 `(문자시작, 문자끝)`을 받는다. **프롬프트 문자열을 그대로
  토큰화**하기 때문에(chat 템플릿을 문자열로 먼저 만든 뒤 토큰화) offset과 모델 입력이 정확히 일치한다.
- `def <이름>(` 형태로 찾는 이유: 이름만 검색하면 본문·호출부에서 **우연히 겹치는 위치**까지 잡힌다.
  정의부만 확실히 잡는다.
- 특수 토큰은 offset이 비어 있어(`te <= ts`) 자동으로 걸러진다.
- 코드: `attention_probe.find_char_spans` · `attention_probe.locate_token_spans` ·
  `model._locate_target_tokens(span_kind="def_name")`.

> `span_kind="literal"`은 step4/5용이다. 지침 문장의 `camelCase`라는 **단어 자체**의 첫 등장을 잡는다.
> **치환 로직은 완전히 동일하고, 어느 문자열을 겨누는가만 다르다** — CLAUDE.md §7의 "RQ별 스크립트 금지"가
> 이렇게 구현돼 있다.

### 5.3 ④ 짝짓기 문제 — 왜 mean-pool로 통일했나

`split_config`와 `splitConfig`는 **토큰 수가 다를 수 있다.** 짝짓는 방식이 세 가지 있고,
`Condition.token_unit`으로 고른다:

| 방식 | 동작 | 장점 | 문제 |
|---|---|---|---|
| `"all"` | 첫↔첫, 둘째↔둘째 1:1 | 자연스러움 | **토큰 수가 다르면 그 이름 통째로 제외.** 모델에 따라 전부 스킵되는 사고 |
| `"last"` | 마지막 토큰 하나만 1:1 | 항상 성립, 스킵 없음 | 단어의 일부만 덮어 **신호가 약함** |
| **`"mean"`** ★ | 공여 토큰들을 **평균 내 한 벡터**로 만들고, 위반 이름의 **모든 토큰 자리에 브로드캐스트** | 개수 불일치 허용(스킵 0) + 단어 전체를 덮음 | 공여 쪽 조각별 순서 정보는 뭉개짐 |

**통일 재실험은 `mean`으로 고정**(CLAUDE.md §3). 4개 모델의 토크나이저가 제각각이라
`all`은 모델 간 비교 자체가 불가능하기 때문이다.

수식으로:

```
위반 이름 i 의 토큰 자리 집합  V_i = {p_1, …, p_a}
공여 이름 i 의 토큰 자리 집합  D_i = {q_1, …, q_b}      (a ≠ b 여도 됨)

v̄_i = (1/b) Σ_{q ∈ D_i}  v_q^(ℓ)            ← KV head별·차원별 평균
그리고  ∀p ∈ V_i :  v_p^(ℓ) ← v̄_i           ← 같은 벡터를 전부 덮어씀
(Key도 동일: k̄_i 를 만들어 덮는다)
```

- 코드: `intervention.align_name_groups` (짝짓기, torch 없이 순수 함수 — 단위 테스트 가능) →
  `model._score_layer_kind`의 mean 경로 (`dv[:, :, dps, :].mean(dim=2)`).
- **덮어쓴 자리 수**는 결과 JSON에 `n_substituted_tokens`로 기록된다. 모델별 실측:

  | 모델 | 층 수 | 위반 이름 6개가 차지한 토큰 자리 (42묶음 범위) | 평균 | 이름당 |
  |---|---|---|---|---|
  | Qwen2.5-Coder-3B | 36 | 12 ~ 15 | 12.7 | 2.1 |
  | Llama-3.2-3B | 28 | 12 ~ 15 | 12.7 | 2.1 |
  | StableCode-3B | 32 | 18 ~ 24 | 20.4 | 3.4 |
  | DeepSeek-Coder-6.7B | 32 | **19 ~ 29** | 22.5 | 3.8 |

  값이 **묶음마다 다르다**는 점에 주의 — 이름 조합에 따라 토큰화가 달라진다. 즉 개입 강도(덮은 자리 수)가
  묶음·모델마다 변한다. 모델 **간** 회복률 크기 비교에서 이것이 교란 요인이 된다
  (`docs/step3/구조적결함.md` C4).

  → **토크나이저가 snake 이름을 얼마나 잘게 쪼개는지가 모델마다 크게 다르다.** `all` 방식이었다면
  DeepSeek·StableCode는 대량 스킵됐을 것이다. mean-pool 선택의 정당화 근거이자, 논문에 실을 표.
- 이름을 못 찾은 경우(양쪽 중 하나라도 빈 리스트)는 `skipped_names`에 인덱스로 남는다.
  step3 결과는 전부 `[]`(스킵 0).

### 5.4 ⑤ 무엇을 덮어쓰나 — kind별 정확한 동작

```python
edit_k = kind in ("key", "key_value")
edit_v = kind in ("value", "key_value")
```

| kind | keys 텐서 | values 텐서 | 관측되는 변화 |
|---|---|---|---|
| `key` | 덮어씀 | 그대로 | `q_n · k_j` 변화 → softmax **전체 재분배** |
| `value` | 그대로 | 덮어씀 | 어텐션 분포 불변, **읽히는 내용만** 교체 |
| `key_value` | 덮어씀 | 덮어씀 | 둘 다 |

**세 kind는 같은 층에서 순차로, 각각 독립적으로** 측정된다(측정 후 매번 복구). 즉
`key_value`는 `key` 다음에 `value`를 누적한 게 아니라, **깨끗한 위반 상태에서 다시 시작해 둘 다 덮은 것**이다.

### 5.5 KV group 단위라는 말의 실제 의미

캐시 텐서의 차원은 `[B, H_kv, seq, d_head]`이고, 우리 코드는

```python
ev[:, :, vp, :] = vm       # 두 번째 축(H_kv)에 슬라이스가 없다 = 전 KV head
```

**KV head 전부를, 즉 모든 query head 그룹을 한꺼번에** 바꾼다. 이것이 "group 단위"의 뜻이다.
GQA 모델에서 `H_kv`개만 건드려도 **`H_q`개의 query head가 전부** 영향을 받는다.
→ 우리 개입의 공간 해상도는 **"층 × 토큰 위치"** 이지 head가 아니다. 논문에서
"layer-level localization"이라고만 주장해야 하고 "head-level"이라고 하면 과장이다.

### 5.6 ⑥ 편집 → 측정 → 복구 루프

전 층 스윕은 **작업 캐시(work cache) 하나**를 재사용한다.

```python
work = _clone_cache(ctx["viol_cache"])          # 위반 캐시 사본 하나
for ℓ in 모든 층:
    for kind in (key, value, key_value):
        백업 = work[ℓ]의 해당 자리 값들 .clone()
        work[ℓ]의 해당 자리 ← 공여 평균값
        S_int = S(work, last)                    # ← 내부에서 work를 또 복제해 forward
        work[ℓ]의 해당 자리 ← 백업                # 원상 복구
```

- **왜 매번 복구하나:** 복구하지 않으면 층 ℓ의 편집이 층 ℓ+1 측정에 누적된다.
  각 층의 기여를 **독립적으로** 재려면 매번 깨끗한 위반 상태에서 출발해야 한다.
- **왜 층마다 깊은 복사를 안 하나:** 캐시 전체 복사는 비싸다. 채점 함수 `S`가 내부에서 어차피
  복제해 forward하므로 `work` 자체는 측정 중 오염되지 않는다 → 편집한 자리만 백업/복구하면 충분.
- 선행 프롬프트 forward는 **조건당 딱 3번**(위반·깨끗·공여)이고 층 스윕은 그걸 재사용한다.
  무료 티어 비용 절감의 핵심(`_preference_context` docstring).
- 코드: `model._score_layer_kind` · `model.intervene_preference_sweep`.

### 5.7 우리는 무엇을 "인과"라고 부르는가 — 개입의 정확한 범위

```
                층 ℓ의 캐시를 바꾸면 …

   문맥 위치 j (split_config)              생성 위치 n (def 다음)
   ┌───────────────────────────┐          ┌─────────────────────┐
   │ 층 ℓ+1 KV : 원본 그대로 ✗  │          │ 층 ℓ+1 : 영향 받음 ✓ │
   │ 층 ℓ   KV : ★ 우리가 편집  │─────────►│ 층 ℓ   : 영향 받음 ✓ │
   │ 층 ℓ-1 KV : 원본 그대로    │          │ 층 ℓ-1 : 영향 없음   │
   └───────────────────────────┘          └─────────────────────┘
        (다시 forward하지 않음)              (여기는 새로 계산됨)
```

- **가로 방향(문맥 → 생성 위치)**: 층 ℓ에서 정확히 한 번 전달된다. 이건 진짜 인과 경로다.
- **세로 방향(문맥 위치 자신의 상위 층)**: 전파되지 **않는다**. 그 위치의 층 ℓ+1 이상 캐시는
  원래 텍스트(snake)로 계산된 값 그대로 남아 있다.
- 반면 **생성 위치 쪽**은 새로 forward되므로, 층 ℓ에서 받은 변화가 잔차를 타고 층 ℓ+1, ℓ+2…로
  **정상적으로 전파**된다.

→ 따라서 step3이 재는 것은 정확히 이것이다:
**"문맥의 그 이름이 층 ℓ에서 내보내는 신호 하나만 바꿨을 때, 최종 표기 선호가 얼마나 움직이는가."**

이 좁은 정의 덕분에 **층 국소화 주장이 깨끗해진다**(다른 층은 원본 그대로이므로 그 층만의 기여).
대신 회복률이 1.0에 못 미치는 것은 **당연한 결과**이지 실패가 아니다 — 신호는 여러 층에 걸쳐
중복 전달되는데 우리는 한 층만 고쳤기 때문이다(§8.1).

### 5.8 대안이었을 방법들과 왜 안 골랐나

| 대안 | 내용 | 왜 안 썼나 |
|---|---|---|
| 텍스트 자체를 바꾸기 | snake → camel로 고쳐서 다시 생성 | 그건 `S_clean`(천장)일 뿐, **내부 어디인지**를 말해주지 못한다 |
| 잔차 스트림 패칭 | 층 ℓ의 `x_j`를 통째 교체 | 그 위치의 상위 층 전부가 바뀌어 **층 국소화가 불가능** |
| 어텐션 가중치 직접 조작 | `a_nj`에 배율을 곱함 | 축 A만 건드림. 우리 스키마에 `ATTENTION_AMPLIFY`로 자리는 있으나 step3 범위 밖 |
| head 단위 패칭 | KV head 하나씩 | 조건 수가 `층 × head`로 폭발. T4 무료 티어에서 불가 |
| 평균 제거(mean ablation) | 값을 데이터셋 평균으로 | "망가뜨리기"는 되지만 **"준수 쪽으로 되돌리기"** 는 안 됨. 우리 질문은 방향이 있는 회복 |

## §7. 재현 — 비용, 순서, 안전장치

### 7.1 조건 수와 계산량

```
조건 수 = 묶음 42 × 공여 3종 = 126 (모델당) → 4모델 = 504 파일
조건 하나당 forward 수
   = 2~3 (선행 프롬프트: 위반·깨끗 + 공여가 별도일 때만 1회 더)   ← 한 번만
   + 4   (S_base·S_clean, 각각 후보 두 개를 채점 → 2회씩)
   + 층 수 L × 방식 3 × 2 (매 측정마다 후보 두 개 채점)
   ≈ Qwen(L=36), donor=compliant: 2 + 4 + 216 = 222 회
```

- 선행 forward는 프롬프트 전체(수백 토큰)를 처리하는 무거운 3회뿐이고, 나머지 216회는
  후보 토큰 2~4개짜리 짧은 forward다.

채점 forward는 후보 토큰 수(2~4개)만 처리하므로 개별 비용은 작지만, **매번 KV 캐시를 깊은 복사**한다
(`_clone_cache`). 이것이 step3이 "무거움"으로 분류된 실질적 이유다.
(최적화 여지: 후보 채점에서 캐시 복사 대신 길이를 되돌리는 방식 — 현재 결과와의 호환을 위해 손대지 않았다.)

## §8. 이 설계가 말할 수 있는 것과 없는 것 (논문 한계 절 재료)

### 8.1 부분 회복(<1.0)은 결함이 아니다 — 하지만 정직하게 써야 한다

봉우리에서도 회복률은 0.20~0.58이다. 이유는 §5.7의 구조에서 나온다:

1. **한 층만** 고쳤다. 표기 신호가 여러 층에 중복으로 실려 있으면 한 층 수리로는 부족하다.
2. **읽는 쪽만** 고쳤다. 그 위치의 상위 층 표현은 여전히 snake로 계산된 값이다.
3. **mean-pool**로 단어 전체를 한 벡터로 뭉갰다. 조각별 미세 구조는 재현되지 않는다.

→ 주장은 **"층 ℓ이 이 신호에 인과적으로 기여한다"** 까지다.
**"층 ℓ이 유일한 원인"** 이라고 쓰면 과장이다.

### 8.2 Key 조건에 불리한 편향이 있다 (★ 반드시 명시)

§1.5·§3.4에서 본 대로:

- 캐시의 Key는 **post-RoPE**라 공여 위치의 위상이 함께 이식된다. 위반/공여 프롬프트는
  토큰 수가 다르므로 위상이 어긋난다.
- mean-pool은 **서로 다른 위치의 회전된 Key들을 평균**낸다 — Value에는 없는 추가 왜곡.
- 공여 프롬프트가 `unrelated_*`일 때는 함수가 6개뿐이라 절대 위치가 더 크게 어긋난다.

우리 결론("Value > Key")은 이 편향과 **같은 방향**이다. 따라서 논문에서는
"Key 경로의 효과는 하한(lower bound)일 수 있다"고 쓰고, 후속 통제를 제안하는 것이 정직하다:

- **위치 정합 공여**: 공여 프롬프트를 위반 프롬프트와 토큰 수가 같도록 구성.
- **RoPE 보정 패칭**: 공여 Key에 `R(공여위치)⁻¹ R(위반위치)`를 적용해 위상만 맞춰 이식.
- 실제로 결과는 이 편향이 있음에도 `key_value ≈ value`(어텐션을 더해도 안 늘어남)라서
  "내용 충분(sufficiency)" 주장은 이 편향에 영향을 덜 받는다 — 이 점을 근거로 쓰는 게 좋다.

### 8.3 그 밖의 한계

| 한계 | 내용 | 완화/대응 |
|---|---|---|
| **합성 자극** | 본문이 `return value`로 동일한 인공 코드 | 통제의 대가. 실제 저장소 코드 경로(`Source.REPO`)가 스키마에 있으나 step3에선 미사용 |
| **닫힌 두 후보** | camel/snake 둘만 놓고 잰 상대 선호 | 절대 준수율은 step1 담당. 실제 모델은 `other`(한 단어 등)로도 빠질 수 있다 |
| **층 해상도만** | head·뉴런 단위 국소화는 안 함(§5.5) | "layer-level"로만 서술 |
| **fp16** | S가 격자에 붙고, 0 근처 값은 잡음 | 회복률 절대비교 금지, 0 근처는 0으로 읽기 |
| **긍정형·약한 어조만** | step3은 `positive`/`weak` 고정 | 지침 형식 축은 RQ3(step4/5)의 몫 |
| **4개 모델** | 일반화 범위 | 코드전용 3 + 범용 1, 3B~6.7B. 그 이상은 주장 안 함 |
| **묶음이 반복 표본** | 42묶음 = 42개 이름 조합. 완전 독립 표본은 아님(같은 풀에서 나옴) | 신뢰구간은 "이 풀 안에서의 변동"으로 해석 |

### 8.4 이 설계가 **배제한** 대안 설명 (validity 요약)

| 대안 설명 | 어떻게 배제했나 |
|---|---|
| "그냥 그 단어를 외운 것" | `unrelated_camel`이 `compliant`와 비슷 → 이름 정체성이 아니라 **형태**가 옮겨진다 |
| "아무거나 덮으면 흔들린다(노이즈)" | `unrelated_snake`가 훨씬 낮음 → **표기 특정적** |
| "텍스트가 바뀌어서 그런 것" | 텍스트는 **한 글자도 안 바꿨다**. 캐시만 편집 |
| "어텐션이 원인" | `key` 단독 효과 < `value`, 그리고 `key_value ≈ value` |
| "전 층에 골고루 퍼져 있다" | 봉우리 층 외에는 거의 0 (층별 독립 측정이라 가능한 진술) |
| "문맥이 원래 선호에 영향이 없다" | `S_clean − S_base` 격차가 커서 판정 불가 0개 |

## §9. 용어 대조표 — 쉬운 말 ↔ 전문 용어 ↔ 코드 심볼

| 화면·문서의 쉬운 말 | 전문 용어 | 기호 | 코드 심볼 |
|---|---|---|---|
| 얼마나 보나 | 어텐션 가중치 (축 A) | `a_nj` | `attention_weight` |
| 무엇이 실려 오나 | Value 벡터 (축 B) | `v_j` | `v_norm`, `value` |

| 방향이 다른가 | Value 코사인 유사도 | `cos(v_camel, v_snake)` | `v_cosine` |
| 준수 선호 (점수) | 로그 오즈비 | `S` | `preference_score`, `S_int` |
| 되돌림 정도 | 회복률 (normalized recovery) | `(S_int−S_base)/(S_clean−S_base)` | `recovery` |
| 깨끗 / 위반 / 개입 | clean / corrupted(base) / patched | `S_clean` `S_base` `S_int` | 동일 |
| 바꿔넣는 이름 | 공여자 (donor) | — | `intervention.donor` |
| 음성 통제 | negative control | — | `unrelated_snake` |
| 형태 통제 | form control | — | `unrelated_camel` |
| 평균 덮어쓰기 | mean-pooled activation patching | `v̄_i` | `token_unit="mean"` |
| 바꾼 조각 수 | 패칭된 토큰 위치 수 | — | `n_substituted_tokens` |
| 판정 불가 | 분모 미달(효과 없음) | `|S_clean−S_base| < 1` | `GAP_MIN`, `recovery_rate → None` |
| 어느 층 | 층 인덱스 / 상대 깊이 | `ℓ`, `ℓ/(L−1)` | `per_layer`, `relative_layer()` |
| 묶음 | 이름 블록(반복 표본) | `b = 0..41` | `pool_block` |
| 속을 바꾼다 | KV 캐시 패칭 | — | `_score_layer_kind` |
| 조각 | 서브워드 토큰 | — | token |
| 처리 단계 | 층(layer) | `ℓ` | `layer` |
| 묶음 어텐션 그룹 | GQA KV group | `H_q / H_kv` | `GQAInfo.group_size` |
