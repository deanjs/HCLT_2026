## A. 주장에 직접 영향 (🔴)

### A1. 회복률의 분모가 "개입이 도달할 수 없는 변화"까지 포함한다

**[근거]**
`runner._preference_setup`에서 `S_clean`은 문맥 12개를 **전부 camel로 다시 렌더한 별도 프롬프트를
처음부터 forward**해서 얻는다.

```python
comp_text = render_preceding([(s, target) for s, _ in specs])   # 새 문자열 → 새 forward
```

그런데 개입(`S_int`)은 **위반 프롬프트의 층 ℓ 캐시에서, 위반 이름 토큰 자리만** 덮는다.
두 상태의 차이는 이름 6개에 그치지 않는다:

- `split_config` → `splitConfig`로 바뀌면 **토큰 수가 달라져 뒤따르는 모든 토큰의 절대 위치가 밀린다.**
- 코드 블록 뒤의 ```` ``` ````, 요청 문장, chat 템플릿 꼬리 토큰들의 표현이 **camel 문맥 아래서
  전부 다시 계산**된다. 이 위치들은 우리가 건드리지 않는다.
- 문맥 이름들 **서로 간의** 상호작용(앞 이름이 뒤 이름의 표현에 주는 영향)도 재계산된다.

**[영향]** 분모 `S_clean − S_base`가 **개입으로는 원리적으로 도달 불가능한 성분**을 포함한다.
따라서 회복률은 **구조적으로 과소평가**된다. `results.md`가 "봉우리에서도 0.20~0.58, 완전 회복 아님"을
한계로 적었는데, **그 미달분 중 얼마가 '층이 여러 개라서'이고 얼마가 '분모가 부풀어서'인지 현재 구분 불가**다.
→ "신호가 여러 층에 퍼져 있다"는 해석의 근거가 약하다.

**[수정]** **도달 가능 상한(oracle)을 재서 두 번째 정규화를 병기한다.**
전 층을 **동시에** 패칭한 상태의 점수 `S_all`을 조건당 1회 추가로 재면:

```
현행 회복률   = (S_int − S_base) / (S_clean − S_base)     ← 도달 불가 성분 포함
도달가능 회복률 = (S_int − S_base) / (S_all  − S_base)     ← 우리 개입이 낼 수 있는 최대 대비
```

`S_all`이 `S_clean`에 가까우면 A1은 기우였다고 결론 나고, 많이 낮으면 층별 회복률을 `S_all` 기준으로
다시 보고해야 한다. **비용:** 조건당 forward 2회 추가(전체의 1% 미만). `_score_layer_kind`를
층 리스트를 받도록 일반화하면 구현 몇 줄.

### A2. Key 조건은 RoPE 위상 편향을 안은 채 측정됐다 (결론과 같은 방향)

**[근거]** 세 가지가 겹친다.

1. HuggingFace 구현에서 **KV 캐시의 Key는 RoPE가 이미 적용된(post-RoPE) 상태**다. Value에는
   위치 정보가 없다.
2. 공여 프롬프트와 위반 프롬프트는 **토큰 수가 다르다**(camel/snake 토큰화 차이). 같은 역할의 이름이라도
   절대 위치가 어긋나 → 공여 Key에 **다른 위치의 회전**이 실려 온다.
3. mean-pool은 한술 더 떠 **서로 다른 위치의 회전된 Key 2~4개를 평균**낸다. 회전 벡터의 평균은
   어느 위치의 Key도 아니다. Value 평균에는 이런 왜곡이 없다.

**[영향]** Key 경로의 효과가 **체계적으로 과소 측정**된다. 우리 결론이 "Value > Key"이므로
**편향의 방향이 결론과 일치** — 리뷰어가 가장 먼저 찌를 지점이다.
현재 `results.md` §3의 결론 2("내용이 어텐션보다 유의하게 더 되돌린다")는 이 편향을 통제하지 않았다.

**[영향이 덜한 부분]** `key_value ≈ value`(어텐션을 더해도 안 늘어남)라는 **충분성(sufficiency)**
주장은 이 편향에 덜 민감하다. Key를 얹어서 이득이 없다는 것은 Key가 왜곡됐어도 "Value만으로 이미
천장"이라는 뜻이기 때문. → **논문에서는 충분성을 주 논거로, 우열 비교를 보조 논거로 배치**하는 것이 안전하다.

**[수정]** 둘 중 하나(또는 둘 다).

- **위상 보정 패칭:** 공여 Key에 `R(위반위치) R(공여위치)⁻¹`를 곱해 위치 위상만 맞춰 이식.
  RoPE는 차원쌍 회전이라 구현이 어렵지 않다(`cos/sin` 캐시 재사용).
- **위치 정합 공여:** 공여 프롬프트를 위반 프롬프트와 **토큰 수가 같도록** 구성해 위상차를 없앤다.
  (A3의 수정과 함께 하면 한 번에 해결)

**비용:** 전자는 `_score_layer_kind`에 회전 보정 한 블록 추가 + 재실행. 후자는 자극 설계 수정 + 재실행.
어느 쪽이든 **Key 조건만 다시 돌리면 되므로 전체의 1/3.**

### A3. 무관(unrelated) 공여 프롬프트가 "6함수·단일 표기" 모듈이라 통제가 오염됐다

**[근거]** 실제로 렌더해 확인했다(`prompt.unrelated_specs` → `render_preceding`).

| 공여 조건 | 공여 프롬프트의 실제 모습 |
|---|---|
| `compliant` | **12개 함수, 전부 camel** (= clean 프롬프트 재사용) |
| `unrelated_camel` | **6개 함수, 전부 camel** (별도 프롬프트) |
| `unrelated_snake` | **6개 함수, 전부 snake** (별도 프롬프트) |

Value는 문맥이 반영된 표현이다(층 ℓ까지의 어텐션·FFN을 거친 값). 따라서 공여 Value는
**그 이름 자체의 형태뿐 아니라 "이 모듈 전체가 camel/snake다"라는 문맥 정보까지** 싣는다.

**[영향]** 두 통제 주장이 모두 약해진다.

- **형태 통제**(`unrelated_camel ≈ compliant` → "이름 암기가 아니라 형태가 옮겨진다"):
  두 공여의 **문맥 구성이 다르다**(12함수 vs 6함수). 비슷하게 나온 것이 오히려 우연일 수 있고,
  차이가 났더라도 이름 정체성 때문인지 문맥 길이 때문인지 구분 불가.
- **음성 통제**(`unrelated_snake` 낮음 → "표기 특정적"):
  공여가 **전부 snake인 모듈**에서 왔으므로, 낮게 나온 것이 "그 이름이 snake라서"인지
  "모듈 전체가 snake라서"인지 갈라낼 수 없다. → `results.md` §2-2의 "camel공여 − snake공여" 격차가
  **과대평가**됐을 가능성.

**[수정]** 공여 프롬프트를 **위반 프롬프트와 같은 규격(12함수, 준수 6 / 위반 6)** 으로 만들고,
공여로 쓸 6개 이름만 원하는 표기로 지정한다. 그러면 세 공여 조건이 **문맥 구성·길이가 동일**해지고,
A2의 위치 위상 문제도 크게 줄어든다.
**비용:** `prompt.unrelated_specs` 호출부(`runner._preference_setup`)에서 공여 문맥을 12개로 채우는
수정 + `unrelated_*` 두 조건 재실행(전체의 2/3).

### A4. 생성 기반 검증이 없고, 그 코드는 현재 설정에서 크래시한다 (버그)

**[근거]** step3 본실험은 **점수(S)** 만 잰다. "선호 점수가 실제로 다른 이름을 쓰게 만드는가"는
`mode='intervene_generate'` 경로가 담당하는데, 그 경로는 `align_name_tokens`를 호출한다:

```python
# model.intervene_generate
pairs, skipped = align_name_tokens(..., mode=token_unit)
```

그런데 `align_name_tokens`는 `"all"`/`"last"`만 받는다. 통일 설정은 `token_unit="mean"`이다.
확인:

```
>>> align_name_tokens([[1,2]], [[3]], mode='mean')
ValueError: mode는 "all" 또는 "last"만 허용한다
```

→ **통일 재실험 설정으로는 생성 기반 검증을 돌릴 수 없다.** `intervene_generate`는 mean-pool 경로가
아예 구현돼 있지 않다(`_score_layer_kind`에만 있다).

**[영향]** 리뷰어의 필수 질문 — "로그확률 차이가 0.5 회복됐다는데, 그래서 모델이 실제로 camelCase로
쓰기는 하나?" — 에 답할 데이터가 없다. 점수 기반 주장만으로는 **행동 수준 인과가 미확인**이다.

**[수정]** 두 단계.

1. `model.intervene_generate`에 mean-pool 분기 추가 — `_score_layer_kind`의 mean 경로를 그대로
   재사용하면 되므로 실질 3~5줄(치환부를 공통 헬퍼로 뽑는 편이 낫다).
2. **봉우리 층에서만** 생성 검증 실행: 모델 4 × 묶음 42 × 공여 3 = 504회 생성.
   봉우리 층 하나만 하면 되므로 전 층 스윕보다 훨씬 가볍다.
   지표: 개입 전/후 첫 함수 이름의 표기 전환율(snake→camel).

## B. 재현·검증 불가 (🟠)

### B1. 결과 폴더 레이아웃이 저장 규약과 어긋나 재분석이 실패한다

**[근거]** `results.py::result_path`는 `results/<step>/<slug>.json`을 만든다. 노트북 셀 ⑤도
그 경로로 되읽는다. 그런데 저장소에 커밋된 실제 레이아웃은:

```
results/step3_code-cause_results_qwen/       ← 모델별로 수동 분리됨
results/step3_code-cause_results_deepseek/
results/step3_code-cause_results_llama/
results/step3_code-cause_stable/             ← 이름 규칙도 다름(_results_ 없음)
```

확인: 노트북이 찾는 `results/step3_code-cause/<slug>.json` → **존재하지 않음**.

**[영향]** 저장소를 새로 클론해 노트북 셀 ⑤·⑥을 돌리면 **결과 0개를 읽는다.** 그림·표를 다시 만들려면
사람이 파일을 옮겨야 한다는 사실이 어디에도 적혀 있지 않다.

**[수정]** 504개를 `results/step3_code-cause/`로 합친다(슬러그에 모델명이 이미 들어 있어 충돌 없음).
결과물은 불변이지만 **경로 이동은 내용 변경이 아니다**. 옮기지 않기로 한다면, 노트북 셀 ⑤에
폴더 목록을 명시하는 주석·코드를 넣어야 한다.

### B2. 504개 결과 전부 `meta`가 비어 있다

**[근거]** 전 파일 스캔 결과 `meta == {}` → **504 / 504.**
`results.ResultRecord`는 `meta`를 "git sha, 실행 환경 등"으로 명시해 두고 있는데 아무도 안 채웠다.

**[영향]** **KV 캐시 레이아웃은 transformers 버전에 따라 세 갈래**(`_cache_kv` 참조)이고,
dtype·양자화·GPU도 수치에 영향을 준다. 지금 결과가 어느 환경에서 나왔는지 **복원 불가**다.
"deepseek 8bit로 돌렸나?"를 확인할 방법이 조건 스키마의 `quantization` 필드(전부 `null`)뿐이다.

**[수정]** 노트북 셀 ④에서 저장할 때 채운다(이후 실험분부터):

```python
import transformers, torch, subprocess
meta = {"git_sha": subprocess.check_output(["git","rev-parse","HEAD"]).decode().strip(),
        "transformers": transformers.__version__, "torch": torch.__version__,
        "gpu": torch.cuda.get_device_name(0), "gqa": str(handle.gqa_info())}
```

기존 504개는 불변 규약상 **수정하지 않고**, 환경을 아는 범위에서 `docs/step3/results.md`에 追記한다.

**[수정]** 집계·작도 셀을 노트북에 추가하거나 `docs/step3/` 아래 스크립트로 커밋한다.
CI 정의(정규근사인지 t분포인지, 짝지음 차이를 먼저 계산했는지)도 함께 명시.

### B4. GQA·모델 config가 step3 결과에 기록되지 않는다

**[근거]** `extra.gqa`는 **관측 모드(step2/4)에만** 담긴다. 개입 모드 결과에는 없다.
`n_substituted_tokens`는 있지만 head 수·KV head 수·head_dim은 없다.

**[영향]** 논문 모델 표(층 수 / head / KV head / group size)를 결과 파일에서 못 뽑는다.
"KV group 단위 치환"이 각 모델에서 몇 개 query head를 동시에 바꿨는지 **결과만 보고는 알 수 없다.**

**[수정]** `_run_intervention_sweep`의 `extra`에 `"gqa": handle.gqa_info()` 3필드와
`"num_layers"`를 추가(이후 실험분부터). 기존 결과는 모델 config를 따로 조회해 문서에 적는다.

### B5. step3 전용 테스트가 없다

**[근거]** `tests/`에 `test_step1/2/4`, `test_stepA/A1/A2/B/C`는 있으나 **step3용 파일이 없다.**
mean-pool **정렬**(`align_name_groups`)은 `test_step4.py`가 커버하지만, step3이 실제로 쓰는
**전 층 스윕의 편집→측정→복구 루프**(`_score_layer_kind`)는 어떤 테스트도 건드리지 않는다.

**[영향]** 다음 항목이 회귀해도 아무도 모른다:
- 복구가 빠져 층 편집이 **누적**되는 사고(층별 독립성이 깨짐 → 결론 전체가 무효)
- `kind` 분기(`key`/`value`/`key_value`)가 엉뚱한 텐서를 건드리는 사고
- transformers 업그레이드로 `_cache_kv` 레이아웃이 또 바뀌는 사고

**[수정]** 가짜 캐시(작은 텐서 3층짜리)와 항등 모델 스텁으로 다음을 검증하는 `tests/test_step3.py`:
① 측정 후 캐시가 **비트 단위로 원상복구**되는가 ② `kind='value'`가 keys를 안 건드리는가
③ mean-pool 값이 공여 위치 평균과 일치하는가.

## C. 서술을 정정해야 하는 것 (🟡)

### C1. 방법론 문서의 "덮은 자리 수" 표가 틀렸다 (수정 완료)

**[근거]** `docs/step3/방법론_코드와개념.md` §5.3이 모델당 단일값(qwen 12, deepseek 19 …)으로 적었다.
504개 전수 확인 결과 **묶음마다 다르다**:

| 모델 | 덮은 자리 수 범위 | 평균 |
|---|---|---|
| Qwen2.5-Coder-3B | 12 ~ 15 | 12.7 |
| Llama-3.2-3B | 12 ~ 15 | 12.7 |
| StableCode-3B | 18 ~ 24 | 20.4 |
| DeepSeek-Coder-6.7B | **19 ~ 29** | 22.5 |

**[수정]** 방법론 문서의 표를 범위·평균으로 교체했다. C4도 이 사실에서 나온다.

### C2. "토큰 길이 편향이 회복률에서 상쇄된다"는 논증은 근사다

**[근거]** 방법론 문서 §4.3은 길이 편향을 **상태와 무관한 가법 상수 `c`** 로 놓고 소거했다.
그러나 로그확률은 상태 의존이므로 `c`가 세 상태에서 정확히 같다는 보장이 없다.

**[영향]** 상쇄는 **1차 근사**로만 성립한다. 결론이 뒤집힐 정도는 아니지만 "완전히 상쇄된다"는 서술은 과장.

**[수정]** 문장을 "대부분 상쇄된다(1차 근사)"로 낮추고, 강건성 점검으로 **토큰당 평균 로그확률**
버전의 `S`를 같은 결과에서 재계산해 봉우리 층 결론이 유지되는지 확인한다(추가 실험 불필요 —
후보 토큰 수만 기록하면 되는데, 현재 결과에 그 값이 없어 재실행이 필요하다는 점이 B4와 연결된다).

### C3. 봉우리 층 선택 편향 — 검증해보니 문제없었으나 근거가 저장소에 없다

**[근거]** `results.md` §2-3은 **42묶음 평균 곡선에서 argmax로 봉우리 층을 고르고, 같은 42묶음으로
그 층의 평균·신뢰구간을 보고**한다. 원칙적으로는 승자의 저주(winner's curse)가 낀다.
실제로 분할검증(앞 21묶음으로 층 선택 → 뒤 21묶음에서 평가)을 돌려봤다:

| 모델 | 전체 봉우리 | 앞 21묶음 | 뒤 21묶음 | value@봉우리(전체) | 교차검증값 |
|---|---|---|---|---|---|
| Qwen | L25 | L25 | L25 | 0.536 | 0.535 |
| DeepSeek | L20 | L20 | L20 | 0.200 | 0.210 |
| Llama | L15 | L15 | L15 | 0.583 | 0.565 |
| StableCode | L18 | L18 | L18 | 0.255 | 0.231 |

**봉우리 층이 네 모델 모두 분할에 무관하게 동일**하고 교차검증값도 거의 같다 → **선택 편향은 무시할 수준.**

**[영향]** 결과는 안전하다. 문제는 **이 검증이 저장소 어디에도 없다는 것**이다. 리뷰어가 물으면
답할 근거가 없다.

**[수정]** 이 분할검증을 B3의 집계 스크립트에 포함해 커밋하고, `results.md` §2-3에 한 줄 추가.

### C4. 모델 간 회복률 "크기" 비교는 개입 강도 차이와 뒤섞여 있다

**[근거]** C1의 표대로 덮은 자리 수가 모델마다 다르다(평균 12.7 vs 22.5). 회복률은 이 값을 통제하지 않는다.
묶음 내 상관을 재보니 약했다(봉우리 층·Value 기준 `r` = qwen +0.10, deepseek −0.20, llama +0.15,
stable +0.01) → **한 모델 안에서는 개입 강도가 회복률을 좌우하지 않는다.**

**[영향]**
- **모델 내 결론**(층 국소화, Value>Key, 통제 통과)은 안전하다.
- **모델 간 크기 비교**("deepseek는 0.20으로 낮다")는 위험하다. 토크나이저가 이름을 잘게 쪼개
  더 많은 자리를 덮었는데도 회복이 낮다는 건, 모델 특성인지 mean-pool이 조각 수가 많을수록
  더 뭉개는 탓인지 구분되지 않는다.

**[수정]** `results.md` §3에서 모델 간 절대 크기 비교 문장("deepseek은 되돌림 자체가 작고")에
단서를 달거나, 덮은 자리 수를 공변량으로 넣은 비교를 병기한다.

## D. 주장 범위를 좁혀야 하는 항목 (과대주장 위험)

결함은 아니지만 **현재 서술이 데이터보다 넓다.** 논문에서 아래로 제한해야 한다.

| 지금 말할 수 있는 범위 | 넘어가면 안 되는 선 |
|---|---|
| **층 단위** 국소화 | head·뉴런 단위 (§5.5 — 전 KV head를 한꺼번에 바꿨다) |
| 문맥 **6/12 위반 한 점**에서의 인과 | "위반 비율 전 구간에서" (비율 축은 step1이 담당, step3은 안 훑었다) |
| **긍정형·약한 어조** 지침에서의 인과 | 부정형·강한 어조 (step3 조건은 `positive`/`weak` 고정) |
| **합성 코드**(본문 `return value` 동일)에서의 인과 | 실제 저장소 코드 (`Source.REPO` 경로는 step3에서 미사용) |
| `def ` 강제 직후 시점의 **두 후보 상대 선호** | 자연 생성 분포에서의 준수율 (teacher-forcing 시점 고정, A4 미검증) |
| **camel ↔ snake 2종** | 그 외 표기 규약(PascalCase, kebab 등) |
