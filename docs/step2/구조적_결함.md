## A. 결과 타당성을 흔드는 것

### A1. 표기 배정이 seed와 무관하게 고정된다 — 셔플 두 개가 서로 상쇄

**증상.** 어떤 seed를 줘도 **블록 안 앞 6개 이름은 항상 camel, 뒤 6개는 항상 snake**가 된다.
seed는 프롬프트 안 배치 순서만 바꾼다.

**원인.** `prompt.py:83` `build_preceding_code`와 `prompt.py:62` `_pool_indices`가
**같은 seed로 같은 길이(12) 리스트를 셔플**한다 → **동일한 순열**이 두 번 적용되어 상쇄된다.

```python
notations = [target]*6 + [violation]*6
random.Random(condition.seed).shuffle(notations)   # 순열 P
...
idxs = list(range(start, start+n))
random.Random(condition.seed).shuffle(idxs)        # 같은 순열 P
funcs = [NAME_PAIR_POOL[j].render(nt) for j, nt in zip(idxs, notations)]
# → 풀 위치 (start+p) 는 p<6 일 때 항상 target 표기
```

**확인.** seed 42 / 7 / 123 전부:

```
camel이 되는 블록내 위치 = [0,1,2,3,4,5]   snake = [6,7,8,9,10,11]
```

**영향.** 두 가지가 갈린다.

1. **seed 강건성 검증이 불가능하다.** "표기 배정을 바꿔도 같은 결과가 나오나"를 물을 수 없다.
   `conditions.py`의 `pool_block` 설명은 "seed는 표기·위치 변주"라고 쓰여 있는데 **표기 변주는 실제로 없다.**
   (마스터 플랜 §1은 "seed는 배치 순서만 정한다"고 되어 있어 계획서와는 일치한다 — 두 문서가 어긋나 있다.)
2. **camel 진영과 snake 진영이 서로 다른 이름 집합이다** (같은 이름이 두 표기로 등장하는 일이 없다).
   즉 within-item 대조가 아니라 between-item 대조다.

**단, 어휘 수준 균형은 우연히 잘 맞아 있다** (실측):

| | 개수 | 고유 동사 | 고유 명사 | 평균 글자수 |
|---|---|---|---|---|
| camel 진영 | 252 | 50 | 50 | 13.69 |
| snake 진영 | 252 | 50 | 50 | 13.60 |

동사·명사 50개 전부가 양 진영에 모두 나타나고 이름 길이도 거의 같다. 같은 (동사,명사) 짝이 양쪽에
있는 경우는 0. → **치명적 교란은 아니지만, "같은 이름을 표기만 바꿔 비교했다"고 쓰면 사실과 다르다.**

**고칠 방향(택1, 승인 필요).**
- (a) **서술만 정정** — "표기별로 짝지어진 서로 다른 이름 504개(어휘 수준 균형)"로 정확히 쓰고,
  seed 변주 주장을 뺀다. 재실험 없음. 가장 싸다.
- (b) **표기 배정을 seed와 분리** — `_pool_indices`에 다른 seed(예: `seed+1`)를 쓰거나, 배정용
  RNG를 따로 둔다. → step2 재실행 필요(168개).
- (c) **완전 대조 설계** — 같은 블록을 표기 배정만 뒤집은 쌍(A/B)으로 두 번 돌려 within-item 비교.
  가장 강하지만 실행량 2배.

> 어느 쪽이든 **기존 `results/`는 불변**(§6)이다. (b)·(c)는 새 조건으로 추가 실행하는 형태가 된다.

### A2. 합 기반 구간 지표가 토큰 수에 비례해 부풀려진다

**증상.** `attention_weight`와 `av_norm`은 구간 **합**인데, 모델에 따라 snake 구간의 토큰이 훨씬 많다.

**원인.** `attention_probe.py:36` `span_metrics` — 설계상 합이 맞다(어텐션 질량). 문제는
**비교 대상 두 구간의 토큰 수가 다른데 그대로 비교**한 것.

**확인.** 42블록 평균 토큰 수(이름 12개 기준):

| 모델 | camel | snake | 비율 |
|---|---|---|---|
| Qwen | 12.60 | 12.74 | 1.011 |
| Llama | 12.60 | 12.74 | 1.011 |
| **DeepSeek** | 16.21 | 22.45 | **1.385** |
| **StableCode** | 14.21 | 20.40 | **1.436** |

원인은 토크나이저: DeepSeek·StableCode는 밑줄을 독립 토큰으로 뗀다(`' split','_','config'`).

**영향.** DeepSeek·StableCode의 "snake를 더 본다"는 관측 중 일부가 토큰 수 때문이다.
`token_detail`이 저장돼 있어 **재실행 없이** 토큰당 평균으로 재계산 가능하고, 실제로 해 보면:

| 모델 | 합 기준 최대 격차 | 토큰당 평균 기준 |
|---|---|---|
| Qwen | 어텐션 L25 −0.0290 / ‖a·v‖ L33 −0.2634 | L25 −0.0022 / L33 −0.0190 |
| DeepSeek | 어텐션 L0 −0.0241 / ‖a·v‖ L26 −0.2878 | L0 −0.0008 / L26 −0.0093 |
| Llama | 어텐션 L12 −0.0104 / ‖a·v‖ L24 −0.0724 | L12 −0.0008 / L24 −0.0055 |
| StableCode | 어텐션 L15 −0.0278 / ‖a·v‖ L17 −0.2273 | L15 −0.0011 / **L15** −0.0080 |

**부호와 봉우리 층은 유지**(StableCode ‖a·v‖ 봉우리만 L17→L15). 정성 결론은 살아 있다.

**고칠 방향.** 지표를 바꿀 필요는 없다. **논문·`results.md`에 싣는 수치를 토큰당 평균으로
정규화하거나, 합 기준임을 명시**한다. 집계 함수에 `attention_weight_per_token` 같은 파생 필드를
추가하는 것도 방법(기존 결과에서 재계산 가능하므로 재실험 불필요).

### A3. Key 평균 덮어쓰기가 RoPE 위상을 상쇄시킨다 — 우리 가설 쪽으로 편향

> **가장 심각하다.** step3·5의 결론("Value는 되고 Key는 안 된다")이 **방법 때문에 만들어질 수 있다.**

**증상(예상).** `token_unit='mean'`으로 Key를 치환하면, 주입되는 key 벡터의 크기가 원본보다 작아져
어텐션 점수가 전반적으로 줄어든다 → **Key 경로가 실제보다 무력해 보인다.**

**원인.** 두 사실의 결합.

1. 이 4개 모델(Llama 계열·Qwen2·StableLM 계열)의 HF 구현은 **RoPE를 적용한 뒤의 key를 캐시에 저장**한다.
   즉 캐시의 key에는 **그 토큰이 있던 위치의 회전 위상**이 박혀 있다.
2. `model.py:334-347`의 mean 경로는 **여러 위치의 key를 평균**한다.

```python
km = dk[:, :, dps, :].mean(dim=2)   # 서로 다른 위치의 post-RoPE key 평균
```

위상이 다른 회전 벡터를 평균하면 **상쇄 간섭**이 일어나 `‖km‖ < mean‖k‖`가 된다. Value는 RoPE가
적용되지 않으므로 이 문제가 없다. → **K와 V가 대칭적으로 다뤄지지 않는다.**

여기에 더해, 공여 프롬프트(전부 준수)와 위반 프롬프트는 토큰 수가 달라 **같은 이름이라도 위치가
밀려 있다**. 위치가 다른 key를 가져오면 위상 자체가 틀린 값이 들어간다.

**영향.** `key` 회복률이 낮게 나와도 그것이
"어텐션 경로가 원래 무력해서"인지 **"우리가 key를 망가뜨려서"** 인지 구분할 수 없다.
우리 주장이 정확히 "Key는 안 되고 Value는 된다"이므로, **결론이 방법의 산물일 위험이 직결된다.**

**고칠 방향(step3 착수 전 필수).**
1. **진단 먼저.** 치환 시점에 `‖km‖ / mean_p ‖dk[...,p,:]‖` 비율을 층별로 찍어 남긴다.
   1에 가까우면 문제 없음, 뚜렷이 작으면 아래 대안을 쓴다. (구현: `_score_layer_kind`에서
   비율을 계산해 결과 `extra`에 저장 — 측정만 추가, 로직 변경 없음.)
2. **대안 A — 위치 정합 치환.** 공여 위치를 위반 위치와 맞춘 뒤(같은 인덱스) 치환.
3. **대안 B — Key만 `last` 모드.** Value는 mean, Key는 단일 토큰(평균 안 함)으로 위상 보존.
   단 두 경로의 치환 강도가 달라지므로 그 자체를 보고해야 한다.
4. **대안 C — 축 A는 어텐션 직접 조작으로 검증.** 어텐션 배율을 직접 건드리면 RoPE 교란 없이
   축 A를 볼 수 있다. Key 치환 결과를 이것과 교차검증하면 위 위험을 근본적으로 피한다.
   **단 `ATTENTION_AMPLIFY`는 현재 구현이 없다 → §C4를 먼저 해결해야 쓸 수 있다.**

> 최소한 (1) 진단 + (4) 교차검증은 하고 가야 한다. 그래야 "Key가 안 된다"를 주장할 수 있다.

### A4. `av_norm`은 "실제 기여"가 아니다 — 상한이고 `W_O` 이전 값이다

**원인.** 우리가 재는 것은 `Σ_j a_j ‖v_j‖` 인데, 잔차에 실제로 더해지는 것은 `W_O · (Σ_j a_j v_j)` 다.

```
Σ_j a_j ‖v_j‖  ≥  ‖ Σ_j a_j v_j ‖        (삼각부등식 — 벡터 상쇄를 무시한 상한)
그리고 출력 사영 W_O 를 통과하기 전 값이다.
```

**영향.** `results.md`의 "잔차 스트림에 **실제로 밀어 넣는 양**"이라는 표현은 이 두 단계를 건너뛴다.
(인과 해석 과장은 커밋 `456ccc4`에서 이미 정정했으나, **상한·pre-`W_O` 성질은 아직 안 적혀 있다.**)

**고칠 방향.** 지표 유지, 서술 정정. "구간이 기여할 수 있는 **크기의 상한**(방향 상쇄·출력 사영 이전)"으로
쓴다. 순 기여가 필요하면 `‖Σ_j a_j v_j‖`를 별도 지표로 추가해야 하는데 이는 **재실행이 필요**하다
(`token_detail`에는 노름만 있고 벡터가 없다).

### A5. 캐시 개입의 범위 한정 — "층 L을 바꿨다"는 과장

**원인.** `_preference_context`가 프롬프트를 **한 번 forward해 캐시를 만든 뒤**(`model.py:266`)
층 L의 칸을 고친다. 따라서:

- 바뀌는 것: **채점 forward에서 층 L이 그 위치들로부터 읽는 K/V.**
- 바뀌지 않는 것: **프롬프트 토큰 자신의 층 L+1 이상 표현**(이미 계산됨, 재계산 안 함).

**영향.** 이건 우리 RQ("생성 시점에 문맥에서 무엇을 읽어 오는가")에 맞는 설계라 **결함이라기보다
범위 한정**이지만, 이 한정을 빼고 쓰면 과장이 된다. 특히 "층 L을 조작했다"는 표현은
활성값 패칭(전체 재계산)과 혼동을 부른다.

**고칠 방향.** 서술을 "층 L의 **KV 읽기 경로**를 반사실로 바꿨다"로 고정한다. 코드 변경 없음.

## B. 엔진이 통일 규격을 못 돌리는 것 (실행 차단)

### B1. `mean` 모드를 못 받는 경로가 두 개 — step3에서 바로 막힌다

**증상.** CLAUDE.md §3이 치환 규격을 **평균 덮어쓰기(mean)로 통일**했는데, 두 경로가 이를 거부한다.

| 경로 | 호출 | 결과 |
|---|---|---|
| `mode='intervene_generate'` | `model.py:603` `align_name_tokens(mode=token_unit)` | `token_unit='mean'` → **ValueError** |
| `mode='vcosine'` | `model.py:521` 동일 | `token_unit='mean'` → **ValueError** |

**확인.**

```
align mode=all: OK / mode=last: OK / mode=mean: 거부 → mode는 "all" 또는 "last"만 허용한다
```

**영향.**
- `intervene_generate`(치환 후 실제 생성으로 재확인 — 선호 점수의 직관적 뒷받침)를
  **통일 규격으로 돌릴 수 없다.** step3에서 쓰려면 지금 막힌다.
- `vcosine`(v 방향 관측)은 `mean`이 개념상 안 맞는 게 맞다(코사인은 짝이 필요). 그런데
  `token_unit`이 **Condition 하나에 필드 하나**라, `mean`으로 설정한 조건은 vcosine을 **아예 못 돌린다.**
  더 나쁜 것은 `all`로 돌리면 DeepSeek·StableCode는 토큰 수 불일치로 **전부 스킵되어 `n_pairs=0`**,
  결과가 빈 `per_layer`가 된다(§C2와 같은 조용한 실패).

**고칠 방향.**
1. `intervene_generate`에 mean 경로 추가 — `_score_layer_kind`의 mean 분기를 그대로 재사용하면 된다
   (이미 검증된 로직, 중복 구현 금지).
2. vcosine은 `token_unit`과 분리된 자체 정렬 인자를 갖게 하거나, `mean`이면 자동으로 `last`로
   내려가되 **그 사실을 결과에 기록**한다(조용한 대체 금지).

### B2. 합성 코드 + JavaScript 조건을 표현할 수 없다 — step1의 JS 절반이 설계대로 안 된다

**증상.** CLAUDE.md §3은 **step1(생성)만 파이썬 + 자바스크립트 2종**을 요구한다. 그런데 스키마상
자바스크립트는 **실제 저장소 파일(`source=REPO`)로만** 가능하다.

**원인.** `conditions.py` `PrecedingCode.__post_init__`:

```python
else:  # SYNTHETIC
    if self.repo_lang is not None or self.repo_file is not None:
        raise ValueError("source=SYNTHETIC에는 repo_lang·repo_file을 두지 않는다")
```

그리고 `prompt.py:32` `_lang()`은 `source=REPO`가 아니면 무조건 `"python"`을 돌려준다.

**확인.**

```
합성 JS: 불가 → source=SYNTHETIC에는 repo_lang·repo_file을 두지 않는다
```

**영향.** step1의 핵심 조작은 **준수 개수(0~12) 스윕**인데, `source=REPO`는 설계상
`n_compliant`·`composition`을 쓰지 않는다("실코드는 관습이 고정"). 즉
**자바스크립트에서는 준수율 절벽(RQ1의 주 조작)을 만들 수 없다.**
현재 번들된 JS 파일은 3개(`buildURL.js`·`formDataToJSON.js`·`utils.js`)뿐이라
실코드 경로로도 스윕을 대신할 수 없다.

**고칠 방향.** 언어 축을 `source` 축에서 분리한다 — `PrecedingCode`에 `lang` 필드를 두고
`SYNTHETIC`에서도 `javascript`를 허용, `TaskSpec.render`가 언어별로 `def`/`function`을 내도록 확장.
(`naming.first_js_name`은 **이미 있다** — 추출기는 준비돼 있고 렌더러만 없다.)
스키마 변경이므로 §1 승인 대상.

### B3. 결과 경로 규약과 저장소 레이아웃이 어긋난다 — 재개·재분석이 코드로 안 된다

**증상.** `result_path()`가 가리키는 경로에 파일이 없다.

```
코드가 찾는 경로: results/step2_code-observe/<slug>.json           → 존재? False
실제 저장소     : results/step2_code-observe_results_{qwen,deepseek,llama,stable}/<slug>.json
```

**원인.** 노트북은 `results/step2_code-observe/`에 저장한 뒤 zip으로 내려받아 **모델별 폴더로 나눠**
커밋했다. 슬러그에 이미 모델명이 들어 있어(`qwen2-5-coder-3b-instruct__...`) 분리할 필요가 없었다.

**영향.**
- 새로 클론한 환경에서 노트북을 다시 돌리면 **재개 로직이 기존 결과를 못 보고 168개를 전부 재실행**한다
  (`todo = [c for c in conditions if not result_path(c, step=STEP).exists()]`).
- 셀 ⑥·⑦의 재분석(`load_result(result_path(...))`)도 파일을 못 찾는다.

**고칠 방향.** `results/step2_code-observe/` 한 폴더로 합친다(파일명이 이미 모델을 구분한다).
파일 내용은 그대로이므로 **`git mv`만으로 끝나고 불변 규약도 지켜진다.** 이후 스텝도 같은 규약을 따른다.

## C. 조용한 실패 / 판정 규칙 미구현

### C1. 구간 탐색이 실패해도 조용히 `None`이 된다

**원인.** `find_char_spans`는 못 찾으면 빈 리스트를 돌려주고, `span_metrics`는 빈 구간을
`{attention_weight: None, ...}`로 기록할 뿐 **아무도 오류를 내지 않는다**. 관측 경로에는
치환 쪽의 `skipped_names` 같은 실패 신고 장치가 없다.

**위험 지점.** `instruction` 구간은 시스템 문장이 chat 템플릿 안에 **문자 그대로** 남아 있다는 가정에
의존한다. 템플릿이 공백·이스케이프를 건드리는 모델이 들어오면 **조용히 0 토큰**이 된다.
(현재 4개 모델은 37~43 토큰으로 정상 — 문제가 터진 적은 없다. 구조적 취약점이다.)

**고칠 방향.** `observe_generation_query`가 반환 전에 **기대 구간이 비어 있으면 경고/예외**를 내고,
`span_token_counts`와 함께 `empty_spans` 목록을 결과에 남긴다.

### C2. 정렬 실패(치환 0자리)가 "개입해도 효과 없음"과 구분되지 않는다

**원인.** `align_name_tokens(mode='all')`이 전부 스킵하면 `pairs=[]` → 아무것도 안 덮는다 →
`S_int == S_base` → **`recovery = 0.0`**. 이는 "개입했는데 안 돌아왔다"와 **수치가 완전히 같다.**

**영향.** DeepSeek·StableCode에서 `all` 모드는 §3.3의 토큰 수 불일치 때문에 **전부 스킵되는 것이 정상**이다.
그대로 돌리면 "이 모델들은 Value 치환이 안 먹힌다"는 **정반대 결론**이 나온다.
`skipped_names`·`n_substituted_tokens`에 기록은 남지만, 집계할 때 이를 보지 않으면 놓친다.

**고칠 방향.** `n_substituted_tokens == 0`이면 `recovery`를 **`0.0`이 아니라 `None`(판정 불가)** 으로
기록한다. 한 줄이면 되고, 이게 §4의 "판정 불가로 분리" 규칙과도 맞는다.

### C3. "판정 불가" 임계값이 사실상 없다

**원인.** `intervention.py:87` `recovery_rate`의 가드는 `eps=1e-9`다.

```python
denom = s_clean - s_base
if abs(denom) < eps: return None
```

이건 **0 나누기 방지용 부동소수 가드**일 뿐이다. CLAUDE.md §4가 요구하는
"영향력이 0에 가까운 조건(지침·문맥이 안 먹히는 모델)은 판정 불가로 분리"는 **구현돼 있지 않다.**

**영향.** `S_clean − S_base = 0.01`이면 분모가 살아 있으므로 회복률이 계산되는데, 분자의 작은 잡음이
수십 배로 증폭되어 **회복률 3.7 같은 값**이 나온다. 층 스윕 곡선이 이런 값 하나로 망가진다.

**고칠 방향.** 연구적 임계값(예: `|S_clean − S_base| < 0.5`)을 조건으로 두고 그 아래는 판정 불가로
표시한다. 임계값은 step3 예비 실행에서 S 분포를 보고 정하는 게 맞다 — **지금 숫자를 못 박지 말 것.**

### C4. `ATTENTION_AMPLIFY`가 스키마에만 있고 구현이 없다 — 조용히 "회복률 0"을 돌려준다

**원인.** `InterventionKind.ATTENTION_AMPLIFY`와 `Intervention.amplify`는 `conditions.py`에 정의돼
있고 검증까지 하지만, **`amplify`를 실제로 쓰는 코드가 없다.** `_score_layer_kind`(`model.py:331`)는

```python
edit_k = kind in ("key", "key_value")
edit_v = kind in ("value", "key_value")
```

만 보므로 `kind="attn_amplify"`면 **둘 다 False → 아무것도 안 바꾸고** `S_int == S_base` →
**`recovery = 0.0`** 이 저장된다. 예외도 경고도 없다.

**확인.**

```
$ grep -rn "amplify" src/harness/ --include=*.py | grep -v conditions.py
(출력 없음 — 스키마 밖에서는 아무도 쓰지 않는다)
```

**영향.** 이 조건을 돌리면 **"어텐션을 키워도 준수 행동이 안 돌아온다"는 결과가 자동으로 나온다.**
그런데 이건 정확히 우리가 Spotlight를 반박하려는 결론이다. → **반박 근거가 미구현 코드의
산물이 될 수 있다.** §A3의 교차검증 대안도 이것 때문에 지금은 쓸 수 없다.

**고칠 방향.** 구현하거나(어텐션 후처리 훅으로 지침·코드 구간 가중치에 배율 적용 후 재정규화),
**구현 전까지 이 조건을 실행 금지**한다. 최소 조치로 `_score_layer_kind`가 미지원 `kind`에
대해 **예외를 던지게** 한다(조용한 0 반환 금지). §C2와 같은 계열의 문제다.

## D. 지표 정의와 구현의 불일치

### D1. `subsequent_violation_rate` — 주석은 조건부, 구현은 무조건부

`runner.py:505` `_run_generation`:

```python
subsequent = notations[1:]
subsequent_violation = sum(n != target for n in subsequent) / len(subsequent)
...
# 자기증폭: 첫 함수가 위반일 때 뒤 함수도 위반인 비율     ← 주석
```

구현은 **첫 함수의 결과와 무관하게** 2·3번째 함수의 위반율을 낸다. 주석이 말하는 조건부 확률
`P(뒤 위반 | 첫 위반)`이 아니다. step1의 "자기증폭" 서술이 이 필드에 기대면 어긋난다.

**고칠 방향.** 조건부가 필요하면 집계 단계에서 `first_violated == True`인 실행만 골라 평균한다
(필드는 그대로 두고 이름을 정확히 하거나 주석을 고친다). **원자료는 이미 `turn_notations`에 다 있으므로
재실행은 불필요하다.**

### D2. 지침 지시어 구간이 구조적으로 2:1 — 그리고 관측과 치환의 구간 정의가 다르다

**원인 1 (등장 횟수).** 지침 3문장에서 `camelCase`는 **2번**(rule + closed), `snake_case`는 **1번**(closed) 나온다.

```
In this project we generally write function names in camelCase.        ← rule
Every function name uses one of two styles only: camelCase or snake_case.  ← closed
```

`find_char_spans`는 **모든 등장**을 잡으므로 실측 토큰 수가 구조적으로 2:1이다:

| 모델 | `instr_target_word` | `instr_viol_word` |
|---|---|---|
| Qwen / Llama | 4 | 2 |
| DeepSeek | 6 | 4 |
| StableCode | 4 | 3 |

**원인 2 (정의 불일치).** 치환 쪽 `_locate_target_tokens(span_kind="literal")`(`model.py:658`)은
`spans[0]` — **첫 등장만** 쓴다. 즉 **관측은 2곳, 치환은 1곳**을 대상으로 한다.

**영향.** step4에서 "모델이 지시어를 더 본다"를 §A2의 합 지표로 주장하면 **등장 횟수 때문**이다.
그리고 step4(관측)와 step5(치환)가 서로 다른 구간을 보므로 두 결과를 직접 이어 붙일 수 없다.
목표 표기를 snake로 뒤집는 조건에서는 비대칭 방향도 뒤집혀 조건 간 비교까지 흔들린다.

**고칠 방향.**
1. 관측 구간을 **rule 문장의 등장만** 잡도록 좁혀 치환과 정의를 맞춘다(권장 — 두 스텝이 같은 대상을 본다).
2. 또는 등장 횟수로 정규화하고, 두 스텝의 구간이 다르다는 것을 명시한다.

기존 step2 결과에도 이 필드들이 들어 있지만 **step2의 주인공은 `code_camel`/`code_snake`** 이므로
step2 결론에는 영향이 없다. **step4 착수 전에 정해야 한다.**
