# step2 — 코드 신호 관측 결과 (RQ2, 관측)

> **스텝:** step2 (코드 관측) · **RQ:** RQ2 (관측) · **브랜치:** `step2/code-observe`
> **무엇을 봤나:** 문맥에 섞인 `camelCase` 이름과 `snake_case` 이름이, 이름을 만들려는 그 순간
> 모델 **안에서 어디에·어느 층에서 다르게 드러나는가**.
> 이 스텝은 **관측(첫 단서)** 이다. 어텐션이 원인인지 내용(Value)이 원인인지의 **최종 판정은 step3(인과)** 에서 한다.
>
> **코드·방법론을 깊이 보려면:** [`코드와_방법론.md`](코드와_방법론.md) — 트랜스포머 Q/K/V·GQA·KV 캐시 개념부터
> 우리 코드의 흐름, 관측 지표의 정확한 정의, KV 치환(step3·5)의 원리와 주의사항까지.

- 모델 4개 × 묶음 42개 = **파일 168개**, 시드 42, 내부 값 치환 없음(`int-none`, 순수 관측).
- 아래 수치·그래프는 **묶음 42개 평균**(각 묶음 = 함수 12개짜리 문맥 하나).

---

## 1. 관측한 "504개 점"이 무엇인가

| 항목 | 내용 |
|---|---|
| 전체 이름 수 | **504개** 함수 이름 |
| 구성 | 동사 × 명사 조합으로 만든 이름을, **camel 252개 + snake 252개** |
| 묶는 방식 | **12개씩 42묶음**(`pool_block` 0~41). 한 묶음 안은 항상 **camel 6개 + snake 6개**로 균형 |
| 한 묶음(=파일 1개)이 하는 일 | 그 12개 이름을 문맥으로 넣고 모델이 **새 이름을 만들려는 마지막 위치**에서, 문맥의 각 구간을 얼마나·어떻게 보는지 1회 측정 |
| 왜 504개인가 | 42묶음 × 12개 = 504. 즉 **504개 이름이 각각 정확히 한 번씩** 문맥에 등장(중복 없이 전수 커버) |
| "점"의 의미 | 그래프의 각 선은 이 **504개 이름(=42묶음)에 대한 평균**이다. 한 점 = 특정 모델·특정 층에서, 그 구간(camel 또는 snake)에 대한 42묶음 평균값 |

요약하면 **504개 점 = 표기 규약만 다르고 역할은 같은 이름 504개**이고, 이를 camel/snake 두 진영으로 갈라
"모델이 두 진영을 층별로 다르게 처리하는가"를 본다. 균형 설계(묶음마다 6:6)라서 camel과 snake의 차이가
이름 개수·문맥 길이 같은 곁가지 때문이 아니라 **표기 규약 자체 때문**이 되도록 통제돼 있다.

## 2. 결과 JSON 각 필드의 의미

파일 하나(`...__pre-c6of12-pool-syn-b{N}__ins-pos-camel-w__int-none__s42.json`)의 구조와 뜻.

### 2-1. 최상위·조건 필드

| 필드 | 의미 |
|---|---|
| `step` / `rq` | 스텝 이름(`step2_code-observe`) / 연구질문(`RQ2`) |
| `prediction` | 실행 전 예측(관측이라 `null`) |
| `created_at` | 측정 시각 |
| `condition.model` | 어떤 모델인지(`name`/`family`/`dtype`) |
| `condition.preceding` | 문맥 설정. `n_functions=12`(문맥 이름 수), `n_compliant=6`(그중 규약 준수 개수 → 6:6 균형), `composition=pool`·`source=synthetic`(합성 이름 묶음), `pool_block`=몇 번째 묶음(0~41) |
| `condition.instruction` | 지침 설정. `form=positive`, `target_notation=camel`(지침이 요구하는 규약), `strength=weak` |
| `condition.intervention.kind=none` | **값 치환 없음** = 순수 관측 |
| `condition.seed=42` | 고정 무작위값 |
| `condition.token_unit=all` | 구간 점수를 그 구간 **토큰 전체** 기준으로 집계 |

### 2-2. 지표 필드 (`metrics`)

측정의 핵심은 세 "축"이다. 이름을 만들려는 마지막 위치의 어텐션 한 행이 문맥의 각 구간을 어떻게 처리하는지를 층별로 잰다.

| 필드 | 쉬운 말 | 정확한 정의 |
|---|---|---|
| `attention_weight` | **축 A — 얼마나 보나** | 그 구간 토큰들에 준 어텐션의 **합**(query head 평균). "구간을 얼마나 쳐다보는가" |
| `v_norm` | **축 B — 내용 크기** | 그 구간 토큰이 실어 나르는 표현 벡터 ‖v‖의 **평균**(KV head별). "구간이 담은 내용의 크기" |
| `av_norm` | **축 A×B — 밀어 넣는 양(크기)** | ‖a·v‖ = 어텐션 × 내용 크기의 **합**. "그 구간이 잔차 스트림에 **실제로 밀어 넣는 양(크기)**". 단, 이 **크기값**이 행동을 바꾸는 원인인지(어텐션 탓인지 내용 탓인지)는 **관측만으론 못 가른다** — av = a×‖v‖라 둘이 안 분리됨. 인과 판정은 step3 몫 |
| `compliance_*` | (관측이라 비어 있음) | 생성 준수율 계열은 step1 담당 |
| `per_layer.{L}` | **층별로** 위 세 축을, 5개 구간 각각에 대해 저장 | 아래 5개 구간 |

`per_layer`의 각 층에는 `{구간}__{축}` 형태로 15개 값(5구간 × 3축)이 들어 있다.

| 구간 이름 | 무엇을 가리키나 |
|---|---|
| `code_camel` | 문맥 속 **camelCase 이름 6개**의 토큰들 |
| `code_snake` | 문맥 속 **snake_case 이름 6개**의 토큰들 |
| `instruction` | 지침 문장 전체 (step4에서 본격 사용) |
| `instr_target_word` | 지침 속 요구 규약 단어(예: "camelCase") |
| `instr_viol_word` | 지침 속 반대 규약 단어 |

> step2의 주인공은 **`code_camel` vs `code_snake`** 다. 나머지 세 구간은 같은 파일에 함께 기록돼 있지만
> 지침 쪽 분석(step4)에서 쓴다.

### 2-3. 부가 정보 (`metrics.extra`)

| 필드 | 의미 |
|---|---|
| `mode` | `observe`(관측) |
| `group_names` | 그 묶음에 실제로 들어간 camel/snake 이름 목록 |
| `span_token_counts` | 각 구간이 토큰 몇 개였는지(camel 12 · snake 12로 균형 확인용) |
| `seq_len` | 전체 입력 토큰 길이 |
| `gqa` | 어텐션 head 구조(`num_attention_heads`·`num_key_value_heads`·`group_size`). **평균 덮어쓰기(mean-pool)를 KV group 단위로 맞추기 위한 핵심 정보** — 모델마다 다름 |
| `token_detail` | 어떤 토큰이 어느 구간에 속했는지 상세 |

## 3. 결과

### 3-1. 그래프 (지표별)

그래프는 **세 지표 순서**로 본다: ① Attention weight(축 A) → ② ‖a·v‖(축 A×B, 기여량) → ③ ‖v‖(축 B, 내용 크기).
각 지표마다 **모델 4개를 하나씩 따로** 실었다(파일: `figures/<지표>_<모델>.png`).

모든 그림 공통:

- **파란선 = camelCase 문맥**, **빨간선 = snake_case 문맥**, 가로축 = 층 번호(왼쪽=입력쪽, 오른쪽=출력쪽).
- 값은 모두 **묶음 42개(=이름 504개) 평균**. 두 선이 **벌어질수록** 그 층에서 두 규약을 다르게 처리한다는 뜻.

---

#### ① Attention weight — 축 A: 모델이 그 구간을 **얼마나 쳐다보는가**

> 이 지표만 보면 "규약이 다른 이름을 더/덜 본다"는 **어텐션 차이**를 알 수 있다. 다만 이건 "보는 양"일 뿐,
> 잔차 스트림에 밀어 넣는 양(크기)은 ②에서 본다.

![attention-qwen](figures/attention_qwen.png)
![attention-deepseek](figures/attention_deepseek.png)
![attention-llama](figures/attention_llama.png)
![attention-stable](figures/attention_stable.png)

- **Qwen:** 두 선이 거의 완전히 겹침 → 어텐션으로는 두 규약을 거의 구분 안 함.
- **DeepSeek:** 중·후반 층 내내 **snake를 더 본다**(빨강>파랑). 네 모델 중 어텐션 분리가 가장 큼.
- **Llama:** 격차가 작음, 후반부에서 snake 쪽이 살짝 더.
- **StableCode:** **중반 층(15~17 부근)** 에서 snake를 더 보는 구간이 뚜렷.

#### ② ‖a·v‖ — 축 A×B: 그 구간이 잔차 스트림에 **실제로 밀어 넣는 양(기여량)**

> 잔차 스트림에 밀어 넣는 **양(크기)**. **두 선이 벌어지는 층 = 두 규약이 다르게 처리되는 양이 큰 층.**
> (이 크기 차이가 행동을 바꾸는 원인인지까지는 관측으로 못 정함 → step3 인과에서 판정.)

![av-deepseek](figures/av_deepseek.png)
![av-llama](figures/av_llama.png)

- 네 모델 모두 기여량은 **층이 깊어질수록 커지고**, camel–snake 격차의 **봉우리가 후반부**에 몰린다(§3-2 표).
- **DeepSeek**이 가장 크게 벌어지고(후반 층에서 snake가 뚜렷이 높음), **Qwen**은 ‖v‖ 폭증 층(32~33)에서만 잠깐 벌어진다.

> **두 선이 겹치면 "내용 크기 자체는 규약과 무관"** 이라는 뜻. ②의 격차가 내용 크기 차이 때문인지 아닌지를 가른다.

- 네 모델 모두 camel·snake의 **‖v‖는 거의 완전히 겹친다**(내용 크기는 규약과 무관). 크기 자체는 층이 깊어질수록 함께 커질 뿐.
- 즉 ②의 기여량 격차는 "snake가 더 큰 벡터를 실어서"가 아니라 **①의 어텐션 차이가 후반부에서 커진 ‖v‖에 곱해져 증폭된 것**이다(→ §4 해석).

#### ④ camel − snake 격차 — 두 축을 **한 그림에** (어텐션 격차 vs 기여량 격차)

> ①·②를 겹쳐 본 그림. **청록 = 어텐션 격차**(왼쪽 눈금), **보라 = 기여량 ‖a·v‖ 격차**(오른쪽 눈금).
> 눈금이 좌우 2개인 이유: 두 격차의 **절대 크기가 대략 10배 다르다**(어텐션 ±0.03 vs 기여량 ±0.3). 나눠야 둘 다 보인다.
> 음수 = snake가 더 큼(대부분의 층에서 snake 쪽이 더 보고·더 밀어 넣음).

![gap-deepseek](figures/gap_deepseek.png)
![gap-llama](figures/gap_llama.png)
![gap-stable](figures/gap_stable.png)

- **핵심:** 청록(어텐션 격차)은 작고 비교적 평평한데, 보라(기여량 격차)는 **후반부로 갈수록 크게 벌어진다.**
- **Qwen:** 두 격차 모두 대부분 0 근처, ‖v‖ 폭증 층(25·33)에서만 보라가 아래로 툭 튐.

## 4. 해석

**세 가지 관측 사실:**

1. **내용 크기(‖v‖)는 camel과 snake가 거의 똑같다.** 지표 ③(‖v‖) 그림들에서 파란선·빨간선이 대부분의 층에서
   겹쳐 있다. 즉 "snake 토큰이 더 큰 벡터를 싣는다" 같은 **내용 크기 자체의 차이는 없다.**

2. **어텐션(축 A) 차이는 존재하지만 절대값은 작다**(층별 격차 대체로 ≤ 0.03; DeepSeek만 상대적으로 큼).
   방향은 모델 대부분에서 snake를 조금 더 본다.

3. **실제 기여량(‖a·v‖) 격차는 후반 층에서 급격히 벌어진다.** 지표 ②(‖a·v‖) 그림들. 그리고 그 봉우리는
   4개 모델 모두 **네트워크 후반부**에 몰려 있다(§3-2).

**이것이 뜻하는 것 (그리고 뜻하지 않는 것):**

- 두 규약을 가르는, **행동에 실제로 영향을 줄 신호는 "후반 특정 층"에 집중**돼 있다. 이건 4개 모델에서
  일관되게 재현된 뚜렷한 관측이다. → **"어디"에 대한 첫 답: 후반 층.**
- 다만 ‖v‖가 두 규약 사이에 사실상 동일하므로, 기여량(‖a·v‖) 격차는 **"같은 어텐션 차이가 후반부에서 커진
  ‖v‖에 곱해져 증폭된 것"** 으로도 똑같이 설명된다. 즉 **관측만으로는 어텐션 탓인지 내용(Value) 탓인지
  가를 수 없다.** ‖a·v‖ = a × ‖v‖ 라서 관측값에서 둘을 분리할 수 없기 때문이다.
- 따라서 이 스텝은 계획대로 **"내용 쪽인가 어텐션 쪽인가의 첫 단서"** 까지만 준다. **최종 판정은
  step3(인과)** — 후반 각 층에서 어텐션만 / 내용만 / 둘 다 바꿔치기해서 **무엇을 바꿔야 행동이 되돌아오는지**
  로 확정한다.

**판정 가능성(§4 규칙):** 기여량(‖a·v‖)이 4개 모델 모두 0에서 충분히 떨어져 있어(후반 층에서 0.2~2.4대),
**네 모델 모두 "판정 불가" 아님** — step3 인과 실험 대상으로 모두 적격.
