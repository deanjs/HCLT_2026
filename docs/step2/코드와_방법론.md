## §1. 배경 — 트랜스포머 한 층에서 무슨 일이 일어나는가

논문에 필요한 개념을 **우리 실험에서 쓰이든 안 쓰이든** 전부 정리한다. 각 항목 끝에
`[우리 실험: …]` 표시로 실제 사용 여부를 붙였다.

### 1.1 토큰 · 임베딩 · 잔차 스트림(residual stream)

입력 문자열은 **토크나이저**가 정수 토큰 열 `t_1…t_n`으로 쪼갠다. 각 토큰은 임베딩 행렬을 거쳐
`d_model` 차원 벡터가 되고, 이 벡터가 층을 지나며 **더해지기만 하면서** 위로 올라간다. 이 통로를
**잔차 스트림**이라 부른다.

```
x^(0)_i  =  embed(t_i)
x^(L)_i  =  x^(L-1)_i  +  Attn^L(x^(L-1))_i  +  FFN^L( x^(L-1)_i + Attn^L(...)_i )
```

핵심 성질: **각 층은 잔차 스트림을 덮어쓰지 않고 "읽고 더한다"**. 그래서
"어느 층이 무엇을 더 얹었나"를 층별로 따로 물을 수 있고, 우리 실험이 **층 스윕**을 하는
근거가 된다. `[우리 실험: 층 인덱스가 곧 이 잔차 스트림의 단계다]`

### 1.2 어텐션의 Q · K · V — 역할 분담

층 `L`, head `h`에서 각 위치 `i`의 잔차 벡터로부터 세 벡터를 만든다.

| 기호 | 이름 | 만드는 법 | 직관 |
|---|---|---|---|
| `q_i` | **Query** | `W_Q x_i` | 지금 위치가 **무엇을 찾는가** (질문) |
| `k_j` | **Key** | `W_K x_j` | 그 위치가 **무엇으로 검색되는가** (색인) |
| `v_j` | **Value** | `W_V x_j` | 그 위치가 **무엇을 건네주는가** (내용) |

어텐션은 두 단계다.

```
(1) 얼마나 볼까      a_{i,j} = softmax_j ( q_i · k_j / sqrt(d_head)  + causal_mask )
(2) 무엇을 가져올까   o_i     = Σ_j  a_{i,j} · v_j          → concat(heads) → W_O → 잔차에 더함
```

- `a_{i,j}`는 **스칼라**이고 `≥ 0`, 그리고 `Σ_j a_{i,j} = 1` (한 행이 확률분포).
- **causal mask**: `j > i`는 `-inf` → 미래를 못 본다. 그래서 우리가 보는 "마지막 위치의 어텐션 행"은
  **문맥 전체를 볼 수 있는 유일하게 완전한 행**이다.
- **결정적 분해:** 행동을 바꾸는 경로는 정확히 둘뿐이다 — `a`(=Key·Query가 정함)를 바꾸거나,
  `v`(=Value)를 바꾸거나. **이것이 우리 연구의 축 A / 축 B다**(→ §2).

`[우리 실험: a는 관측·치환 모두, v는 관측·치환 모두, q는 "마지막 위치의 질문"으로만 간접 사용]`

### 1.3 head · multi-head · GQA

- **head**: 위 계산을 `d_head` 차원 부분공간에서 독립적으로 여러 벌 돌린다. head마다 다른 것을 본다.
- **MHA(Multi-Head Attention)**: query head 수 `Hq` = key/value head 수 `Hkv`.
- **GQA(Grouped-Query Attention)**: `Hkv < Hq`. 여러 query head가 **하나의 KV를 공유**해 메모리를 줄인다.
  `group_size = Hq / Hkv`이고, HuggingFace 구현(`repeat_kv`)의 매핑은

  ```
  query head h  →  kv head  h // group_size
  ```

  **KV를 치환할 때 반드시 이 group 단위로 해야 한다**(CLAUDE.md §3). 우리 모델 4개의 실측값:

  | 모델 | 층수 | Hq | Hkv | group_size | 형태 |
  |---|---|---|---|---|---|
  | Qwen2.5-Coder-3B | 36 | 16 | 2 | 8 | GQA |
  | DeepSeek-Coder-6.7B | 32 | 32 | 32 | 1 | MHA |
  | Llama-3.2-3B | 28 | 24 | 8 | 3 | GQA |
  | StableCode-3B | 32 | 32 | 32 | 1 | MHA |

  → **모델마다 다르므로 매번 확인해야 한다.** 코드에서는 `ModelHandle.gqa_info()`(`model.py:50`)가
  config에서 읽어 오고, 관측 결과 JSON의 `metrics.extra.gqa`에 그대로 저장된다.

`[우리 실험: 필수. 어텐션은 [Hq, seq], value는 [Hkv, seq, d]로 모양이 달라 둘을 곱하려면 매핑이 필요하다]`

### 1.4 FFN (Feed-Forward Network, = MLP)

어텐션 뒤에 오는 위치별 2층 신경망: `FFN(x) = W_down · σ(W_up x)` (요즘은 SwiGLU 게이트 변형).
어텐션이 **위치 사이에서 정보를 옮기는** 장치라면, FFN은 **한 위치 안에서 정보를 변환·저장**하는
장치다. 해석가능성 문헌에서 FFN을 "key–value 메모리"로 보는 관점이 있는데, 이때의 key/value는
**어텐션의 K/V와 전혀 다른 것**이다 — 용어 충돌에 주의해야 한다(논문에서 반드시 구분 표기).

`[우리 실험: 직접 건드리지 않는다]`
왜 안 건드리는가: 우리 질문은 "**문맥의 다른 위치**(선행 코드 이름, 지침 단어)가 새 이름을 쓰려는
위치에 어떻게 영향을 주는가"다. 위치 간 전달은 어텐션이 전담하므로, 개입 지점도 어텐션의 입력
(K/V)이 정확한 자리다. FFN 개입은 "같은 위치 안의 변환"을 바꾸는 것이라 우리 RQ와 맞지 않는다.
다만 **관측 결과의 해석**에는 FFN이 등장한다: 후반 층에서 `‖v‖`가 커지는 현상은 잔차 스트림이
FFN 기여로 계속 부풀기 때문이다(→ §5.7).

### 1.5 위치 정보 — RoPE (Rotary Position Embedding)

현대 디코더 모델은 위치를 **q와 k에 회전을 곱해** 넣는다. 중요한 비대칭:

```
q, k  ←  RoPE 적용 (위치에 따라 회전)      v  ←  적용 안 함
```

그리고 HuggingFace 구현은 **RoPE를 적용한 뒤의 k를 캐시에 저장**한다. 따라서 우리가 캐시에서 꺼낸
`key`에는 **그 토큰이 있던 위치의 위상이 이미 박혀 있다**. 이 사실은 §6.6(K 치환의 주의사항)에서
결정적으로 쓰인다.

주의할 표현: "v에는 위치 정보가 없다"는 **RoPE가 v에 곱해지지 않는다**는 뜻일 뿐이다.
`v_j = W_V x_j`이고 `x_j`는 이전 층들을 거치며 위치 의존 정보를 이미 흡수했으므로,
"v가 위치와 무관하다"는 말은 틀리다. `[우리 실험: K 치환 해석의 전제]`

### 1.6 KV 캐시(past_key_values) — 우리 개입 지점

자기회귀 생성에서 같은 프롬프트의 K/V를 매 토큰마다 다시 계산하면 낭비다. 그래서 **층별로
`[batch, Hkv, seq, d_head]` 텐서 두 개(key, value)를 저장**해 두고 재사용한다.

우리에게 중요한 것은 **속도가 아니라 이것이 "문맥이 앞으로 전달할 내용"의 완전한 물리적 표현**이라는
점이다. 캐시의 `(layer, position)` 한 칸을 고치면, 그 이후의 forward에서 **그 층이 그 위치로부터
읽는 것이 정확히 그 값으로 바뀐다**. 텍스트는 한 글자도 안 바꾸고 내부만 반사실로 만들 수 있다.

`transformers` 버전마다 레이아웃이 달라 `_cache_kv()`(`model.py:674`)가 세 가지를 모두 처리한다:
`cache.layers[i].keys/.values` (4.54+) · `cache.key_cache[i]` (구형) · `cache[i][0]` (legacy tuple).
`[우리 실험: 관측(V 꺼내기)·치환(K/V 덮어쓰기) 양쪽의 핵심]`

### 1.7 출력 — 언임베딩 · 로짓 · 로그확률

마지막 층 잔차에 `W_U`를 곱하면 어휘 크기 벡터(**로짓**)가 나오고, `log_softmax`로 로그확률이 된다.
여러 토큰으로 쪼개지는 이름의 확률은 **토큰별 로그확률의 합**이다(체인 룰):

```
log P("removeDuplicates") = Σ_k log P( tok_k | prefix, tok_<k )
```

`[우리 실험: 준수 선호 점수 S의 재료 — model.py:290-302]`

### 1.8 teacher forcing · greedy 디코딩

- **teacher forcing**: 모델이 스스로 생성하게 두지 않고 우리가 원하는 문자열을 강제로 이어 붙여
  "다음에 올 토큰"의 조건을 못 박는 기법. 우리는 프롬프트 뒤에 **`"def "` 를 붙여**
  *다음 예측 토큰이 반드시 함수 이름의 첫 조각이 되게* 만든다(`forced_prefix`, `model.py:105`).
  이렇게 해야 "이름을 쓰려는 바로 그 순간"의 내부 상태를 관측할 수 있다.
- **greedy 디코딩**: 매 스텝 최고 확률 토큰 선택(`temperature=0`). 같은 입력 → 항상 같은 출력이므로
  재현성이 보장된다(`model.py:87-95`).

`[우리 실험: teacher forcing은 전 경로 필수, greedy는 생성 실험(step1)·생성기반 치환]`

## §2. 우리 연구의 좌표계 — 축 A(Key/어텐션)와 축 B(Value/내용)

### 2.1 두 축은 임의로 정한 게 아니다

§1.2의 항등식을 다시 본다.

```
o_i  =  Σ_j  a_{i,j} · v_j            a는 Q·K가 정함,  v는 W_V가 정함
```

"이름을 쓰려는 위치 `i`가 문맥의 이름 `j`로부터 받는 것"은 **오직 이 두 인자의 곱**이다. 따라서
"문맥의 규약 위반 이름이 행동을 망친다"면 원인은 논리적으로 **둘 중 하나이거나 둘 다**다.

| | 이름 | 무엇을 뜻하나 | 손잡이 |
|---|---|---|---|
| **축 A** | 얼마나 보나 | `a_{i,j}` — 그 토큰에 준 어텐션 질량 | **Key** 치환 / 어텐션 재가중 |
| **축 B** | 무엇을 싣나 | `v_j` — 그 토큰이 건네는 내용 벡터 | **Value** 치환 |

### 2.2 이 좌표계가 곧 우리 주장이다

기존 접근(Spotlight 계열)은 **"지침을 덜 봐서 못 지킨다"** 고 진단하고 **축 A를 키운다**
(지침 구간 어텐션 증폭). 우리 주장은 **문제도 손잡이도 축 B에 있다**는 것이다.

그래서 실험 설계가 이렇게 나온다.

| | 하는 일 | 판정 |
|---|---|---|
| **step2·4 (관측)** | a, ‖v‖, ‖a·v‖를 층·구간별로 잰다 | **첫 단서만**. 관측으로는 축을 못 가른다(→ §5.7) |
| **step3·5 (인과)** | Key만 / Value만 / 둘 다 치환하고 되돌림 정도를 잰다 | **판정**. Value만 바꿔도 되돌아오면 축 B 확정 |
| (통제) | 어텐션 증폭(`ATTENTION_AMPLIFY`) | 축 A를 직접 키워도 안 되면 Spotlight 반박 |

**Key 치환이 "어텐션 개입"인 이유:** Key를 바꾸면 `q·k` 점수가 바뀌고 softmax를 거쳐 `a`가 바뀐다.
즉 Key 치환 = **"이 토큰이 얼마나 검색될지"만 반사실로** 바꾸는 것이고, 그 토큰이 건네는 내용은
그대로다. 반대로 Value 치환 = **"얼마나 보는지는 그대로 두고 건네는 내용만"** 바꾸는 것이다.
두 조작이 축 A/축 B를 **깨끗하게 분리**한다는 것이 이 방법론의 핵심 이점이다.

## §3. 데이터와 프롬프트 형식

### 3.1 이름 풀 504개 — 어떻게 만들어지나

`src/harness/tasks.py:117` `_build_name_pool()`

```
동사 50개 × 명사 50개  →  (동사, 명사) 짝을 shift 규칙으로 중복 없이 504개 선택
  1단계: 원래 80개  = 앞 20동사 × 20명사, shift 0~3   ← 파일럿과의 연속성 보존(순서까지 고정)
  2단계: 504가 될 때까지 shift를 늘리며 50×50 공간에서 중복 없이 채움
```

각 짝은 `TaskSpec`(`tasks.py:22`)이 되고, 표기에 따라 두 이름으로 렌더된다.

```python
TaskSpec(words=("parse","header"), description="parses the header and returns it",
         params=("value",), body=("return value",))
→ camel: parseHeader      → snake: parse_header
```

**결정적 통제:** 풀 전 항목의 `params`·`body`가 **완전히 동일**하다(`(value)` 받아 `return value`).
함수들 사이에서 변하는 것은 **오직 이름의 표기**뿐이다. 그래서 camel/snake 그룹 간 차이가
"하는 일이 달라서"가 아니라 **표기 때문**임이 설계로 보장된다.

**커버리지:** 504 = 12 × 42. `pool_block` b가 풀의 `[12b, 12b+12)`를 덮으므로,
b=0…41을 다 돌면 **504개 이름이 정확히 한 번씩** 쓰인다(중복 없는 전수 커버).
seed 42는 **어떤 이름을 쓰는지는 안 바꾸고** 블록 안의 배치 순서와 표기 배정만 섞는다
(`prompt.py:62` `_pool_indices`, `prompt.py:83`).

### 3.2 실제 프롬프트 (block 0, seed 42, Qwen 기준)

**system (지침) — `prompt.py:42`:**

```
You are helping extend an existing Python module.
In this project we generally write function names in camelCase.
Every function name uses one of two styles only: camelCase or snake_case.
```

## §5. 관측 방법론 상세 — step2가 실제로 한 일

### 5.1 "구간"을 어떻게 정확히 집는가 (offset_mapping)

우리는 토큰 인덱스가 아니라 **문자열**로 관심 대상을 안다("`decodeNode`라는 이름"). 이를 토큰
인덱스로 바꾸는 두 단계:

1. `find_char_spans(text, ["def decodeNode("])` → 문자 구간 `(s, e)`. 이때 **이름 단독이 아니라
   `def <이름>(` 형태로 검색**한다. 이름만 찾으면 본문·호출부에서 우연히 겹칠 수 있기 때문.
   찾은 뒤 `s+4 ~ e-1`로 잘라 **이름 부분만** 남긴다(`model.py:156`).
2. `locate_token_spans(offsets, char_spans)` → 토큰 `[ts,te)`와 문자 구간 `[cs,ce)`가
   **겹치면**(`ts < ce and te > cs`) 그 토큰을 구간에 넣는다. 이름이 하위토큰 여러 개로 쪼개져도
   전부 포착된다. 특수 토큰(`te <= ts`, 빈 offset)은 건너뛴다.

**결정적 세부:** chat 템플릿을 `tokenize=False`로 **먼저 문자열로 뽑고**, 그 문자열을 다시
토크나이저에 넣어 offset을 받는다(`model.py:134-145`). 이렇게 해야 모델이 실제로 먹는 토큰 열과
offset이 **정확히 같은 것**이 된다. (템플릿에서 바로 토큰을 받으면 offset과 어긋난다.)

### 5.2 왜 `attn_implementation='eager'` 인가

`output_attentions=True`로 어텐션 가중치를 **꺼내려면 eager 어텐션이어야 한다**. SDPA/FlashAttention은
softmax 행렬을 메모리에 만들지 않는 fused 커널이라 가중치를 `None`으로 돌려준다
(`model.py:719`, 노트북 셀 ⑤). 대신 eager는 `[1, Hq, seq, seq]` 전체 행렬을 층마다 뜨므로
**메모리를 많이 쓴다** — 그래서 step2 프롬프트를 수백 토큰으로 유지했고, DeepSeek-6.7B는 T4에서
OOM 가능성을 노트북 셀 ①에 미리 적어 두었다(§5 규칙).

### 5.3 무엇을 꺼내 쓰는가 (텐서 모양)

| 꺼내는 것 | 원본 모양 | 우리가 쓰는 부분 |
|---|---|---|
| `out.attentions[L]` | `[1, Hq, seq, seq]` | `[0, :, -1, :]` → **마지막 query 행** `[Hq, seq]` |
| `past_key_values[L].values` | `[1, Hkv, seq, d]` | `.norm(dim=-1)` → **토큰별 ‖v‖** `[Hkv, seq]` |

**"마지막 행"의 의미:** 입력 끝이 `"def "` 이므로, 마지막 위치의 query는 **"이제 함수 이름을
써야 하는데 무엇을 참고할까"** 라는 질문 그 자체다. 이 한 행이 step2의 관측 대상 전부다.

### 5.4 세 지표의 정확한 정의 (`attention_probe.py:23,36`)

토큰 `j` 하나에 대해:

```
a_j   = mean_h  a[h, j]                                 (query head 평균)
av_j  = mean_h  a[h, j] · ‖v[ h // group_size , j ]‖     ← GQA 매핑이 여기 들어간다
v_j   = mean_k  ‖v[k, j]‖                                (KV head 평균)
```

구간 `S`에 대해:

| 지표 | 집계 | 왜 이 집계인가 |
|---|---|---|
| `attention_weight` | `Σ_{j∈S} a_j` (**합**) | 각 head의 행은 전체 위치에 대해 1로 합해진다. 구간 합 = 그 구간이 가져간 **어텐션 질량**(0~1) |
| `av_norm` | `Σ_{j∈S} av_j` (**합**) | 구간이 잔차에 밀어 넣은 **총량** |
| `v_norm` | `mean_{j∈S} v_j` (**평균**) | 크기 지표이므로 토큰당 평균이 맞다 |
| `n_tokens` | 구간 토큰 수 | 합↔평균 환산용 |

**GQA 방법 A의 항등식 — 근사가 아니라 정확하다.**
`a[h,j]`는 **스칼라이고 음이 아니므로**

```
‖ a[h,j] · v[h//gs, j] ‖  =  a[h,j] · ‖ v[h//gs, j] ‖
```

가 정확히 성립한다. 즉 우리는 큰 텐서를 곱하지 않고 **어텐션 스칼라와 노름 스칼라만** 곱하면 된다.
이 덕분에 집계가 순수 파이썬 함수로 내려와 GPU 없이 검증 가능해졌다.

### 5.5 반드시 알아야 할 편향 — `av_norm`·`attention_weight`는 **합**이다

`attention_weight`와 `av_norm`이 구간 **합**이므로, **구간의 토큰 수가 많으면 값이 커진다.**
그런데 §3.3에서 봤듯 DeepSeek·StableCode는 snake 이름을 1.4배 많은 토큰으로 쪼갠다.
즉 이 두 모델에서 "snake를 더 본다"의 **일부는 토큰 수 때문**이다.

결과 JSON에는 `token_detail`(토큰별 a/av/v 전부)과 `span_token_counts`가 이미 저장돼 있으므로,
**재실행 없이** 토큰당 평균으로 다시 계산할 수 있다. 실제로 계산해 본 결과:

| 모델 | 합 기준 최대 격차(camel−snake) | 토큰당 평균 기준 |
|---|---|---|
| Qwen | 어텐션 L25 −0.0290 / ‖a·v‖ L33 −0.2634 | L25 −0.0022 / L33 −0.0190 |
| DeepSeek | 어텐션 L0 −0.0241 / ‖a·v‖ L26 −0.2878 | L0 −0.0008 / L26 −0.0093 |
| Llama | 어텐션 L12 −0.0104 / ‖a·v‖ L24 −0.0724 | L12 −0.0008 / L24 −0.0055 |
| StableCode | 어텐션 L15 −0.0278 / ‖a·v‖ L17 −0.2273 | L15 −0.0011 / **L15** −0.0080 |

**결론:** 부호(snake가 더 큼)와 봉우리 층은 **StableCode의 ‖a·v‖ 봉우리(L17→L15)를 빼면 그대로
유지**된다. 즉 `results.md`의 정성적 결론은 정규화에 견딘다. 다만 **절대 크기는 토큰 수에 부풀려져
있으므로 논문 수치로 쓸 때는 정규화 기준을 명시**해야 한다. 이건 결과의 오류가 아니라
**해석 시 반드시 붙여야 할 단서**다(결과 자체는 불변 원칙에 따라 그대로 둔다).

### 5.6 `token_detail` — 왜 통째로 저장하나

`code_camel`/`code_snake` 구간은 층마다 **토큰별** `a`, `av`, `v`를 전부 저장한다
(`model.py:175-196`). 결과가 불변이라 나중에 다시 못 뽑으므로, 사후 분석(밑줄 토큰만 따로 보기,
토큰당 정규화, 첫/마지막 토큰 비교)이 가능하도록 **곱게 남겨 두는** 설계다. §5.5의 재계산이
가능했던 것도 이 덕분이다.

### 5.7 관측의 원리적 한계 — 왜 step3가 반드시 필요한가

```
av = a × ‖v‖
```

관측값 `av`에서 `a`와 `‖v‖`의 기여를 **분리할 수 없다.** step2 결과가 보여준 것은

- `‖v‖`는 camel/snake가 거의 같다,
- `a`의 차이는 작다,
- 그런데 `av` 격차는 후반 층에서 크게 벌어진다.

이 패턴은 **"작은 어텐션 차이가 후반부에서 커진 ‖v‖에 곱해져 증폭된 것"** 으로도 똑같이 설명된다
(후반부 ‖v‖ 증가는 §1.4에서 말한 잔차 스트림 누적의 자연스러운 결과다).
따라서 step2가 답한 것은 **"어디(어느 층)"** 까지이고, **"무엇(축 A냐 축 B냐)"** 은
**바꿔보는 수밖에 없다.** 이것이 step3의 존재 이유다.

부수적으로 `‖a·v‖`는 `‖Σ_j a_j v_j‖`가 아니라 `Σ_j a_j‖v_j‖`이므로 **벡터 상쇄를 무시한
상한**이고, `W_O`를 통과하기 **전** 값이다. "잔차에 실제로 더해진 순 기여"와는 다르다는 점도
논문에 명시해야 한다.

### 5.8 step4를 위한 미리 알림 — 지침 구간의 등장 횟수 비대칭

같은 JSON에 지침 구간 3개가 함께 기록돼 있다(`instruction`, `instr_target_word`, `instr_viol_word`).
여기에 함정이 있다: 지침 3문장에서 **`camelCase`는 2번**(rule + closed), **`snake_case`는 1번**
(closed) 등장한다. `find_char_spans`는 **모든 등장**을 잡으므로 실측 토큰 수가
`instr_target_word:instr_viol_word = 4:2`(Qwen), `6:4`(DeepSeek)로 **구조적으로 2:1**이다.
→ step4에서 "지시어를 더 본다"를 주장하려면 **등장 횟수로 정규화**하거나 rule 문장만 잡아야 한다.
(치환 쪽 `_locate_target_tokens(span_kind="literal")`은 반대로 **첫 등장만** 쓴다 — 관측과
치환의 구간 정의가 다르다는 점을 인지하고 있어야 한다.)

## §6. 치환(개입) 방법론 상세 — step3·step5에서 돌아갈 코드

step2에서는 실행되지 않았지만 **코드는 이미 완성돼 있고**, 이 문서의 원래 질문
("KV 치환이라면 K와 V를 어디서 어떻게 뽑아 어떻게 덮는가")의 답이 여기 있다.

### 6.1 전체 그림 — 반사실 3상태와 되돌림 정도

텍스트는 손대지 않고 **내부만** 바꾼다. 세 상태를 잰다.

| 상태 | 무엇 | 코드 |
|---|---|---|
| **clean** (천장) | 문맥이 **전부 준수**인 프롬프트 | `comp_messages` |
| **base** (바닥) | 실제 조건(위반 섞임) 프롬프트 | `viol_messages` |
| **int** (개입) | base 텍스트 그대로, 위반 이름의 **층 L KV만** 공여값으로 덮음 | 캐시 편집 |

점수는 **준수 선호 점수**:

```
S  =  log P("removeDuplicates")  −  log P("remove_duplicates")        (intervention.py:109)
```

고정된 두 후보 이름의 로그확률 차이다. 양수면 준수 쪽을 선호. 생성을 돌리지 않고 **확률만**
비교하므로 잡음이 적고 값이 연속적이다(층 스윕에 적합).

**되돌림 정도(회복률)** — `intervention.py:87`:

```
recovery = (S_int − S_base) / (S_clean − S_base)
   0 = 개입해도 그대로     1 = 위반이 없었던 상태까지 완전 회복
   분모 ≈ 0 → None (= 판정 불가: 애초에 clean과 base가 구별 안 되는 조건)
```

### 6.2 K와 V를 **어디서** 뽑는가

```
공여(donor) 프롬프트  ──forward 1회──▶  past_key_values
                                          └ _cache_kv(cache, L) ─▶ (key, value)  각 [B, Hkv, seq, d]
                                                                          │
위반(base) 프롬프트   ──forward 1회──▶  past_key_values ──▶ 이 텐서의 특정 (L, position) 칸에 덮어씀
```

- 공여의 기본값은 **같은 이름의 준수판**(`donor='compliant'`) — 즉 `remove_duplicates` 자리에
  `removeDuplicates`의 KV를 넣는다. 이름의 정체성은 같고 **표기만 다른** 최소 대조다.
- **통제 조건**으로 `unrelated_camel`/`unrelated_snake`가 있다(`prompt.py:168` `unrelated_specs`).
  선행에 쓰이지 않은 다른 이름의 KV를 넣는 것 — "표기가 아니라 아무 값이나 넣어도 되는 것 아니냐"를
  배제한다.
- step5(지침 인과)는 공여가 **반대 지침 프롬프트**다(`runner.py:206`). "camelCase로 써라"의
  지시어 KV를 "snake_case로 써라"의 것으로 바꿔 **전이율**을 잰다.
- 비용 절감: 위반·준수·공여 프롬프트를 **각각 한 번씩만** forward하고(`model.py:264-276`),
  층 스윕 전체가 이 캐시들을 재사용한다.

### 6.3 **어디에** 덮는가 — 위치 정렬 3모드

위반 이름의 토큰 위치와 공여 이름의 토큰 위치를 짝지어야 한다(`intervention.py:13,58`).

| 모드 | 방식 | 장단점 |
|---|---|---|
| `all` | 첫↔첫, 둘째↔둘째 1:1 | 정확하지만 **토큰 수가 다르면 그 이름을 통째로 스킵** → §3.3 때문에 DeepSeek/StableCode에서 전부 스킵됨 |
| `last` | 마지막 토큰만 1:1 | 항상 짝지어지지만 이름 전체를 못 덮어 신호가 약함 |
| **`mean`** | **공여 토큰들의 KV를 평균 내 한 벡터로 만들고, 위반 이름의 모든 토큰 자리에 브로드캐스트** | **토크나이저 무관, 스킵 없음, 단어 전체를 덮음** → **통일 규격**(CLAUDE.md §3) |

mean-pool의 실제 코드(`model.py:334-353`):

```python
for vps, dps in ctx["groups"]:            # vps: 위반 이름의 토큰 위치들, dps: 공여의 토큰 위치들
    if edit_k:
        km = dk[:, :, dps, :].mean(dim=2)  # [B, Hkv, d]  ← 공여 위치들의 평균(KV group 유지)
        for vp in vps:
            bk[vp] = ek[:, :, vp, :].clone()   # 백업
            ek[:, :, vp, :] = km               # 덮어쓰기
    if edit_v:  # value도 동일
```

`dim=2`가 **위치(seq) 축**이고 `Hkv` 축은 그대로 유지된다는 점이 중요하다 —
**KV group 구조를 깨지 않고** 평균이 이뤄진다(§1.3 요구사항).

### 6.4 무엇을 덮는가 — kind 3종

`kind ∈ {key, value, key_value}` (`model.py:331-332`). 이 세 조건이 곧 §2의 축 분해다.

```
key       → a만 바뀐다        (축 A 경로)
value     → 실리는 내용만 바뀐다 (축 B 경로)
key_value → 둘 다             (상한)
```

**해석 규칙:** `value` 단독으로 회복률이 높고 `key` 단독은 낮으면 → **축 B 확정**(우리 가설).
반대면 Spotlight 쪽 손을 들어줘야 한다. `key_value`는 상한 기준선.

### 6.5 층 스윕 — 편집 → 측정 → **복구**

`model.py:318` `_score_layer_kind`의 구조:

```
work_cache = 위반 캐시의 복사본 (한 번만)
for L in 0..num_layers-1:
    for kind in (key, value, key_value):
        ① 층 L의 해당 위치를 공여값으로 덮음 (덮기 전 값은 백업)
        ② S_int 측정   ← 이때 S 내부에서 캐시를 다시 복제해 forward하므로 work_cache는 안 더러워진다
        ③ 백업으로 원상 복구   ← 다음 층이 깨끗한 위반 상태에서 시작
```

층마다 깊은 복사를 하지 않아 무료 티어에서도 전 층 스윕이 돌아간다.
`S_clean`·`S_base`는 층과 무관하므로 **한 번만** 계산한다.
산출물은 층별 회복률 곡선 3개(kind별)이고, `peak_layer()`(`intervention.py:114`)가
**"표기 결정이 어느 처리 단계에서 굳는가"** 의 답인 봉우리 층을 뽑는다.

### 6.6 이 개입이 **정확히 무엇을** 반사실로 만드는가 (범위 한정)

논문에 반드시 써야 할 정밀한 진술이다.

프롬프트를 **한 번 forward해 캐시를 만든 뒤** 층 L의 칸을 고치므로:

- ✅ 바뀌는 것: **채점 시점의 forward에서, 층 L이 그 위치들로부터 읽어 들이는 K/V.**
- ❌ 바뀌지 않는 것: **프롬프트 토큰 자신의 층 L+1 이상 표현.** 이미 계산된 값이라 재계산되지 않는다.

즉 우리 개입은 "문맥 토큰을 다른 토큰으로 바꿨을 때의 전체 파급"이 아니라,
**"이름을 쓰려는 그 위치가 층 L에서 문맥으로부터 읽는 내용"만 국소적으로** 바꾼다.
이건 결함이 아니라 **우리 RQ에 정확히 맞춘 설계**다 — 우리가 묻는 것이 정확히
"생성 시점에 문맥에서 무엇을 읽어 오는가"이기 때문이다. 다만
**"이 층의 K/V 읽기 경로"** 라는 한정을 빼고 "층 L을 바꿨다"고 쓰면 과장이 된다.

### 6.7 알아야 할 주의사항

1. **RoPE 위상 (K 치환에만 해당).** §1.5대로 캐시의 key에는 **원래 위치의 회전이 이미 박혀 있다.**
   공여 위치 `dp`의 key를 위반 위치 `vp`에 넣으면 `dp`의 위상이 따라 들어온다. `vp ≠ dp`면
   (토큰 수가 달라 위치가 밀리면 흔히 발생) 순수한 "내용만 다른 key"가 아니게 된다.
   **mean-pool은 여러 위치의 key를 평균 내므로 위상이 섞인다** — Value 치환보다 Key 치환이
   해석상 더 조심스럽다. 실무적 함의: **`value` 회복률이 높게 나오는 것은 강한 증거이고,
   `key` 회복률이 낮게 나오는 것은 "축 A가 무력하다"의 증거로 쓰기 전에 이 교란을 언급해야 한다.**
   (통제: 어텐션을 직접 조작하는 `ATTENTION_AMPLIFY` 조건이 이 교란 없이 축 A를 검증하는 경로다.)
2. **후보 길이 편향.** `S`는 길이 정규화 없는 로그확률 합이라 토큰 수가 다른 두 후보 사이에
   상수 편향이 있다. 다만 세 상태(clean/base/int)에서 **같은 후보 쌍**을 쓰므로 회복률(차이의 비)에서는
   대체로 상쇄된다.
3. **캐시 복제.** 채점 forward는 캐시를 늘리므로(`logp_candidate`) 매번 `_clone_cache`로 복제한 뒤
   돌린다(`model.py:293`). 이걸 빼면 층 스윕에서 캐시가 오염된다.
4. **`intervene_generate`는 아직 mean 모드를 못 받는다.** `align_name_tokens(mode=token_unit)`만
   호출하므로(`model.py:603`) `token_unit='mean'`을 주면 `ValueError`가 난다. 생성 기반 재확인을
   통일 규격(mean-pool)으로 돌리려면 **이 함수에 mean 경로를 먼저 추가해야 한다** — step3 착수 전
   확인할 항목.
5. **`skipped_names`를 반드시 보고한다.** 정렬 실패로 제외된 이름이 있으면 그 조건의 치환 강도가
   달라진다. `n_substituted_tokens`(실제로 덮은 자리 수)와 함께 결과 JSON에 남는다.

## §7. 방법론 지도 — 우리 것이 어디에 서 있나 (논문 용어)

| 방법 | 무엇을 하나 | 우리와의 관계 |
|---|---|---|
| **Probing** | 표현에서 정보를 읽어 낼 수 있는지 분류기로 확인 | step2 관측이 여기에 가깝다(다만 분류기 없이 직접 지표) |
| **Activation patching / Causal tracing** | 한 실행의 내부 활성값을 다른 실행 값으로 바꿔 인과 확인 | **우리 KV 치환이 이 계열이다.** 다만 개입 지점을 **어텐션의 K/V 입력**으로 한정 |
| **Path patching** | 특정 경로(어느 head → 어느 head)만 바꿈 | 우리는 층 단위. head 단위 분해는 확장 여지 |
| **Attention knockout** | 특정 어텐션 연결을 0으로 끊음 | `ATTENTION_AMPLIFY`(배율<1)가 비슷한 역할 |
| **Ablation (zero / mean)** | 표현을 0 또는 평균으로 지움 | 우리 mean-pool은 "지우기"가 아니라 **반대편 값으로 갈아끼우기**(더 강한 대조) |
| **Logit lens / DLA** | 중간 층 표현을 바로 어휘로 투영해 읽음 | 미사용. 층별 "언제 결정이 굳는가"를 보는 대안 |
| **Spotlight / 어텐션 재가중** | 지침 구간 어텐션을 키워 준수율을 올리려는 접근 | **반박 대상.** 축 A 손잡이만 건드리므로, 축 B가 원인이면 실패해야 한다 |

**우리 방법의 한 줄 정의:**
> 표기만 다른 최소쌍 문맥에서, 생성 시점 어텐션의 **Key 경로와 Value 경로를 층별로 따로 반사실
> 치환**해, 표기 준수 행동을 되돌리는 것이 **"얼마나 보나"인지 "무엇을 싣나"인지**를 가른다.

**한계 (논문 Limitations에 들어갈 것)**

1. **관측은 축을 못 가른다** — `av = a × ‖v‖`(§5.7). step2 단독으로는 "어디(층)"까지만.
2. **합 기반 지표의 토큰 수 편향** — DeepSeek/StableCode에서 snake 구간이 1.4배 길다(§5.5).
   정성 결론은 정규화에 견디지만 절대 수치는 기준 명시 필요.
3. **`‖a·v‖`는 상한이자 W_O 이전 값** — 순 기여(벡터 상쇄 후, 출력 사영 후)와 다르다.
4. **개입의 범위 한정** — 프롬프트 토큰의 상위층 표현은 재계산되지 않는다(§6.6).
5. **K 치환의 RoPE 교란** — 위치가 다르면 위상이 섞인다(§6.7-1).
6. **합성 문맥** — 모든 함수가 `return value`인 극단적 통제. 실제 코드 일반화는 `Source.REPO`
   조건(`data/repo_files/`)으로 별도 확인해야 한다.
7. **단일 seed** — seed 42만 사용. 배치 순서 변주에 대한 분산은 42개 블록 간 변동으로 대신한다.
8. **모델 4개 · 3~7B 규모** — 더 큰 모델로의 외삽은 미검증.

### 부록 B. 자주 헷갈리는 용어 짝

| 헷갈리는 것 | 구분 |
|---|---|
| 어텐션의 **Key/Value** ↔ FFN의 "key-value 메모리" | 완전히 다른 것. 우리가 치환하는 건 **어텐션 쪽** |
| **`v_norm`(축 B 크기)** ↔ **`v_cosine`(축 B 방향)** | 크기가 같아도 방향은 다를 수 있다. 그래서 코사인 관측 경로(`mode='vcosine'`)가 따로 있다 |
| **준수율**(생성 결과) ↔ **준수 선호 점수 S**(확률 차) | 전자는 step1, 후자는 개입 실험. S는 생성 없이 재는 연속값 |
| **회복률/되돌림 정도** ↔ **전이율** | 같은 공식. 코드 대상(step3)은 "회복", 지침 대상(step5)은 "반대 지침으로 넘어감" 이라 이름만 다르게 부른다 |
| **`group_size`**(GQA) ↔ **`pool_block`**(데이터 묶음) | 전자는 head 구조, 후자는 이름 12개 묶음 번호 |
