# 연구 계획 — 통일 재실험

흩어진 설정(데이터 80/504 혼용, 모델 제각각, 치환 방법 3종)을 **하나의 규격**으로 통일해
처음부터 다시 실험한다. 이 문서는 전체 지도다.

---

## 0. 무엇을 밝히려는가 (연구 질문)

**큰 질문:** 코드를 만드는 언어모델은 "함수 이름을 camelCase로 써" 같은 **표기 규약 지침을 왜 자주 어기는가?**

**우리 주장(가설):** 지침을 "덜 봐서"가 아니다. 지침은 충분히 읽힌다. 문제도, 바로잡는 손잡이도
모두 **모델이 어느 토큰을 얼마나 보느냐(어텐션)가 아니라, 그 토큰이 실어 나르는 내용(Value)**에,
그리고 **후반부 특정 층**에 있다. 그래서 어텐션을 키우는 기존 접근(Spotlight)은 잘못된 곳을 건드린다.

이 큰 질문을 세 개로 쪼갠다.

| | 질문 | 한 줄 |
|---|---|---|
| **RQ1** | 문맥에 규약을 어긴 코드가 섞이면 새 코드의 준수율이 떨어지는가? | 실패가 실제로 있나 |
| **RQ2** | 그 방해 신호는 **내용인가 형태인가**, 모델 속 **어디(어텐션/Value)**·**어느 층**에 있나? | 코드 신호의 정체 |
| **RQ3** | **지침**의 영향력도 코드와 같은 통로(Value)인가, 아니면 어텐션인가? | 지침 신호의 정체 |

**흐름:** RQ1(실패 확인) → RQ2(코드 신호 = 내용/Value/후반층) → RQ3(지침도 같은가) → 방법론.

## 1. 고정 설정 (모든 실험 공통)

### 모델 — 4개

| 이름 | 종류 | 역할 |
|---|---|---|
| Qwen2.5-Coder-3B-Instruct | 코드 전용 | 기준(주 분석) |
| deepseek-coder-6.7b-instruct | 코드 전용 | 다양성 |
| Llama-3.2-3B-Instruct (unsloth 미러) | 범용 | 다양성 (코드전용 vs 범용 대조) |
| stable-code-instruct-3b | 코드 전용 | 다양성 |

> unsloth 미러를 쓰는 이유: 원본 Llama는 로그인·승인이 필요한데 unsloth판은 같은 모델이면서 그게 없다.

### 데이터 — 함수 이름 504개

- **동사 50개 × 명사 50개** 조합에서 겹치지 않게 골라 **504개** 이름 (`parseHeader`/`parse_header` …)
- 함수 속 내용은 전부 동일(값 그대로 반환). **오직 이름 표기만** 다르게 함 — 다른 게 안 섞이게 하는 통제
- 504개를 **12개씩 42묶음**으로 나눠, 묶음을 바꿔가며 504개를 전부 사용

### 무작위 고정값(seed) — 42

- seed는 "어느 이름을 쓰는가"는 안 바꾼다(그건 묶음이 정함). **배치 순서만** 정한다.
- 전 실험 **42로 통일**해 재현 라벨을 맞춘다.

### 내부 값을 바꾸는 방법 — "평균 덮어쓰기" 하나로 통일

한 단어의 속(내부 표현)을 반대쪽 단어의 속으로 바꿔치기할 때:
- 반대쪽 단어의 조각들을 **평균 내 하나로 만들고**, 그걸 바꿀 단어의 **모든 조각 자리에 덮어쓴다.**
- 이렇게 하면 모델마다 단어를 몇 조각으로 쪼개든 상관없이 되고(건너뛰는 일 없음), 단어 전체를 바꾼다.
- 코드 이름이든 지침 단어든 **똑같은 방법**을 쓴다.

### 무엇을 재는가 (직관 설명)

| 측정값 | 쉬운 뜻 |
|---|---|
| **준수율** | 모델이 새 함수 이름을 규약(camel)대로 쓴 비율 |
| **어텐션** | 모델이 특정 부분(코드 이름 / 지침 단어)을 얼마나 보는가 |
| **영향력** | 지침이나 문맥을 바꿨을 때 모델 행동이 실제로 바뀌는 정도. 크면 영향 있음, 0에 가까우면 그 모델은 그 신호를 무시. (영향력이 0이면 "속을 바꾸면 어떻게 되나"를 물을 대상 자체가 없으므로 그 조건은 제외한다) |
| **되돌림 정도** | 모델 속을 목표 쪽으로 바꿨을 때 행동이 목표로 얼마나 돌아오나. 0 = 그대로, 1 = 완전히 넘어감 |
| **어느 층** | 위 변화가 몇 번째 처리 단계(층)에서 일어나는가 |

## 2. 실험 순서 — GPU 적게 쓰는 것부터

가벼운(빠른) 실험으로 먼저 파이프라인을 검증하고, 무거운 것을 마지막에 돌린다.

| 순서 | 스텝 | RQ | GPU 부하 | 이유 |
|---|---|---|---|---|
| 1 | step2 (코드 관측) | RQ2 | **가벼움** | 조건당 계산 1번 |
| 2 | step4 (지침 관측) | RQ3 | **가벼움** | 조건당 계산 1번 |
| 3 | step1 (준수율 절벽) | RQ1 | 중간 | 짧은 생성 몇 번 |
| 4 | step3 (코드 인과) | RQ2 | **무거움** | 전 층 훑기 |
| 5 | step5 (지침 인과) | RQ3 | **무거움** | 전 층 훑기 |

> 논문에 싣는 논리 순서는 1→5(step1→step5)이지만, **돌리는 순서는 위 표대로** 가벼운 것부터.

## 3. 스텝별 상세 (브랜치별)

각 스텝 = 브랜치 1개 = 실험 1개.

### step1 — 준수율 절벽 (브랜치 `step1/cliff`)

| | |
|---|---|
| RQ | RQ1 |
| 궁금한 것 | 문맥에 규약 어긴 이름이 많아질수록 새 코드의 준수율이 떨어지는가, 어디서 급락하는가 |
| 바꾸는 것 | 문맥 12개 함수 중 규약을 지킨 개수 (0개 ~ 12개), 이름 묶음, 모델 |
| 재는 것 | 모델이 새로 쓴 함수 이름의 준수율 |
| 결과 해석 | 지킨 개수가 줄수록 준수율이 떨어지고 특정 지점에서 급락 → "방해 신호가 있다"(RQ2로 넘어감) |

### step2 — 코드 신호 관측 (브랜치 `step2/code-observe`)

| | |
|---|---|
| RQ | RQ2 (관측) |
| 궁금한 것 | 문맥의 camel 이름과 snake 이름이 모델 속에서 **어디에 다르게 드러나는가** |
| 바꾸는 것 | 이름 묶음, 모델 (문맥은 camel 6 / snake 6 균형) |
| 재는 것 | 두 그룹(camel/snake)의 어텐션과 내부 표현 크기 |
| 결과 해석 | 차이가 어텐션 쪽인가 내용 쪽인가의 첫 단서 (확정은 step3 인과) |
| **자리 통제(추가)** | 표기 배치를 뒤집은 **시드 67**(시드 42의 정확한 여집합)로 166조건을 더 돌린다. 두 시드를 짝지어 평균하면 자리 효과가 소거된다 |
| **결과(확정)** | **격차는 자리 효과였다.** Qwen·Llama는 배치를 뒤집자 부호까지 뒤집혀 두 시드 평균이 0이다. → **이 스텝의 주요 결론을 철회했고, RQ2의 답은 step3가 전담한다** |

### step3 — 코드 신호 인과 (브랜치 `step3/code-cause`)

| | |
|---|---|
| RQ | RQ2 (인과) |
| 궁금한 것 | 코드의 표기 신호가 **어텐션(Key)인가 내용(Value)인가, 어느 층**인가 |
| 바꾸는 것 | 문맥의 위반 이름 속을 규약형으로 바꿔치기 — 어텐션만 / 내용만 / 둘 다, 전 층 각각 |
| 재는 것 | 되돌림 정도(층별), + 무관한 규약형 이름으로 바꿔도 같은지(형태 통제) |
| 결과 해석 | 내용(Value)을 바꿔야 되돌아오고 어텐션은 안 되면 → **코드 신호 = 내용, 후반 단일 층** |

### step4 — 지침 관측 (브랜치 `step4/instr-observe`)

| | |
|---|---|
| RQ | RQ3 (관측) |
| 궁금한 것 | 모델이 지침 속 "camelCase" 지시어 단어를 **보기는 하는가**, 어느 층에서 |
| 바꾸는 것 | 이름 묶음, 모델 |
| 재는 것 | 지침의 지시어 단어에 대한 어텐션 (코드 이름 어텐션과 비교) |
| 결과 해석 | 지시어를 본다면 "안 봐서 못 지킨다"는 설명은 틀림 → 문제는 내용/층 (step5 인과로 확인) |

### step5 — 지침 인과 (브랜치 `step5/instr-cause`)

| | |
|---|---|
| RQ | RQ3 (인과) |
| 궁금한 것 | 지침을 바꾸면 행동이 바뀌는가, 바뀐다면 **어텐션인가 내용인가** |
| 바꾸는 것 | 지침 지시어 단어의 속을 반대 지침 것으로 바꿔치기 — 어텐션만 / 내용만 / 둘 다, 전 층 |
| 재는 것 | 되돌림 정도 + 영향력(지침이 그 모델에서 먹히는지 먼저 확인) |
| 결과 해석 | 내용을 바꿔야 넘어가면 → **지침도 코드와 같은 내용(Value) 통로** → 기존 접근(어텐션 키우기) 반박 |

## 4. 노트북 만드는 규칙 (전 스텝 공통)

1. **모델 하나씩.** 노트북 맨 위에서 모델 1개를 고른다. 한 번에 그 모델만 돈다. → 런타임이 끊겨도 그 모델만 영향.
2. **완료된 건 다시 안 함(재개).** 조건마다 결과를 파일로 저장하고, 이미 있으면 건너뛴다. 끊긴 뒤 다시 돌리면 남은 것만 이어서 한다.
3. **중간 결과 표시.** 진행 상황과 지금까지의 값을 중간중간 화면에 찍는다.
4. **쉬운 말.** 화면 출력·표에 줄임말·전문용어 쓰지 않는다 (예: "바꾼 조각 수", "영향력", "되돌림 정도").
5. **마지막에 zip 다운로드.** 결과 폴더를 zip으로 묶어 내려받는 셀을 맨 끝에 둔다.
6. **결과 저장 위치:** `results/<스텝 폴더>/` (조건이 파일명에 드러나게).

## 5. 브랜치 한눈 정리

| 브랜치 | 스텝 | RQ | 한 줄 | GPU |
|---|---|---|---|---|
| `step1/cliff` | 절벽 | RQ1 | 위반 개수↑ → 준수율 | 중간 |
| `step2/code-observe` | 코드 관측 | RQ2 | 코드 어텐션·내부표현 | 가벼움 |
| `step3/code-cause` | 코드 인과 | RQ2 | 코드 속 바꿔 되돌림 측정 | 무거움 |
| `step4/instr-observe` | 지침 관측 | RQ3 | 지시어 어텐션 | 가벼움 |
| `step5/instr-cause` | 지침 인과 | RQ3 | 지침 속 바꿔 되돌림 측정 | 무거움 |

기존 브랜치(pool-500·model-diversity 등)와 그 결과는 그대로 보존한다(참고용). 새 실험은 위 5개로만.
