# 코드와 방법론 — 하네스 구조 · 트랜스포머 개념 · 측정 설계

이 연구가 **무엇을 어떻게 재는지**를 코드와 개념 양쪽에서 정리한다. 논문 방법론 절의 원본이자,
새로 합류한 사람이 `src/harness`를 열기 전에 읽는 문서다.

읽는 순서: **1부(개념)** → **2부(지표)** → **3부(방법론)** → **4부(코드 구조)** → **5부(실행 추적)**.
급하면 4부·5부만 읽어도 코드는 돌릴 수 있지만, 1~3부 없이는 결과를 해석할 수 없다.

---

# 1부. 트랜스포머 — 우리가 건드리는 부분

우리가 쓰는 모델은 전부 **디코더 전용 인과 언어모델**(decoder-only causal LM)이다.
앞의 토큰들만 보고 다음 토큰의 확률을 낸다. 여기서는 우리 실험이 실제로 손을 대는 부품만
정확히 짚는다. 안 쓰는 부품도 "왜 안 쓰는가"가 논문의 주장이 되므로 같이 정리한다.

## 1.1 토큰 · 임베딩 · 잔차 스트림

텍스트는 먼저 **토큰**으로 쪼개진다. 중요한 건 토큰 경계가 우리 실험 대상과 정확히
일치하지 않는다는 점이다. 예를 들어 같은 함수를 뜻하는 두 이름이

- `format_matrix` → `format`, `_`, `matrix` (3토큰)
- `formatMatrix` → `format`, `Matrix` (2토큰)

처럼 **다른 개수**로 쪼개진다. 표기 규약 연구가 토크나이저와 정면으로 부딪히는 지점이고,
3부의 정렬(alignment) 문제가 여기서 나온다.

각 토큰은 벡터가 되어 층을 통과한다. 이 벡터가 층을 거치며 갱신되는 통로를 **잔차 스트림
(residual stream)** 이라 부른다. 층은 잔차를 **덮어쓰지 않고 더한다**:

```
h ← h + Attention(h)
h ← h + FFN(h)
```

그래서 잔차 스트림은 "여러 부품이 각자 기여분을 적어 넣는 공용 게시판"에 가깝다.
층이 깊어질수록 최종 출력에 가까운 정보가 쌓인다.

## 1.2 층 하나의 구조

층 하나는 두 블록이다.

| 블록 | 하는 일 | 정보 이동 방향 |
|---|---|---|
| **Attention** | 다른 **위치**(토큰)의 정보를 현재 위치로 끌어온다 | 위치 ↔ 위치 (가로) |
| **FFN (MLP)** | 현재 위치의 벡터 하나를 비선형 변환한다 | 위치 내부 (세로) |

**"앞선 코드의 이름이 지금 생성될 이름에 영향을 준다"는 우리 현상은 정의상 위치를 건너
뛰는 정보 이동이다. 그 통로는 Attention뿐이다.** FFN은 위치를 넘나들지 못한다.
이것이 우리가 개입 지점을 Attention으로 좁히는 1차 근거다.

## 1.3 Q · K · V — 정확히 무엇인가

Attention 블록에서 각 토큰의 잔차 벡터 `h`는 세 개의 벡터로 투영된다.

```
q = h · W_Q      (Query)
k = h · W_K      (Key)
v = h · W_V      (Value)
```

그리고 위치 `i`의 출력은:

```
attn_out_i = Σ_j  softmax_j( q_i · k_j / √d ) · v_j
             └────────── a_ij ──────────┘
```

마지막에 `W_O`로 한 번 더 투영되어 잔차에 더해진다.

| | 무엇인가 | 비유 | 수식에서의 역할 |
|---|---|---|---|
| **Q** | 지금 위치가 **무엇을 찾는지** | 검색어 | `a`를 만드는 데 참여 |
| **K** | 각 토큰이 **자신을 어떻게 광고하는지** | 색인 카드 | `a`를 만드는 데 참여 → **라우팅** |
| **V** | 각 토큰이 **실제로 실어 나르는 내용** | 색인이 가리키는 본문 | `a`로 가중합됨 → **운반물** |

핵심은 **역할 분리**다. `a`(어텐션 가중치)는 **얼마나 볼지**만 정하고, 실제로 잔차에 더해지는
정보는 `v`다. **어텐션을 아무리 키워도 `v`가 비어 있으면 아무 일도 안 일어난다.**

> **이 연구의 주장이 바로 여기 걸린다.** 기존 접근(Spotlight 계열)은 "모델이 지침을 덜 본다"
> 고 보고 **`a`를 키우는** 처방을 낸다. 우리는 문제도 손잡이도 **`v`(내용)** 에 있다고 본다.
> K와 V를 따로 치환해 어느 쪽이 행동을 바꾸는지 보는 것이 3부의 설계다.

## 1.4 멀티헤드와 GQA — 왜 신경 써야 하나

Attention은 한 벌이 아니라 **head** 여러 개가 병렬로 돈다. head마다 `W_Q/W_K/W_V`가 따로다.

최신 모델 대부분은 **GQA(Grouped Query Attention)** 를 쓴다. query head는 많은데
**K/V head는 적고, 여러 query head가 하나의 K/V를 공유**한다.

```
group_size = num_attention_heads / num_key_value_heads
query head h  →  KV head (h // group_size)
```

예: Qwen2.5-Coder-3B는 `num_attention_heads=16`, `num_key_value_heads=2`, `head_dim=128`
→ **group_size = 8**. query head 8개가 KV head 하나를 공유한다.
(이 값은 이전 실험 기록 기준이다. **모델마다 group 구성이 다르니 매번 `gqa_info()`로
확인한다** — CLAUDE.md §7.)

**이게 왜 중요한가.** K/V를 치환할 때 "query head 하나 몫만" 바꾸는 건 불가능하다.
KV head 하나를 건드리면 그것을 공유하는 **query head 8개 전부**가 영향을 받는다.
치환은 반드시 **KV group 단위**여야 한다(CLAUDE.md §3). 우리 코드는 확장된 텐서가 아니라
**KV 캐시 원본**(`[B, n_kv, seq, d]`)을 직접 편집해서 이 조건을 구조적으로 만족시킨다 —
캐시에는 애초에 `n_kv`개만 들어 있으므로 group을 쪼갤 방법 자체가 없다.

관측 쪽에서는 반대로 **매핑**이 필요하다. `a`는 query head별(`Hq`종), `v`는 KV head별
(`Hkv`종)이라 곱하려면 인덱스를 맞춰야 한다 (`attention_probe.py`의 "방법 A"):

```
av[h, j] = a[h, j] · ‖v[h // group_size, j]‖
```

## 1.5 KV 캐시 — 우리 개입의 실제 지점

생성할 때 매 토큰마다 앞 전체를 다시 계산하면 낭비다. 그래서 각 층·각 위치의 `k`와 `v`를
한 번 계산해 **캐시**(`past_key_values`)에 저장하고 재사용한다. 모양은 층마다:

```
[batch, num_key_value_heads, sequence_length, head_dim]
```

**우리는 이 캐시를 직접 편집한다.** 이게 방법론의 핵심이다.

- 텍스트는 **한 글자도 바꾸지 않는다.** 모델이 읽는 프롬프트는 그대로다.
- 특정 **층 L**, 특정 **위치**(위반 이름 토큰들)의 `k` 또는 `v`만 다른 값으로 덮는다.
- 그 상태로 다음 토큰을 예측시켜 **행동이 바뀌는지** 본다.

**이 개입이 왜 깨끗한가 — 층 국소성.** 층 L의 캐시를 고쳐도 층 L+1의 캐시는 안 바뀐다.
L+1의 K/V는 프리필(prefill) 때 이미 계산돼 저장돼 있기 때문이다. 그래서 편집의 효과는
**"새로 생성되는 위치가 층 L에서 무엇을 읽는가"** 딱 하나로 한정된다. 층·경로가 뒤섞이지
않으므로 "어느 층, 어느 경로"라는 질문에 답할 수 있다.

## 1.6 우리가 **안** 건드리는 것들 — 그리고 그게 왜 주장인가

| 부품 | 우리 처리 | 이유 |
|---|---|---|
| **FFN (MLP)** | 개입 안 함 | 위치 간 정보를 못 옮긴다(§1.2). 문맥 전파의 통로가 아니다 |
| **W_O** (출력 투영) | 개입 안 함 | `v` 다음 단계의 고정 선형 변환. `v`를 바꾸면 자동으로 반영된다 |
| **Q** | 개입 안 함 | 개입 대상은 **참조되는 쪽**(선행 코드/지침). Q는 참조하는 쪽이라 조작 대상이 아니다 |
| **어텐션 증폭** | 스키마에만 존재, **미구현** | `InterventionKind.ATTENTION_AMPLIFY`가 `conditions.py`에 정의만 돼 있고 `model.py`에 실행 코드가 없다. Spotlight 직접 반박 arm이라 **구현이 남아 있다** |

> **미구현 사항 명시.** 어텐션 증폭 개입은 아직 코드가 없다. "어텐션을 키워도 안 바뀐다"를
> 직접 보이려면 이 arm이 필요하다. 현재는 **Key 치환이 무반응**이라는 간접 증거로 대신하고
> 있다. 논문에 쓰려면 구현하거나, 주장을 Key/Value 분해 범위로 좁혀야 한다.

## 1.7 층의 깊이 — "후반"이 무슨 뜻인가

층 인덱스는 절대값이라 모델 간 비교가 안 된다(Qwen 36층 vs 다른 모델 24층). 그래서
**상대 위치**를 쓴다 (`ModelHandle.relative_layer`):

```
상대 위치 = layer / (num_layers - 1)
```

L25 / 36층 → 0.714 = **후반**. 통념상 초반 층은 표층 형태·구문, 중반은 의미·관계, 후반은
출력 결정에 가까운 정보를 다룬다. **표기 규약 결정이 후반에서 굳는다**는 것이 우리의
관측이고, 이는 "표기는 의미가 아니라 출력 직전의 형태 선택"이라는 해석과 맞물린다.

관련 개념으로 **로짓 렌즈(logit lens)** 가 있다. 중간 층의 잔차를 그대로 출력 임베딩에
통과시켜 "이 층에서 이미 어떤 토큰을 밀고 있는가"를 보는 기법이다. 아직 안 쓰지만,
"어느 층에서 표기가 확정되는가"를 직접 보여줄 수 있어 후속 스텝의 유력 후보다.

# 2부. 지표 — 정의와 읽는 법

`metrics.py`가 자리를 고정하고, 각 스텝이 해당하는 것만 채운다.

## 2.1 준수율 (compliance rate) — 생성 실험

모델이 실제로 쓴 함수 이름이 지침 표기와 일치하는 비율. **행동 지표**다.

```
생성 텍스트 → first_function_name() → classify_name() → camel / snake / other
준수 = (분류 결과 == 지침 목표 표기)
```

- 판정은 정규식이다(`naming.py`). camel = `^[a-z][a-z0-9]*([A-Z][a-z0-9]*)+$`,
  snake = `^[a-z][a-z0-9]*(_[a-z0-9]+)+$`. 둘 다 아니면 `other`.
- **한 단어 이름은 판정 불가**다(`clamp`는 camel이자 snake). 그래서 모든 과제 이름은
  **두 단어 이상**으로 강제했다. 실제로 초기 실험에서 모델이 `clamp`로 축약해 `other`가
  쏟아졌고, 그 결과 과제를 `removeDuplicates` 계열로 교체했다(`tasks.py` 주석).

## 2.2 준수 선호 점수 S — 개입 실험

생성은 이산적(camel이냐 snake냐)이라 개입의 **크기**를 못 잰다. 그래서 **연속 점수**를 쓴다.

```
S = logP(준수 후보 이름) − logP(위반 후보 이름)
```

두 후보는 **같은 과제의 두 표기판**으로 고정한다 (`removeDuplicates` vs `remove_duplicates`).
각 후보의 로그확률은 토큰별 로그확률의 합이다.

- **S > 0** = 준수 쪽을 선호
- **S < 0** = 위반 쪽을 선호
- 부호가 뒤집히면 그리디 생성 결과도 뒤집힌다

## 2.3 되돌림 정도 (recovery rate) — 인과의 크기

세 상태의 S를 비교한다.

| 상태 | 뜻 |
|---|---|
| **S_깨끗** (`S_clean`) | 문맥에 위반이 하나도 없을 때 — **천장** |
| **S_위반** (`S_base`) | 실제 조건(위반 포함), 개입 없음 — **바닥** |
| **S_개입** (`S_int`) | 텍스트는 위반 그대로, 내부 표현만 치환 |

```
되돌림 정도 = (S_개입 − S_위반) / (S_깨끗 − S_위반)
```

- **1.0** = 위반이 아예 없던 상태까지 완전 복구
- **0.0** = 개입이 아무 효과 없음
- **분모가 0에 가까우면 `None`** — 천장과 바닥이 구별되지 않는다는 뜻이라 **"판정 불가"** 로
  분리한다(CLAUDE.md §4). 지침이나 문맥이 애초에 안 먹히는 모델이 여기 해당한다.
  **이 조건을 0으로 세면 안 된다.** 효과 없음이 아니라 측정 불능이다.

## 2.4 관측 지표 — 축 A와 축 B

| 지표 | 계산 | 무슨 축 | 읽는 법 |
|---|---|---|---|
| **어텐션 가중치** | 구간 토큰의 `a` **합** (query head 평균) | 축 A (**얼마나 보나**) | head 행은 전체 위치에 대해 1로 합해지므로, 구간 합 = 그 구간이 가져간 어텐션 질량(0~1) |
| **‖v‖** | 구간 토큰 value 노름의 **평균** | 축 B **크기** | 그 토큰이 실어 나르는 표현의 크기 |
| **‖av‖** | `a·‖v‖`의 구간 **합** | 축 A × B | 어텐션과 내용을 곱한 기여량 |
| **v 코사인** | 같은 이름 camel판 v ↔ snake판 v | 축 B **방향** | 1=같은 정보, 0=직교(다른 정보) |

**‖av‖가 정확한 이유.** `a`는 스칼라이고 0 이상이므로 `‖a·v‖ = a·‖v‖`가 **근사가 아니라
항등식**이다. 그래서 head별로 곱한 뒤 평균내도 오차가 없다.

> **‖av‖ 해석 시 주의(논문에 반드시 반영).** 우리가 재는 `Σ_j a_j‖v_j‖`는 실제 잔차 기여
> 벡터의 노름 `‖Σ_j a_j v_j‖`와 **다르다**. 삼각부등식으로 전자가 후자 이상이다(방향이
> 서로 상쇄되면 실제 기여는 더 작다). 또 `W_O` 투영 전 값이다. 따라서 ‖av‖는
> **"그 구간이 쓸 수 있었던 기여 예산"** 으로 읽어야지 "실제 기여량"으로 단정하면 안 된다.
> 구간 간 **상대 비교**에는 문제없지만 절대 해석은 금물이다.

**‖v‖는 크기, 코사인은 방향.** 둘 다 필요한 이유: 이전 실험에서 camel→snake의 ‖v‖ 배율이
1.002로 **크기는 사실상 불변**이었다. 크기로는 아무 차이도 못 잡는다. 그래서 방향을 보는
코사인이 필요했고, 특정 층에서 국소적으로 떨어지는 것이 확인됐다. **표기 신호는 v 안의
미세한 방향 성분**이라는 결론이 여기서 나온다.

# 3부. 방법론 — 관측과 인과

두 갈래다. **관측**(observe)은 "무엇이 무엇과 같이 나타나나"를 보고, **인과**(intervene)는
"바꾸면 행동이 바뀌나"를 본다. 관측만으로는 상관을 인과로 못 읽는다.

## 3.1 관측 — 생성 시점 query 한 행 뜯어보기

`ModelHandle.observe_generation_query`. 순서대로:

**① 측정 시점을 이름 생성 순간에 고정한다 (teacher forcing).**

```python
prompt_text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
prompt_text = prompt_text + "def "     # ← forced_prefix
```

`def `를 강제로 이어 붙이면 **다음에 예측될 토큰이 반드시 함수 이름**이 된다. 모델이
설명 문장을 쓰다가 어디선가 이름을 낼지 기다릴 필요가 없고, 모든 조건에서 **같은 순간**을
잰다. 조건 간 비교 가능성이 여기서 확보된다.

**② 문자 위치 → 토큰 인덱스 매핑.**

```python
enc = tok(prompt_text, return_offsets_mapping=True, add_special_tokens=False)
```

`offset_mapping`으로 각 토큰이 원문의 어느 글자 범위인지 안다. 문자열로 구간을 찾고
(`find_char_spans`) 겹치는 토큰을 모은다(`locate_token_spans`). 이름은 `def <이름>(`로
찾은 뒤 `+4`, `-1`로 **이름 부분만** 잘라낸다 — `def`와 `(`가 섞이면 안 되므로.

> **왜 `apply_chat_template(tokenize=False)` 후 다시 토큰화하나.** 템플릿이 토큰화까지 하면
> offset이 안 나온다. 문자열을 먼저 만들고 그 문자열을 토큰화해야 **모델 입력과 offset이
> 정확히 같은 문자열에서 나온다.** 어긋나면 구간이 통째로 밀린다.

**③ 한 번의 forward로 어텐션과 KV를 동시에 확보.**

```python
out = self.model(**enc, output_attentions=True, use_cache=True)
attentions = out.attentions                  # tuple[L], 각 [1, Hq, seq, seq]
values = _value_cache(out.past_key_values)   # list[L], 각 [1, Hkv, seq, d]
```

- `output_attentions=True`는 **eager 어텐션에서만** 가중치를 돌려준다. SDPA/FlashAttention은
  `None`을 준다. 그래서 관측용 로드는 `attn_implementation='eager'`가 필수다.
- 어텐션 행렬은 `seq × seq`라 메모리를 많이 먹는다. 합성 프롬프트(수백 토큰)는 T4에서
  감당되지만 긴 실코드는 축약 경로가 필요하다.

**④ 마지막 query 행만 꺼내 구간별로 집계.**

```python
attn_last = attentions[layer][0, :, -1, :]     # [Hq, seq] — 마지막 위치가 각 위치를 본 정도
vnorm_kv  = values[layer][0].norm(dim=-1)      # [Hkv, seq]
```

`-1`은 **지금 이름을 생성하려는 위치**다. 그 한 행만 있으면 되므로 `seq × seq` 전체를
파이썬으로 옮기지 않는다. 이후 집계는 torch 없는 순수 함수(`span_metrics`)가 맡아
단위 테스트가 가능하다.

**구간(span) 구성:**

| 구간 | 내용 |
|---|---|
| `code_camel` / `code_snake` | 선행 코드 이름을 표기별로 나눈 것 |
| `instruction` | 지침 문장 전체 |
| `instr_target_word` / `instr_viol_word` | 지침 안의 지시어 단어 (`camelCase` / `snake_case`) |

지시어 단어를 따로 잡는 이유: **지침 문장 전체와 그 안의 표기 단어는 다른 것**이기 때문이다.
"지침을 본다"와 "지침 안의 camelCase라는 단어를 본다"를 구별해야 RQ3에 답할 수 있다.

## 3.2 인과 — 반사실 KV 치환 (counterfactual patching)

핵심 아이디어: **같은 텍스트, 다른 내부 표현.** 프롬프트는 위반 그대로 두고, 위반 이름
토큰의 K 또는 V만 "준수판이었다면 가졌을 값"으로 덮는다. 행동이 바뀌면 그 표현이 원인이다.

### 3.2.1 준비 (`_preference_context`)

세 개의 프롬프트를 각각 **한 번씩만** forward해 캐시를 만든다.

| 캐시 | 프롬프트 | 역할 |
|---|---|---|
| `viol_cache` | 실제 조건 (위반 포함) | 개입 대상 (바닥) |
| `comp_cache` | 같은 선행을 **전부 준수 표기**로 렌더 | 천장 기준 |
| `donor_cache` | 공여 표현의 출처 (기본은 `comp_cache`) | 덮어쓸 값의 재료 |

```python
viol_cache = self.model(viol_ids[:, :-1], use_cache=True).past_key_values
viol_last  = viol_ids[:, -1:]
```

마지막 토큰을 캐시에서 빼두는 이유: 채점 forward에서 `[마지막 토큰 + 후보 토큰들]`을
한 번에 넣기 위해서다. 층 스윕에서 층을 바꿔도 **선행 프롬프트를 재계산하지 않는다**
(무료 티어 GPU 비용 절감).

### 3.2.2 정렬 (alignment) — 토크나이저와 싸우는 부분

"`format_matrix`의 V를 `formatMatrix`의 V로 바꾼다"는 말은 간단하지만, 두 이름의 **토큰
개수가 다르다**(3 vs 2). 어느 토큰을 어느 토큰으로 바꿀 것인가. 세 가지 방식이 있다.

| `token_unit` | 방식 | 장점 | 단점 |
|---|---|---|---|
| `all` | 첫↔첫, 둘째↔둘째 1:1 | 단어 전체를 덮어 신호가 강함 | **토큰 수가 다르면 그 이름 통째로 제외** |
| `last` | 마지막 토큰 하나만 1:1 | 항상 짝이 맞아 제외 없음 | 신호가 약함 |
| `mean` | **평균 덮어쓰기 (mean-pool)** | 제외 없음 + 단어 전체를 덮음 | 공여 토큰들의 평균이라 세부 구조는 잃음 |

**`mean`이 현재 표준이다** (CLAUDE.md §3). 이유: `all`은 camel/snake 토큰 수가 다른 모델에서
**전부 스킵**되어 측정 자체가 안 되고, `last`는 신호가 약하다. `mean`은 토크나이저에
무관하고 코드·지침 양쪽에 같은 방식을 쓸 수 있다.

```python
# align_name_groups → [(위반 위치들, 공여 위치들), ...]  개수 불일치 허용
km = dk[:, :, dps, :].mean(dim=2)     # 공여 토큰들의 K 평균 → [B, n_kv, d]
for vp in vps:
    ek[:, :, vp, :] = km              # 위반 이름의 모든 토큰 자리에 브로드캐스트
```

### 3.2.3 치환과 복구 (`_score_layer_kind`)

```python
ek, ev = _cache_kv(work_cache, layer)     # 편집 가능한 원본 참조
dk, dv = _cache_kv(donor_cache, layer)

# 1) 백업 뜨고 덮어쓰기
bv[vp] = ev[:, :, vp, :].clone()
ev[:, :, vp, :] = vm

# 2) 점수 측정 (S 내부에서 캐시를 복제해 forward → work_cache 오염 없음)
s_int = ctx["S"](work_cache, ctx["viol_last"])

# 3) 원상 복구 → 다음 층이 깨끗한 위반 상태에서 시작
for vp, b in bv.items():
    ev[:, :, vp, :] = b
```

**편집→측정→복구**를 반복하므로 층마다 캐시를 깊은 복사할 필요가 없다. 36층 × 3경로 =
108회 측정을 캐시 하나로 처리한다.

`kind`에 따라 무엇을 덮을지 갈린다:

| `kind` | 덮는 것 | 검증하는 것 |
|---|---|---|
| `key` | K만 | **라우팅**만 준수판으로. 읽히는 내용(V)은 위반 그대로 |
| `value` | V만 | **운반물**만 준수판으로. 어디를 볼지(K)는 위반 그대로 |
| `key_value` | 둘 다 | 상한 |

**이 대비가 이 연구의 심장이다.** `key`가 안 먹히고 `value`가 먹히면, 표기 신호는
어텐션 라우팅이 아니라 **내용**에 있다는 뜻이다.

### 3.2.4 채점 (`logp_candidate`)

```python
c = _clone_cache(cache)                                  # 원본 보호
inp = torch.cat([last_tok, cand[:-1].unsqueeze(0)], dim=1)
logits = self.model(inp, past_key_values=c, use_cache=True).logits[0]
lp = torch.log_softmax(logits.float(), dim=-1)
return sum(lp[k, cand[k]] for k in range(len(cand)))
```

`inp`의 위치 0(마지막 프롬프트 토큰)이 `cand[0]`을 예측하고, 위치 k가 `cand[k]`를 예측한다.
teacher forcing으로 후보 문자열 전체의 로그확률을 한 번의 forward로 얻는다.

### 3.2.5 통제 조건 (donor 종류)

무엇을 덮어쓸 재료로 쓰느냐가 **"신호가 의미인가 형태인가"** 를 가른다.

| `donor` | 공여 재료 | 무엇을 검증하나 |
|---|---|---|
| `compliant` | **같은 이름**의 준수판 (`format_matrix`→`formatMatrix`) | 기본 조건 |
| `unrelated_camel` | **전혀 다른 이름**의 camel판 (`parseHeader` 등) | 의미가 달라도 회복되면 → 신호는 **형태** |
| `unrelated_snake` | 다른 이름의 snake판 | 방향 통제 |

무관 이름은 `unrelated_specs()`가 **선행에 안 쓰인 풀 이름**에서 뽑는다(중복 방지).

### 3.2.6 지침 쪽 개입 (step4/5) — 같은 기계, 대상만 교체

RQ3은 "지침의 영향력도 같은 통로인가"를 묻는다. **치환 로직을 새로 쓰지 않는다.**
`_preference_setup_instruction`이 딱 두 곳만 바꾼다.

| | 코드 개입 (step3) | 지침 개입 (step5) |
|---|---|---|
| **치환 대상** | 선행 코드의 위반 이름 | 지침 문장의 지시어 단어 `camelCase` |
| **`span_kind`** | `def_name` (`def <nm>(`의 이름) | `literal` (문자열 첫 등장) |
| **공여** | 같은 이름 준수판 | **반대 지침**을 렌더한 프롬프트 |
| **천장** | 위반 없는 선행 | 반대 지침 |

`literal`이 **첫 등장**을 잡는 이유: 지침은 rule 문장 다음에 "두 후보 중 하나"라는 closed
문장이 오는데, 두 문장 모두 `camelCase`를 포함한다. rule 문장이 먼저이므로 첫 등장이
**실제 지시어**다.

# 4부. 코드 구조

## 4.1 설계 원칙 — RQ별 스크립트를 만들지 않는다

**모든 실험이 `run(condition)` 하나를 통과한다.** RQ1/RQ2/RQ3은 스크립트가 아니라
**조건 객체의 값 조합**으로 구분된다. `run_rq1.py` 같은 파일은 금지다(CLAUDE.md §7).

이유: 같은 실험 로직이 RQ마다 복붙되면 조건이 조용히 어긋난다. 실제로 `preceding_specs()`와
`build_preceding_code()`는 **같은 seed·같은 셔플 규칙**을 공유해야 하는데, 이게 두 파일에
따로 있으면 개입 대상 이름과 실제 렌더된 이름이 달라진다. 하나의 진입점이 이를 막는다.

## 4.2 파일별 역할

```
conditions.py   실험 설계의 단일 진실 공급원 (스키마 + 파일명 슬러그)
     ↓
tasks.py        함수 과제 정의 (이름 단어 + 본문). 504개 이름 풀
naming.py       camel/snake 렌더링과 판정 (정규식)
prompt.py       선행 코드·지침 문장·메시지 조립 (순수 문자열, 모델 무관)
     ↓
model.py        ★ 모델 접근 전부. 로딩·생성·관측·KV 치환
     ├─ attention_probe.py    구간 집계·GQA 매핑·코사인 (torch 없음, 순수 함수)
     └─ intervention.py       정렬·회복률·선호 점수 (torch 없음, 순수 함수)
     ↓
runner.py       ★ 단일 진입점 run(condition). mode에 따라 라우팅
     ↓
metrics.py      측정값 컨테이너
results.py      불변 저장 (슬러그 파일명, 덮어쓰기 금지)
```

**설계 포인트 — torch 의존성 분리.** `attention_probe.py`와 `intervention.py`는 torch/numpy를
쓰지 않는다. 리스트와 스칼라만 다룬다. `model.py`가 큰 텐서에서 **작은 조각만**
(마지막 query 행 `[Hq, seq]`, 토큰별 ‖v‖ `[Hkv, seq]`) 리스트로 떼어 넘긴다. 덕분에
집계 로직을 GPU 없이 단위 테스트할 수 있고, 큰 텐서를 파이썬으로 옮기지 않아 가볍다.

**지연 임포트.** `model.py`는 `import torch`를 함수 안에서 한다. 조건 스키마 검증·결과
로딩은 torch 없이 돌아야 하기 때문이다(노트북 셀 구성, 로컬 분석).

## 4.3 `run()` 라우팅

```python
run(condition, handle, mode=...)
```

| `mode` | 경로 | 무엇을 하나 | 쓰는 스텝 |
|---|---|---|---|
| `generate` | `_run_generation` | 실제 생성 → 표기 판정 → 준수율 | **step1** |
| `generate` + 개입≠none | `_run_intervention` | 단일 층 KV 치환 → 선호 점수·되돌림 | step3/5 |
| ↳ `layers="sweep"` | `_run_intervention_sweep` | **전 층 × K/V 3경로** 스윕 | step3/5 |
| `observe` | `_run_observation` | 어텐션·‖v‖·‖av‖ 구간 집계 | step2/4 |
| `vcosine` | `_run_cosine_sweep` | camel/snake v 방향차 층별 궤적 | step2 |
| `intervene_generate` | `_run_intervention_generate` | 치환 후 **실제 생성** (선호 점수의 직관적 재확인) | step3 |

분기 조건은 전부 **조건 객체의 값**이다. `if rq == 1` 같은 코드는 없다.

## 4.4 조건 스키마 = 실험 설계 = 파일명

`Condition`은 `frozen=True` 데이터클래스다. 이 객체 하나로 실험이 완전히 재현된다.

```
Condition
├── model         ModelSpec       HF ID, dtype, 양자화
├── preceding     PrecedingCode   준수 개수 / 함수 수 / 구성 / 출처 / 풀 블록 / 언어
├── instruction   Instruction     긍정·부정 / 목표 표기 / 어조 / 닫힌 후보
├── intervention  Intervention    종류 / 층 / 공여 / 배율 / 대상(code|instruction)
├── seed          int
└── token_unit    str             all | last | mean
```

`__post_init__`이 불가능한 조합을 **생성 시점에 거부**한다. 예: `kind=NONE`인데 `layers`가
있으면 예외. 잘못된 실험이 GPU를 태우고 나서 발견되는 일을 막는다.

**슬러그.** `Condition.slug()`가 결정적 파일명을 만든다:

```
qwen2-5-coder-3b-instruct__pre-c0of12-pool-syn-b23__ins-pos-snake-w__int-none__s42.json
└─ 모델 ─────────────┘  └─ 선행: 준수0/12,풀,블록23 ┘ └─ 지침 ┘ └개입┘ └seed┘
```

**파일명만 보면 조건을 안다.** 결과 폴더를 `ls` 하는 것이 곧 실험 목록 확인이다.

## 4.5 결과 불변 규약

```python
if path.exists() and not overwrite:
    raise FileExistsError("결과가 이미 존재한다(불변 규약, §6)")
```

이미 있는 결과는 **덮어쓰지 않는다.** 두 가지 효과:

1. **재개.** 런타임이 끊겨도 이미 저장된 조건은 건너뛰고 남은 것만 이어서 돈다.
   노트북 셀 ④의 `todo = [c for c in conditions if not result_path(c).exists()]`가 이것이다.
2. **결과 보호.** 조건을 슬쩍 바꿔 재실행해 이전 결과를 지우는 일이 구조적으로 불가능하다.

| ④ | 실행 — 조건마다 즉시 저장(재개) |
| ⑤~⑥ | 결과 로드·요약 |
| ⑦ | 결과 폴더 zip 다운로드 |

**모델 하나씩 도는 이유:** 무료 티어 런타임이 끊겨도 그 모델만 영향받는다.

# 5부. step1 한 조건이 흐르는 경로

실제 결과 파일 하나를 거꾸로 따라가 본다.

```
qwen2-5-coder-3b-instruct__pre-c0of12-pool-syn-b23__ins-pos-camel-w__int-none__s42.json
```

**① 조건 객체 생성** (노트북 셀 ③)

```python
Condition(
    model=ModelSpec("Qwen/Qwen2.5-Coder-3B-Instruct", "qwen", "float16"),
    preceding=PrecedingCode(n_compliant=0, n_functions=12,
                            composition=Composition.POOL, pool_block=23),
    instruction=Instruction(InstructionForm.POSITIVE, Notation.CAMEL, Strength.WEAK),
    seed=42,
)
```

준수 0개 = **12개 전부 위반**. 풀 블록 23 = 504개 이름 중 `[276, 288)` 구간.

**② 지침 문장** (`build_instruction_text`)

```
You are helping extend an existing Python module.
In this project we generally write function names in camelCase.
Every function name uses one of two styles only: camelCase or snake_case.
```

- **약한 어조** (`generally`). 강한 어조(`always`)는 준수율이 포화돼 조건 차이가 사라진다.
- **닫힌 후보** 문장이 필수다. 없으면 부정형 지침("snake를 쓰지 마라")이 긍정형과 논리적
  등가가 안 된다 — 모델이 제3의 표기(PascalCase 등)로 도망갈 수 있다.

**③ 선행 코드** (`build_preceding_code`)

```python
notations = [target]*0 + [violation]*12      # snake 12개
random.Random(42).shuffle(notations)         # 위치 변주
idxs = list(range(276, 288)); random.Random(42).shuffle(idxs)
```

seed는 **개수가 아니라 위치·이웃 순서**를 섞는다. 개수는 조건이 정하고, seed는 배치만
바꿔 문맥 강건성 변주를 준다. 실제 출력(앞 3개, 이 조건은 12개 전부 snake):

```python
def split_index(value):
    return value

def decode_matrix(value):
    return value

def fetch_session(value):
    return value
```

**④ 메시지 조립**

```python
[{"role": "system",  "content": <지침>},
 {"role": "user",    "content": "Here is the current module:\n\n```python\n<선행 12개>\n```\n\n"
                                "Add a function that removes duplicate items from a list, preserving order."}]
```

**⑤ 생성** (`chat_generate`)

```python
out = self.model.generate(**enc, max_new_tokens=100, do_sample=False)   # 그리디
```

`temperature=0` → `do_sample=False` → **그리디**. 재현성 확보. 여러 seed로 흔들어 보는
대신 **42개 이름 묶음**으로 변주를 준다(seed는 배치에만 작용).

**⑥ 판정**

```python
name = first_function_name(text, "python")   # "remove_duplicates_preserve_order"
classify_name(name)                          # "snake"
compliance_rate = 1.0 if "snake" == "camel" else 0.0    # → 0.0  (위반)
```

**⑦ 저장** — 슬러그 경로에 JSON. 생성 원문(`turn_texts`)까지 통째로 보존해 눈으로
재검증할 수 있게 한다.

**⑧ 집계** — 42묶음 × 13 위반개수 × 2 방향 = 1,092회. `scripts/step1_cliff_report.py`가
이를 읽어 곡선을 그린다.

# 6부. 설계 결정과 근거 (리뷰어 예상 질문)

| 결정 | 이유 |
|---|---|
| **`def ` teacher forcing** | 모든 조건에서 **같은 순간**을 측정. 이름이 언제 나올지 기다리지 않는다 |
| **그리디 디코딩** | 재현성. 변주는 seed가 아니라 **이름 묶음 42개**로 준다 |
| **닫힌 후보 2개** | 부정형 지침이 긍정형과 논리적 등가가 되게. 제3 표기 도피 차단 |
| **약한 어조** | 강한 어조는 준수율이 천장에 붙어 조건 차이가 안 보인다 |
| **두 단어 이상 이름** | 한 단어는 camel==snake라 판정 불가 |
| **KV 캐시 직접 편집** | 층 국소성 확보(§1.5). 훅으로 모듈 출력을 바꾸면 이후 층까지 전파돼 층 분해가 깨진다 |
| **캐시 편집 = KV group 단위** | 캐시에 `n_kv`개만 있어 group을 쪼갤 수 없다. GQA 요구(§1.4)를 구조적으로 만족 |
| **mean-pool 표준화** | 토크나이저 무관. `all`은 스킵 폭주, `last`는 신호 약함 |
| **선행 프롬프트 1회 forward** | 층 스윕 108회 측정에 프리필 3회면 충분. 무료 티어 비용 |
| **결과 불변** | 재개 가능 + 결과 조용한 덮어쓰기 방지 |
| **504 이름 풀, 블록 커버** | 특정 단어 우연 효과 배제. 블록으로 나눠 **중복 없이** 전부 소진 |

# 7부. 용어 대조표

| 우리 화면 표기 (§5 쉬운 말) | 학술 용어 | 정의 |
|---|---|---|
| 얼마나 보나 | attention weight | `softmax(q·k/√d)` |
| 실어 나르는 내용 | value / V | `h·W_V`, 어텐션이 가중합하는 대상 |
| 색인 | key / K | `h·W_K`, 어텐션 가중치를 정하는 쪽 |
| 바꾼 조각 수 | n_substituted_tokens | 치환한 (위치×층) 자리 수 |
| 영향력 | S_clean − S_base | 지침·문맥이 행동을 실제로 바꾸는 폭. 0이면 판정 불가 |
| 되돌림 정도 | recovery rate | `(S_int−S_base)/(S_clean−S_base)` |
| 평균 덮어쓰기 | mean-pool patching | 공여 토큰 K/V 평균을 대상 자리 전체에 브로드캐스트 |
| 어느 층 | layer / relative depth | `layer/(L−1)` |
| 준수 선호 점수 | preference score S | `logP(준수 이름) − logP(위반 이름)` |
| 반사실 치환 | counterfactual patching / activation patching | 텍스트 고정, 내부 표현만 교체 |

# 8부. 현재 미비점 (정직한 목록)

1. **어텐션 증폭 개입 미구현.** `ATTENTION_AMPLIFY`는 스키마에만 있다. Spotlight를 직접
   반박하려면 필요하다(§1.6).
2. **‖av‖의 해석 한계.** `Σa‖v‖`는 실제 잔차 기여 노름의 상한이고 `W_O` 이전 값이다(§2.4).
   상대 비교용으로만 써야 한다.
3. **로짓 렌즈 미도입.** "어느 층에서 표기가 확정되나"를 직접 보여줄 수단이 없다(§1.7).
4. **step1은 1턴만 생성.** 자기증폭(모델 자신의 위반이 다시 문맥이 되는 연쇄)은 코드에
   자리(`subsequent_violation_rate`)만 있고 측정하지 않았다.
5. **실코드(`Source.REPO`) 경로 미사용.** 합성 코드만 돌렸다. 외적 타당성 확보에 필요하다.
