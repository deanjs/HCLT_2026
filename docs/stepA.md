# step A — RQ1 절벽 재현 (A1 생성)

**한 줄:** 선행 코드에 규약 준수 예시가 몇 개 남았느냐에 따라 이후 생성의 준수율이 어떻게 변하는지 재서, "0개에서 절벽 + 자기증폭"을 이 하네스에서 직접 만든다.

대응: **RQ1** (선행 코드의 위반이 이후 준수율을 낮추는가) — 계획서 §3 RQ1.

## 프롬프트 구조: 선행 12 + 생성 3

| 구획 | 개수 | 기능 | 표기 | 역할 |
|---|---|---|---|---|
| **선행** | 12 | **모두 동일**(clone) | `n_compliant`개 camel + 나머지 snake, 위치 셔플 | 모델이 읽는 재료 |
| **생성** | 3 | **서로 다름**(distinct) | 모델이 선택 | 측정 대상 |

- **선행 12**는 프롬프트에 미리 써넣는 함수(모델은 읽기만). 같은 일을 하고 이름만 다르다.
- **생성 3**은 모델이 새로 쓰는 함수. **첫 번째**의 표기가 준수율, 2·3번째는 자기증폭 관측용.
- 생성 3은 선행 과제와도, 서로와도 달라야 한다 — 같으면 모델이 이름을 복사해 "직접 선택"을 못 본다.

## 바꾸는 조건 축

| 축 | 값 |
|---|---|
| 선행 `n_compliant` | **4 / 3 / 2 / 1 / 0** (12개 중 camel 준수 개수) |
| 선행 `composition` | **clone** |
| 선행 `source` | synthetic |
| 지침 | 긍정 · 목표=camel · 약한 어조 |
| 개입 | none |
| 반복 | 조건당 seed 20 |

→ 5(개수) × 20(seed) = **100회 생성**.

## 재는 것

- **준수율**: 생성 첫 함수가 camel인가 (조건별 비율)
- **자기증폭**: 첫 함수 위반 시 2·3번째로 위반이 연쇄되는가

## 예상과 해석 (어느 쪽이든 그대로 기록, §4)

| 결과 | 해석 | 다음으로 |
|---|---|---|
| ≥1개는 85~90%, **0개에서 ~30% 급락** | 절벽 재현 = A1 | RQ2("무엇이 매개하나") |
| 4→0 매끄러운 하락 | 절벽 아님 | ICL 오버라이드와 구별 필요 |
| 첫 함수 위반 → 뒤 연쇄 | 자기증폭 확인 | 자기 출력이 다시 입력 |

## 구현 범위

`runner.py`의 생성 경로 4단계만 채운다:

| 단계 | 하는 일 |
|---|---|
| `build_preceding` | 선행 12개 구성 (clone, n_compliant camel + 나머지 snake, 셔플) |
| `build_instruction` | 지침 문장 (긍정·camel·약한 어조·닫힌 후보) |
| `build_prompt` | 선행 + 지침 + 생성 과제 → 프롬프트 조립 (chat template) |
| `measure_generation` | 3개 순차 생성 → 첫 함수 표기 판정 → 준수율·자기증폭 |

개입·어텐션 단계(step B·C)는 건드리지 않는다. 과제 스펙과 실제 프롬프트 문구는 `docs/stepA_prompt.md`.

## 설정

**조정 가능한 실행 파라미터** (노트북 셀 4·5에서 바꾼다):

| 파라미터 | 기본값 | 뜻 | 늘리면 / 줄이면 |
|---|---|---|---|
| **모델** | `Qwen/Qwen2.5-Coder-3B-Instruct` (fp16) | 실험 대상 코드 생성 모델 | 크면 정확·느림·메모리↑. 다른 패밀리는 step 2 |
| **표본 크기** | 5 n_compliant × 20 seed = **100회** | 조건당 생성 반복 수. 준수율의 통계적 안정성 | seed↑면 곡선 매끄러움·시간↑. seed↓면 노이즈↑ |
| **max_new_tokens** | **256** | 한 함수 생성 시 뽑는 최대 토큰 수 | 작으면 함수가 잘려 첫 `def` 못 잡을 수 있음·빠름. 크면 안전·느림 |

- **표기 판정**: 생성된 첫 `def`의 함수명이 camel/snake 중 무엇인지 정규식. 둘 다 아니면 `other`로 분류
- **과제 스펙**: 선행용 clone 과제 1 + 생성용 서로 다른 과제 3을 합성으로 정의(코드에 고정)

## 대조 계획 — step A-1 · A-2 (병렬)

step A(합성 clone)의 절벽 주장에 두 가지 반론이 가능하다. 각각을 **선행 코드 축만 바꾼 별도 실험**으로 방어하며, 셋은 서로 입력·출력을 주고받지 않아 병렬로 돈다. A-1·A-2는 step A와 **같은 생성 4단계**를 재사용하고, 조건 축의 `composition`·`source`만 다르다.

| 실험 | 원래 | 바꾸는 축 | 막는 반론 | 대조 방식 |
|---|---|---|---|---|
| **step A-1** | step 3 | `composition = distinct` (선행 12개를 **서로 다른 과제**로) | "준수 실패가 아니라 in-context 데모를 따라한 것" | step A(clone)와 **절벽 유무를 나란히 비교**. distinct에서도 0개 절벽이 재현되면 데모 오버라이드 반론 무력화 |
| **step A-2** | step 4 | `source = repo` (합성 대신 **실제 저장소 파일**) | "합성 코드라서 생긴 인공물" | 언어 관습을 자연 실험으로: Python(자연 snake)·JS/Java(자연 camel) × 지침 camel/snake 2×2. **충돌 칸**에서 준수율 하락 시 실코드에서도 재현 |

- 판정은 전부 **준수율(생성)** 하나로 통일 — step A와 같은 지표라 곡선을 겹쳐 그릴 수 있다.
- A-2는 실제 코드에 camel/snake 대응쌍이 없어 내부 개입은 하지 않는다(생성률만).
- 실험 하나당 브랜치 하나(§2): `stepA-1/…`, `stepA-2/…`. step A 완료 후 **하나씩** 착수한다.
