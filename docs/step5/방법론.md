## 1. 왜 이 실험을 하나

step4는 "지침을 본다"까지였다. 보는 것과 **따르는 것**은 다르다.

**RQ3(인과) — 지침 신호도 코드와 같은 통로(내용/Value)인가?**

step3의 지침 판이다. 장치가 완전히 같고 **치환 대상만 다르다.**

| | step3 | step5 |
|---|---|---|
| 바꾸는 곳 | 선행 코드의 **위반 이름 6개** | 지침의 **지시어 단어 1개** |
| 공여 | 같은 이름의 준수판 | **반대 지침**의 지시어 |
| 구간 종류 | `def_name` | `literal` |

## 2. 무엇을 건드리나

```
   base 프롬프트:
   "In this project we generally write function names in camelCase."
                                                          ^^^^^^^^^
                                                          여기 캐시만 교체
   반대 지침 프롬프트:
   "In this project we generally write function names in snake_case."
                                                          ^^^^^^^^^
                                                          여기서 가져온다
```

**글자는 `camelCase` 그대로 두고, 모델 속 값만 `snake_case`의 것으로 바꾼다.**
그러고 나서 모델이 어느 표기를 선호하는지 본다.

### 위치가 정확히 일치한다

두 프롬프트는 지시어 단어를 빼면 **완전히 같다.**

```
   base:     "You are helping extend an existing Python module.\nIn this project we generally write function names in camelCase."
   opposite: "You are helping extend an existing Python module.\nIn this project we generally write function names in snake_case."
              └────────────────── 103번째 글자까지 동일 ──────────────────┘
```

→ 덮을 자리와 공여 자리의 **시작 위치가 같다**(진단 A에서 어긋남 0.5칸 이하 확인).
step3보다 위치 조건이 깨끗하다.

## 2-1. 실제로 만들어지는 프롬프트

위 그림은 지침 문장만 떼어 보인 것이다. **실제로 모델에 들어가는 글자 전체**는 아래와 같다
(`runner.py:471 _preference_setup_instruction`이 만든 것을 그대로 찍었다. 재현: §2-3).

### ① 기준 프롬프트 — 실험 대상. 여기 점수를 잰다

```
[system] You are helping extend an existing Python module.
         In this project we generally write function names in camelCase.   ← 규칙문
         Every function name uses one of two styles only: camelCase or snake_case.   ← 후보열거
[user]   Here is the current module:

         ```python
         def split_config(value): ...        ← 선행 코드 12개(6개 snake)
         def decodeNode(value): ...
         ... (12개)
         def resolve_packet(value): ...
         ```

         Add a function that removes duplicate items from a list, preserving order.
```

여기서 잰 점수가 **`S_기준`**.

> ⚠️ **`camelCase`는 이 프롬프트에 두 번 나온다** — 규칙문(103번째 글자)과 후보열거(163번째 글자).
> **덮는 것은 첫 번째(규칙문) 하나뿐이다.** 후보열거의 것은 건드리지 않는다.
> 후보열거는 두 표기를 대칭으로 나열하는 문장이라 "지시"가 아니기 때문이다
> (`model.py:816 _locate_target_tokens`의 `span_kind="literal"`이 **첫 등장**만 잡는다.
> 규칙문이 후보열거보다 항상 앞서므로 첫 등장 = 규칙문이 성립한다).

### ② 반대 지침 프롬프트 — 천장 기준. 여기도 점수를 잰다

①과 비교해 **바뀌는 글자는 규칙문의 단어 하나뿐**이다.

```
[system] You are helping extend an existing Python module.
         In this project we generally write function names in snake_case.   ← 여기만 다르다
         Every function name uses one of two styles only: camelCase or snake_case.
[user]   (①과 글자 하나 안 틀리고 완전히 동일 — 선행 코드 12개 그대로)
```

**선행 코드는 두 프롬프트가 공유한다.** step3은 선행 코드를 바꿔 두 상태를 만들었지만,
step5는 **지침 한 단어만** 바꾼다. 여기서 잰 점수가 **`S_반대`(천장)**.

### ③ 공여 프롬프트 — 처치에는 **없다**

step3과 반대다. 처치(`반대 지침`)는 ③을 따로 만들지 않고 **②를 그대로 공여로 쓴다**
(코드에서 `donor_messages = None`으로 찍히는 것이 그 뜻이다).
③을 실제로 새로 만드는 것은 **통제 두 종류뿐**이고, 그것도 **①을 한 번 더 통과시킬 뿐**이다.

| 공여 | ③을 따로 만드나 | 어느 프롬프트에서 | 어느 단어를 떠 오나 |
|---|---|---|---|
| **반대 지침**(처치) | 아니오 — ②를 재사용 | ② 반대 지침 | `snake_case` (규칙문, 103번째 글자) |
| **자기 통제** | 예 — ①을 한 번 더 | ① 기준 | `camelCase` (규칙문 — **같은 자리 같은 단어**) |
| **지시어 절제** | 예 — ①을 한 번 더 | ① 기준 | `project` (같은 규칙문 안의 무관한 단어) |

| 프롬프트 | 채점하나 | 무엇을 위한 것 |
|---|---|---|
| ① 기준 | **잰다 → `S_기준`** | 실험 대상 |
| ② 반대 지침 | **잰다 → `S_반대`** | 천장 기준 · 처치 공여로도 재사용 |
| ③ (통제일 때만) | **안 잰다** | 덮어넣을 내부 값을 뽑는 곳 |

## 2-2. 측정 절차 — 층 하나당 이렇게 돈다

**점수 S 재는 법.** 프롬프트 끝에 `def `를 강제로 붙여 이름 자리를 만들고, 그 자리에 올
후보 두 개의 로그확률을 재서 뺀다(`removeDuplicates` ↔ `remove_duplicates`).
부호 규약은 §3을 먼저 볼 것 — **`camel − snake`가 아니라 `지침 목표 − 반대`다.**

**절차** (Qwen · camel 지침 · 42묶음 평균 실측값).

```
 준비 (딱 한 번)
   1. ①②를 각각 한 번씩 모델에 통과시켜 캐시 2개를 만든다
      (통제 조건이면 ③도 한 번 — 즉 ①을 한 번 더)
   2. ①에서 잰다 → S_기준 = +0.085
      ②에서 잰다 → S_반대 = −4.799        ← 천장이 **아래쪽**이다
   3. ①의 규칙문 `camelCase`, ②의 규칙문 `snake_case`가 각각 몇 번째 토큰인지 찾는다
      → Qwen은 2개 토큰. (DeepSeek 3~4개 · StableCode 2~3개 · Llama 2개)

 층 L 하나마다 (전 층, 방식 3가지씩)
   4. ②의 캐시에서 `snake_case`가 차지한 토큰들의 값을 꺼내 평균 내 벡터 하나로 만든다
   5. ①의 캐시에서 `camelCase`가 차지한 토큰 자리에 그 벡터를 덮어쓴다. 층 L에서만
        → 화면 글자는 여전히 `camelCase`다. 바뀌는 것은 내부 값뿐이다
   6. 그 상태로 다시 잰다 → S_개입 = −4.074   (L27, 내용만)
   7. 전이율 = (S_개입 − S_기준) / (S_반대 − S_기준)
             = (−4.074 − 0.085) / (−4.799 − 0.085) = 0.851
   8. **원상 복구**하고 다음 층으로  ← 층 효과는 누적되지 않는다
```

> **step3과 방향이 반대다.** step3의 천장(`S_깨끗`)은 바닥보다 **위**였고 개입하면 점수가
> 올라갔다. step5의 천장(`S_반대`)은 기준보다 **아래**다 — 지침을 뒤집는 실험이니 당연하다.
> 그래서 **전이율이 커질수록 S는 내려간다.** "되돌림"이 아니라 **"넘어감"** 이라고 부르는 이유다.

**그리고 이 전체를 공여만 갈아끼워 세 번 돌린다.** ①②는 셋 다 완전히 동일하고,
**세 조건 모두 전 층을 훑는다.**

| 무엇을 덮어넣나 | 표기 정보 | Qwen L27 내용만 |
|---|---|---|
| `snake_case` (② 반대 지침에서) | 들어감 | 0.775 |
| `camelCase` (① 자기 자신에서 — 평균 낸 뒤 덮음) | **안 들어감** | 0.050 |
| **차이 = 순효과** | | **0.725** |

> **세 값 모두 확정값이다.** 예전에는 통제를 **봉우리 층 한 곳에서만** 재서 가운데·아래 줄이
> 잠정값이었으나, 통제도 **전 층에서 다시 쟀다**(모델당 168조건, 합 672).
> 봉우리 층 값은 옛 실행분과 소수점까지 같았고(세 모델 1,512개 전부 일치),
> 네 모델 모두 **그 층이 실제 봉우리**임이 확인됐다
> (→ [`results.md`](results.md) §3-2·§3-8).

가운데 줄은 **같은 단어를 같은 자리에 다시 덮는 것**인데도 0.050이 나온다. 항등 개입이
아니기 때문이다 — 조각들을 평균 내 뭉개서 넣으므로 그만큼 교란이 남는다(§4).

## 3. 재는 값

```
   S = log P(지침 목표 표기 이름) − log P(반대 표기 이름)
```

> **부호 주의.** `logP(camel) − logP(snake)`가 **아니다.**
> 목표 표기 기준이므로 snake 지침 조건에서는 부호 관계가 뒤집힌다.
> 실데이터로도 확인: snake 목표 조건은 `S_base > 0`이 168개 중 148개,
> camel 목표 조건은 `S_base < 0`이 168개 중 **137개**.

```
              S_개입 − S_기준
   전이율 = ──────────────────
              S_반대 − S_기준

   S_기준 : 조건 지침 그대로 (camel 지침)
   S_반대 : 반대 지침을 실제로 준 상태 (snake 지침) — 천장
   S_개입 : camel 지침인데 지시어 KV만 snake 것으로 교체
```

**1 = 반대 지침을 실제로 준 것과 같은 수준까지 넘어갔다.**

## 4. 통제 — 세 종류

| 공여 | 지시어 자리에 넣는 것 | 표기 정보 | 정상이면 |
|---|---|---|---|
| **반대 지침** (처치) | 반대 지침의 지시어 | 들어감 | 크게 넘어감 |
| **자기 통제** | **같은 지침의 같은 지시어** | **안 들어감** | ≈ 0 |
| **지시어 절제** | 같은 지침의 무관한 단어(`project`) | 안 들어감 | — |

**순효과 = 처치 − 자기 통제.**

자기 통제는 내용이 그대로이므로 순수하게 "덮어쓰는 행위 자체"의 몫(거품)이다.
(완전한 항등은 아니다 — 자기 조각들을 평균 내 다시 넣으므로 약한 평탄화가 일어난다.)

> **절제 조건은 통제가 아니다.** 지시어 자리를 `project`로 덮으면 **지침이 지워진다.**
> 그러면 모델이 "지침 없는 상태"로 가는데, 그 방향이 마침 반대 지침 쪽과 같다.
> 그래서 값이 크게 나온다(0.27~0.45). 이건 거품이 아니라 **"지시어를 없애면 어떻게 되나"** 를
> 따로 보는 실험이다.

## 5. 파이프라인

```

   ▼
Metrics.per_layer[L]["value__recovery"] 등
```

| **분석** | camel·snake 방향을 **합쳐서** 평균 | **방향별로 분리** | StableCode가 camel 0.45 / snake 1.32로 3배 차이. 평균 0.89는 두 분포를 섞은 값이고 84개 중 38개가 전이율 1을 넘는다 |
| **서술** | `S = logP(camel) − logP(snake)` | **`logP(목표 표기) − logP(반대 표기)`** | snake 목표 조건에서 부호가 뒤집힌다. 이대로면 재현자가 계산을 틀린다 |
| **서술** | "코드 층 ≈ 지침 층 (1~3층 차이)" | **철회** | step3는 camel 한 방향, step5는 양방향 평균 — 조건 집합이 다른 두 봉우리를 맞댄 것이었다. 대신 **step4 관측 ↔ step5 인과** 일치로 대체(3모델 정확히 같은 층) |
| **분석** | 판정 불가 기준 1.0을 노트북 지역 상수로 | **하네스 규약 + 민감도 표** | 기준을 0.5/1.0/2.0 어디에 둬도 전이율은 불변임을 확인 |
| **해석** | 무관 단어를 "음성 통제"로 | **"절제 실험"으로 재해석** | 지시어를 지우면 지침이 무력해지고, 그 방향이 반대 지침 쪽과 같다. 방식 간 차이도 없다(0.415 vs 0.443) |
| **코드** | 층 목록을 주면 첫 층만 | **예외** | 통제를 봉우리−3층에서 재는 사고가 실제로 났다 |
| **코드** | 통제를 K+V 방식으로만 측정 | **세 방식 동시**(`Intervention.kinds`) | 본실험 헤드라인은 Value 단독인데 K+V 거품을 뺄 수 없다 |

## 9. 이 스텝의 한계

- **규칙문 지시어 한 곳만** 바꾼다. 후보열거의 같은 단어는 남아 효과가 희석될 수 있다
- 긍정형·약한 어조 **고정(통제 상수)**. 지침 표현 방식은 RQ3의 축이 아니다(계획서 §0)
- 채점 대상은 고정된 이름 **한 쌍**
- 자기 통제는 완전한 항등이 아니다(약한 평탄화, 내용 쪽 0.05~0.09가 그 크기)
- step3와 봉우리 층을 직접 비교하지 않는다(조건 집합이 다르다)
