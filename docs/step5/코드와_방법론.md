## 1. 큰 그림 — step5는 한 문장으로 무엇인가

> 지침 문장 안의 **지시어 단어 하나**(`camelCase`)가 모델 안에서 만들어 놓은 **속(Key/Value)** 을
> **반대 지침(`snake_case`)의 속**으로 갈아끼우고, 모델의 이름 선택이 반대쪽으로 **넘어가는지**를
> **층마다 · 세 가지 방식(Key만/Value만/둘다)** 으로 잰다.

- **텍스트는 한 글자도 안 바꾼다.** 화면상 프롬프트는 여전히 "camelCase로 써라"이다. 바뀌는 건 모델 내부 숫자뿐.
- 그래서 이건 **관측(상관)이 아니라 인과** 실험이다. "그 단어의 속을 바꿨더니 행동이 바뀌었다" = 그 속이 원인이다.
- 층별로 하는 이유: **어느 처리 단계에서 표기 결정이 굳는지**를 찾기 위해서.
- Key/Value로 쪼개는 이유: **"얼마나 보는가(어텐션)"와 "무엇을 실어 나르는가(내용)"를 분리**하기 위해서.
  이것이 이 논문의 핵심 주장(문제는 어텐션이 아니라 내용)을 검증하는 유일한 칼이다.

## 2. 배경 개념 — 논문에 필요한 트랜스포머 해부

이 절은 "쓰이든 안 쓰이든 반드시 알아야 하는 것"을 담는다. **우리 실험이 어디를 건드리고 어디를 안 건드리는지**를
말하려면 아래 부품 이름과 역할이 정확해야 한다.

### 2.1 토큰과 서브워드 — "단어 하나"가 사실은 조각 여럿

모델은 글자가 아니라 **토큰**(subword unit)을 본다. `camelCase`는 모델마다 다르게 쪼개진다.
실제로 우리 결과 파일의 `n_substituted_tokens`(덮어쓴 조각 수)는:

| 모델 | `camelCase` 조각 수 |
|---|---|
| Qwen2.5-Coder-3B | 2 |
| DeepSeek-Coder-6.7B | 3 |
| Llama-3.2-3B | 2 |
| StableCode-3B | 2 |

→ **모델마다 조각 수가 다르다**는 사실이 §3.4의 "평균 덮어쓰기(mean-pool)"를 강제한다.
토크나이저는 `offset_mapping`(각 토큰이 원문의 몇 번째 글자부터 몇 번째 글자까지인지)을 함께 주며,
우리는 이걸로 **"글자 위치 → 토큰 인덱스"** 변환을 한다 (`attention_probe.locate_token_spans`, `find_char_spans`).

### 2.2 잔차 스트림(residual stream) — 모델의 세로 고속도로

토큰 i는 임베딩 벡터 x_i로 시작해 층을 하나씩 통과한다. 각 층은 x를 **갈아치우지 않고 더한다**:

```
x ← x + Attention(LayerNorm(x))     # 토큰들 사이 정보 교환
x ← x + FFN(LayerNorm(x))           # 각 토큰 자리에서의 개별 가공
```

이 x의 흐름을 **잔차 스트림**이라 부른다. 마지막 층 뒤 `LM head`(선형 사영)를 거치면 어휘 크기의 **logits**가 되고,
`log_softmax`를 씌우면 로그확률이 된다. 우리가 최종적으로 읽는 숫자(§4의 S)는 여기서 나온다.

**중요한 구조적 사실:** 층 안에서 **토큰들 사이에 정보가 오가는 통로는 어텐션뿐이다.** FFN은 토큰 자리마다
독립적으로 작동해 옆 토큰을 보지 않는다. 그러므로 **"지침 단어가 뒤쪽 생성 위치에 영향을 준다"는 경로는
반드시 어텐션을 통과한다.** step5가 어텐션의 부품(K, V)을 개입 지점으로 고른 이유가 이것이다.

### 2.3 Query / Key / Value — 세 역할

각 층의 어텐션은 잔차 스트림에서 세 벡터를 만든다.

| 이름 | 만드는 식 | 직관 | 누구 것인가 |
|---|---|---|---|
| **Query (q)** | q_i = W_Q · x_i | "지금 나는 무엇을 찾는가" | **읽는 쪽**(현재 위치) |
| **Key (k)** | k_j = W_K · x_j | "나는 이런 걸 가진 자리다"(검색 태그) | **읽히는 쪽**(과거 위치) |
| **Value (v)** | v_j = W_V · x_j | "내가 실제로 전달할 내용" | **읽히는 쪽**(과거 위치) |

계산은 두 단계다.

```
(1) 얼마나 볼까:   a_ij = softmax_j ( q_i · k_j / √d )      (j ≤ i, causal mask)
(2) 무엇을 읽을까: out_i = Σ_j a_ij · v_j     →  W_O 사영 후 잔차에 더함
```

- **a_ij(어텐션 가중치)**는 q와 **k**만으로 결정된다. → **Key = "얼마나 보나"의 손잡이(축 A)**
- **v_j**는 가중치와 무관하게 **읽어오는 내용 자체**다. → **Value = "무엇이 실려 오나"의 손잡이(축 B)**
- **causal mask**: 위치 i는 자기보다 뒤(j > i)를 못 본다. 그래서 프롬프트 앞쪽에 있는 **지침 단어는
  뒤에 오는 모든 위치가 볼 수 있고**, 그 반대는 성립하지 않는다. step5가 지침 단어 한 곳만 고쳐도
  생성 시점 행동이 바뀔 수 있는 것은 이 방향성 덕분이다.

> **이 두 줄이 논문의 뼈대다.** "문제는 어텐션이 아니라 내용"이라는 주장은 곧
> **"(1)을 바꿔도 행동이 안 바뀌고 (2)를 바꾸면 바뀐다"** 는 실험 문장으로 번역된다. step5가 그 실험이다.

### 2.4 head(머리) — 같은 층 안의 여러 독립 채널

어텐션은 한 번만 하지 않는다. 층마다 `num_attention_heads`개의 **head**가 서로 다른 W_Q/W_K/W_V로
**병렬로** 위 계산을 하고, 결과를 이어 붙여 W_O로 섞는다. head마다 보는 대상이 다르다(문법 관계, 반복 패턴,
직전 토큰 복사 등). 우리는 **head를 골라내지 않고 전부 한꺼번에 치환한다** — step5의 질문이
"어느 head인가"가 아니라 "**Key 경로인가 Value 경로인가, 어느 층인가**"이기 때문이다.
(head 단위 분해는 후속 연구 여지로 §9에 남긴다.)

### 2.5 GQA — Key/Value는 head보다 적다

최신 모델은 메모리를 아끼려고 **여러 query head가 하나의 K/V를 공유**한다(Grouped Query Attention).

```
group_size = num_attention_heads / num_key_value_heads
query head h  →  KV head (h ÷ group_size) 를 사용
```

저장소 결과에서 확인된 실제 구성:

| 모델 | 층 수 | query head | KV head | group_size | 종류 |
|---|---|---|---|---|---|
| Qwen2.5-Coder-3B | 36 | 16 | 2 | 8 | GQA |
| StableCode-3B | 32 | 32 | 32 | 1 | MHA(공유 없음) |
| DeepSeek-Coder-6.7B | 32 | 실행 시 확인 | 실행 시 확인 | — | 노트북 셀 ④가 `gqa_info()` 출력 |
| Llama-3.2-3B | 28 | 실행 시 확인 | 실행 시 확인 | — | 〃 |

> 층 수는 결과 JSON의 `per_layer` 길이에서 직접 확인한 값이다. head 수는 저장된 결과에 남아 있는
> 두 모델만 표기했다 — 나머지는 노트북 셀 ④ 실행 시 `handle.gqa_info()`가 찍는다.

**왜 중요한가:** KV 캐시의 텐서 모양이 `[배치, num_key_value_heads, 토큰수, head_dim]`이다.
즉 **치환은 query head 단위가 아니라 KV group 단위로만 가능하다.** Qwen에서 KV head 하나를 덮으면
그 그룹의 **query head 8개가 동시에** 영향을 받는다. CLAUDE.md §3의 "mean-pool은 KV group 단위" 규칙은
이 하드웨어적 사실을 그대로 옮긴 것이고, 코드에서는 `_cache_kv`가 돌려주는 텐서를 그대로 슬라이싱하므로
자동으로 지켜진다.

### 2.6 FFN(MLP) — 쓰지 않지만 알아야 하는 부품

어텐션 뒤에 붙는 **FFN**(= MLP, 보통 `up_proj → 활성함수 → down_proj`, 폭은 hidden의 3~4배)은
**토큰 자리마다 독립적으로** 벡터를 가공한다. 옆 토큰을 보지 않는다. 해석 연구에서는 흔히
"사실 지식을 저장하는 곳", "key-value 메모리"로 다뤄진다.

**step5는 FFN을 직접 건드리지 않는다.** 이유와 의미를 정확히 해두면:

- 우리 질문은 "**문맥의 그 단어가 뒤로 보내는 메시지**가 행동을 바꾸는가"이다. 메시지의 통로는 어텐션(§2.2)이므로
  개입 지점도 어텐션 부품(K, V)이 맞다.
- 그 단어 자리의 K/V는 **이미 그 층까지의 FFN 처리를 다 통과한 결과물**이다. 따라서 K/V를 덮으면
  "그 단어가 그 층에서 만들어 낸 최종 메시지"를 통째로 바꾸는 것이고, 하위 FFN의 기여도 함께 대체된다.
- 다만 **읽는 쪽(뒤쪽 위치)의 FFN**은 그대로 남는다 — 이건 의도된 설계다. 우리는 "메시지를 바꾸면
  나머지 모델이 알아서 다르게 행동하는가"를 보는 것이지, 읽는 회로까지 조작하려는 게 아니다.

### 2.7 KV 캐시 — 우리 개입의 실제 무대

생성할 때 매 토큰마다 앞부분을 다시 계산하면 낭비다. 그래서 트랜스포머는 **각 층·각 위치의 K와 V를 저장**해
둔다(`past_key_values`). 새 토큰은 자기 q만 만들고 캐시된 K/V를 읽는다.

이게 step5에 주는 선물이 세 가지다.

1. **접근성** — 층별 K/V가 이미 텐서로 노출돼 있어 forward hook 없이 **직접 슬라이싱해 덮어쓸 수 있다.**
2. **정밀성** — `[층][KV head][토큰위치][차원]` 인덱싱으로 **원하는 층·원하는 단어의 위치만** 정확히 고른다.
3. **비용** — 선행 프롬프트를 **한 번만** forward해 캐시를 만들고, 층 × 방식을 바꿔가며 재사용한다
   (무료 티어 T4로 전 층 스윕이 가능한 이유).

**단, 개입의 의미가 이 구조에 의해 정확히 규정된다.** 층 L의 캐시를 덮으면, 그 단어의 **층 L+1 이상의 K/V는
원래(base) 값 그대로 남는다** — 캐시는 편집 전에 이미 다 계산됐기 때문이다. 즉 우리 개입은
**"층 L에서 그 단어가 내보내는 메시지만 반대 지침 것으로 바꾸고, 나머지 층에서는 원래 메시지를 계속 내보내는"**
매우 국소적인 조작이다. §9의 "전이가 부분적인 이유"가 여기서 나온다. 이건 결함이 아니라 **층 특정성을
얻기 위해 치른 대가**이며, 그 덕분에 "몇 번째 층"이라는 답이 의미를 갖는다.

### 2.8 RoPE — Key에만 위치가 섞여 있다

요즘 모델은 위치 정보를 **회전 위치 임베딩(RoPE)** 으로 넣는다. 구현상 **캐시에 저장되는 K는 RoPE가
적용된 뒤의 값**이고, **V에는 위치 회전이 없다.**

→ **Key 치환은 "내용 + 위치 위상"을 함께 옮기고, Value 치환은 순수하게 내용만 옮긴다.**
   이 비대칭은 "Key 치환이 효과 없었다"를 해석할 때 반드시 짚어야 한다(§9-3).
   step5 설계에서는 **두 프롬프트가 지시어 직전까지 완전히 동일**해서(§3.2) 치환 대상 단어의
   **시작 위치가 base와 donor에서 정확히 같다.** 따라서 위치 위상 불일치는 최대 1~2 토큰 수준으로 작다.

## 3. 방법론 — 무엇을 어떻게 바꿔치기하는가

### 3.1 인과 개입(activation patching)의 일반형

해석가능성 연구의 표준 도구다. 세 가지가 필요하다.

| 구성요소 | step5에서의 실체 |
|---|---|
| **base 실행** | 조건 지침(예: "camelCase로 써라")이 붙은 프롬프트 |
| **donor(반사실) 실행** | 선행 코드는 그대로, **지침만 반대**("snake_case로 써라") |
| **패치 지점** | 층 L, 지시어 단어의 토큰 위치, K/V 텐서 |

base를 돌리다가 특정 지점의 내부 값만 donor 값으로 바꿔 넣고, 출력이 donor 쪽으로 얼마나 움직이는지 본다.
**움직이면 그 지점이 그 행동의 원인 경로 위에 있다.**

step5의 변주가 표준형과 다른 점 두 가지:

- 패치 대상이 잔차 스트림(hidden state)이 아니라 **KV 캐시**다 → Key 경로와 Value 경로를 **분리**할 수 있다.
  (잔차 스트림을 패치하면 둘이 섞여서 "어텐션이냐 내용이냐"를 못 가른다. 이 논문의 주장에는 KV 분해가 필수다.)
- 패치 위치가 **지침의 지시어 단어 하나**다 → 개입 범위가 극도로 좁아 부작용이 작다.
  (step3는 문맥 코드 이름 6개를 바꾸므로 개입이 훨씬 크다. results.md가 "step5가 step3보다 깨끗하다"고
  적은 근거가 이것이다.)

### 3.2 무엇을 어디서 뽑아오는가 — K, V의 출처

세 프롬프트가 아니라 **두 프롬프트**만 forward한다(코드: `model.py:260-276`).

```python
viol_cache = self.model(viol_ids[:, :-1], use_cache=True).past_key_values   # base = 조건 지침
comp_cache = self.model(comp_ids[:, :-1], use_cache=True).past_key_values   # 반대 지침
donor_cache = comp_cache        # step5는 donor가 곧 반대 지침 캐시 (runner.py:249)
```

두 프롬프트는 **system 메시지의 규칙문 한 단어만 다르다.** 실제 렌더 결과:

```
[base]                                              [opposite = donor]
You are helping extend an existing Python module.   You are helping extend an existing Python module.
In this project we generally write function         In this project we generally write function
  names in camelCase.            ← 치환 대상           names in snake_case.        ← 공여 출처
Every function name uses one of two styles only:    Every function name uses one of two styles only:
  camelCase or snake_case.       ← 안 건드림            camelCase or snake_case.    ← 안 건드림
```

user 메시지(선행 코드 12개 + 생성 요청)는 **완전히 동일**하다 — `_preference_setup_instruction`이
`preceding_text`를 한 번 만들어 두 프롬프트에 공유한다(`runner.py:227`).

**치환 대상 위치 찾기** (`model.py:646` `_locate_target_tokens`, `span_kind="literal"`):

1. 프롬프트 문자열에서 `"camelCase"`의 **첫 등장**을 문자 구간으로 찾는다(`find_char_spans`).
2. 규칙문이 후보열거문보다 **앞에 오도록 지침을 조립**했으므로(`prompt.py:59`), 첫 등장 = 규칙문의 지시어다.
3. `offset_mapping`으로 그 문자 구간과 겹치는 토큰 인덱스를 모은다 → 이게 덮어쓸 자리.

> 후보열거문("… camelCase or snake_case")의 같은 단어는 **일부러 안 건드린다.**
> 그 문장은 두 조건에 똑같이 있는 **공통 배경**이지 지시가 아니다. 지시만 바꿔야 인과가 깨끗하다.
> 대신 이 미치환 잔여 신호가 전이율을 1.0 미만으로 누르는 요인 중 하나다(§9-1).

### 3.3 무엇을 어떻게 덮는가 — 세 방식

`_score_layer_kind`(`model.py:318`)가 층 L의 캐시 텐서를 직접 편집한다.

```python
ek, ev = _cache_kv(work_cache, layer)      # 편집 대상(base) [B, n_kv, seq, d]
dk, dv = _cache_kv(ctx["donor_cache"], layer)   # 공여(반대 지침)
```

| 방식(`kind`) | 덮는 것 | 무엇을 검증하나 | 예상 해석 |
|---|---|---|---|
| `key` | K만 | 어텐션 가중치 a_ij만 바뀜, 읽히는 내용은 base 그대로 | 크면 → "문제는 얼마나 보느냐" |
| `value` | V만 | 어텐션은 base 그대로, 읽히는 내용만 반대 지침 것 | 크면 → "문제는 무엇을 싣느냐" |
| `key_value` | 둘 다 | 그 자리를 통째로 반대 지침으로 | `value`와 같으면 → 어텐션은 잉여 |

**세 방식을 다 재는 것이 핵심이다.** `value`만 크면 부분적 증거지만, `key`가 바닥이고
`key_value ≈ value`까지 나와야 "어텐션 경로는 이 행동에 기여하지 않는다"를 말할 수 있다.

### 3.4 평균 덮어쓰기(mean-pool) — 조각 수가 달라도 되게

`camelCase`(Qwen 2조각)와 `snake_case`(3조각일 수 있음)는 조각 수가 다르다. 1:1로 짝지으면
그 조건은 통째로 버려진다(`align_name_tokens`의 `all` 모드). 그래서 CLAUDE.md §3이 **평균 덮어쓰기**로 통일했다.

```python
km = dk[:, :, dps, :].mean(dim=2)     # 공여 토큰들의 K를 평균 → [B, n_kv, d] 벡터 하나
for vp in vps:                        # 그 하나를 대상 단어의 '모든' 토큰 자리에 브로드캐스트
    bk[vp] = ek[:, :, vp, :].clone()  # 원본 백업
    ek[:, :, vp, :] = km              # 덮어쓰기
```

- **장점 1:** 토큰 수 불일치를 허용 → 모델·단어 무관하게 **스킵이 없다**(4모델 336조건 전부 유효).
- **장점 2:** 마지막 조각 하나만 바꾸는 `last` 방식보다 **단어 전체를 덮으므로 신호가 강하다.**
- **대가:** 조각별 구분(예: `camel` / `Case`)이 뭉개진 **평균 벡터**가 들어간다. 즉 "그 단어가 전달하려던
  평균적 내용"으로 대체하는 것이고, 미세한 위치별 구조는 재현하지 않는다. 코드·지침에 **동일 규칙**을
  적용하므로 step3와 step5를 나란히 비교할 수 있다.

### 3.5 편집 → 측정 → 원상복구

층 스윕은 층마다 캐시를 새로 복사하지 않는다. 하나의 `work` 캐시를 **편집 → 측정 → 백업으로 복구**하며 재사용한다.

```
for 층 L:
  for 방식 in (key, value, key_value):
      백업 = 해당 위치 원본 clone
      해당 위치 ← 공여값
      S_int 측정              (측정 함수 내부에서 캐시를 다시 복제해 쓰므로 work는 오염되지 않음)
      해당 위치 ← 백업 복원    ← 다음 층이 '깨끗한 base'에서 시작하도록
```

이 복구가 없으면 층 효과가 **누적**돼 층 특정성이 사라진다. 코드는 `bk`/`bv` 딕셔너리에 백업을 담고
측정 직후 되돌린다(`model.py:349-352`, `365-367`).

## 4. 측정 — 점수 S와 전이율

### 4.1 왜 생성하지 않고 점수를 매기나

"모델이 실제로 어떤 이름을 쓰나"를 보려면 생성을 시켜야 하지만, 생성은 (a) 느리고 (b) 이름이 다른 형태로
튀면(`clamp` 같은 한 단어) 판정 불가가 되고 (c) 미세한 선호 변화를 못 잡는다.
그래서 step3·step5는 **후보 두 개를 고정해 놓고 로그확률을 비교**한다.

- 생성 과제 1번은 `removes duplicate items from a list` → 후보는 **`removeDuplicates`** vs **`remove_duplicates`**.
- 프롬프트 뒤에 `"def "` 를 강제로 붙여(**teacher forcing**) **다음 토큰이 반드시 함수 이름**이 되게 한다.
- 각 후보 문자열의 토큰별 로그확률을 합해 그 문자열의 로그확률로 삼는다(`model.py:290-298`).

```
S = logP(지침 목표 표기 이름) − logP(반대 표기 이름)          [단위: nats]
```

> **정확한 정의 주의.** S는 "camel − snake"가 아니라 **"목표 표기 − 반대 표기"** 다
> (`runner.py:182`, `intervention.py:109`). 지침이 camel인 조건에서는 두 정의가 같지만,
> snake 조건에서는 부호가 뒤집힌 관계다. results.md의 "S = logP(camel) − logP(snake)"는
> camel 방향 조건을 두고 한 서술이며, 두 방향을 함께 평균하는 계산에서는 위 일반형이 맞다.
> (실제 데이터 확인: snake 방향 조건의 `S_base = +4.03`, `S_clean = −0.64` — 목표 표기 선호가 맞다.)

**후보 길이가 다른 것은 문제가 되지 않는다.** `removeDuplicates`와 `remove_duplicates`는 토큰 수가 달라
S의 절댓값에는 길이 편향이 섞이지만, 그 편향은 세 상태(base/opposite/개입)에 **똑같이** 들어가고
전이율은 **차이의 비**라서 상쇄된다.

### 4.2 세 상태와 전이율

| 상태 | 프롬프트 | 내부 조작 | 점수 |
|---|---|---|---|
| **base** | 조건 지침 | 없음 | `S_base` |
| **반대 지침(천장)** | 반대 지침 | 없음 | `S_clean` |
| **개입** | 조건 지침 **(텍스트 동일)** | 층 L의 지시어 KV만 반대 것으로 | `S_int` |

```
넘어감(전이율) = (S_int − S_base) / (S_clean − S_base)
```

- **0** = 개입해도 base 그대로 (그 지점은 원인이 아님)
- **1** = 반대 지침을 실제로 준 것만큼 완전히 넘어감 (그 지점만으로 충분)
- 분모가 0에 가까우면 `None` (구별 불가; `intervention.py:87`)

> step3(코드)는 "위반 → 깨끗"으로 **되돌림**, step5(지침)는 "base → 반대 지침"으로 **넘어감**.
> **부호 방향만 다르고 공식은 같은 함수**(`recovery_rate`)를 쓴다 — 두 스텝의 값을 같은 축에 놓고
> 비교할 수 있는 이유다.

### 4.3 판정불가(undecidable) 기준

**지침이 그 모델의 행동을 애초에 바꾸지 못하면, 전이율의 분모가 무의미해진다.** 그래서 노트북 셀 ⑥이
`|S_clean − S_base| < 1.0`(nats)인 묶음을 **판정불가로 분리**한다.

- 1.0 nat ≈ 두 후보의 확률비가 약 2.7배 움직이는 정도. "지침을 바꿨더니 선호가 최소 이만큼은 움직인다"는 하한선.
- CLAUDE.md §4의 "영향력이 0에 가까운 조건은 판정 불가로 분리한다"를 그대로 코드로 옮긴 것.
- 실제로 llama가 84 중 50개 판정불가로 걸러졌다 → **결과를 조건 바꿔 맞추지 않고 그대로 기록**(§6 규칙 준수).
- 이 임계값 1.0은 **사전에 정한 고정값**이며, 결과를 보고 조정하지 않았다(노트북에 상수로 박혀 있음).

## 6. 코드 흐름 — 함수 단위로 따라가기

### ① 조건 만들기 (노트북 셀 ③)

```python
Condition(
  model      = ModelSpec('Qwen/Qwen2.5-Coder-3B-Instruct', 'qwen', dtype='float16'),
  preceding  = PrecedingCode(n_compliant=6, n_functions=12,
                             composition=Composition.POOL, pool_block=b),   # 문맥 준수6+위반6
  instruction= Instruction(form=POSITIVE, target_notation=camel|snake),      # 지침 방향
  intervention=Intervention(kind=KEY_VALUE, layers='sweep',
                            target='instruction', donor='opposite'),         # ★ step5 스위치
  token_unit = 'mean',    # 평균 덮어쓰기
  seed       = 42)
```

- `layers='sweep'` → 전 층. `target='instruction'` → 코드 이름 대신 **지침 지시어**를 친다.
- `kind=KEY_VALUE`는 **조건 라벨**일 뿐이다. 스윕 경로는 실제로 `("key","value","key_value")` **세 방식을
  모두** 잰다(`runner.py:274`). 파일명에 `key_value`가 박히는 건 이 라벨 때문이다.
- 조건 수 = 지침 방향 2 × 블록 42 = **84** / 모델. 4모델 = 336개 JSON.

### ② 라우팅 (`runner.py:71` `run`)

```
mode='generate'(기본) + intervention.kind ≠ NONE → _run_intervention
                                    → is_sweep → _run_intervention_sweep      ← step5는 여기
```

### ③ 입력 구성 (`runner.py:206` `_preference_setup_instruction`)

step3용 `_preference_setup`과 **구조가 같고 두 곳만 다르다.**

```python
opp_instruction = replace(condition.instruction, target_notation=violation)  # 지침만 뒤집기
opp_condition   = replace(condition, instruction=opp_instruction)
preceding_text  = build_preceding_code(condition)      # 선행 코드는 두 프롬프트가 공유
viol_names  = [notation_word(condition.instruction.token_notation)]   # ['camelCase']  치환 대상
donor_names = [notation_word(opp_instruction.token_notation)]         # ['snake_case'] 공여
```

돌려주는 딕셔너리의 키가 `intervene_preference_sweep`의 인자와 **그대로 맞물린다** —
step3/step5가 같은 모델 메서드를 공유하는 접합부다.

### ④ 준비 (`model.py:211` `_preference_context`)

한 조건당 **딱 한 번** 실행되고, 이후 층 스윕이 그 결과를 재사용한다.

1. 두 프롬프트를 chat 템플릿 + `"def "`로 렌더 → 토크나이즈(offset 포함)
2. `prefix[:-1]`을 forward → `viol_cache`, `comp_cache` 확보 (마지막 토큰은 채점 forward에 넣는다)
3. 후보 두 이름을 토크나이즈
4. 치환 위치 찾기 → `token_unit='mean'`이므로 `align_name_groups`로 (대상 위치들, 공여 위치들) 묶음
5. 채점 함수 `S(cache, last_tok)` 정의, `S_base`·`S_clean` 계산

### ⑤ 층 스윕 (`model.py:415` → `model.py:318`)

```
work = viol_cache의 깊은 복사
for L in 0..마지막:
    for kind in (key, value, key_value):
        s_int = _score_layer_kind(ctx, work, L, kind)     # 편집→측정→복구
        per_layer[L][kind] = {S_int, recovery}
```

**한 조건의 forward 횟수** (층 수 L, 후보 2개):

```
선행 2회  +  채점 2×(2 + 3L)회
Qwen(L=36) → 2 + 2×110 = 222회
```

채점 forward 자체는 토큰 몇 개짜리라 싸지만, 매번 **캐시 깊은 복사**가 일어난다.
캐시 크기 ≈ `층수 × 2 × KV head × 토큰수 × head_dim × 2바이트`.
→ KV head가 32개인 MHA 모델(deepseek 6.7B 등)은 GQA 모델보다 캐시가 훨씬 커서
**노트북이 deepseek에 8bit 옵션을 안내하는 이유**가 된다.

### ⑥ 결과 담기 (`runner.py:279-304`)

```json

        "value__S_int": -4.375, "value__recovery": 0.842,
```

## 7. step3(코드 인과)와의 차이 — 스위치 두 개

같은 엔진, 같은 공식. **딱 두 곳만 다르다.**

| | step3 (코드 인과) | step5 (지침 인과) |

## 9. 정직하게 남는 것 — 방법론적 한계

1. **전이가 부분적인 구조적 이유.** §2.7에서 본 대로 층 L의 캐시만 덮으므로 그 단어는 **다른 모든 층에서
   여전히 원래 메시지를 내보낸다.** 또 후보열거문의 같은 단어는 미치환이다(§3.2). 따라서 전이율 1.0은
   애초에 기대 대상이 아니며, **층 간 상대 비교(어느 층이 봉우리인가)와 방식 간 비교(value vs key)** 가
   이 실험이 지지할 수 있는 결론이다.
2. **평균 덮어쓰기의 성격.** 조각별 구조를 평균으로 뭉갠다(§3.4). 신호를 강하게 만들고 모델 간 비교를
   가능하게 하는 대신, "그 단어가 만든 표현을 정확히 복제"하는 것은 아니다.
3. **Key 치환의 위치 위상 문제(§2.8).** 캐시된 K는 RoPE 적용 후 값이라 위치 정보가 섞여 있다.
   step5는 두 프롬프트가 지시어 직전까지 동일해 시작 위치가 일치하므로 영향이 작지만,
   "key ≈ 0"을 **"어텐션 경로는 원인이 아니다"** 로 읽을 때는 이 가능성을 각주로 남기는 편이 안전하다.
   보강 근거는 step4(관측): 어텐션은 **이미 충분히** 지시어에 가 있었다 — 즉 늘릴 여지가 적다.
4. **head 단위 분해 없음.** KV group 단위로 전부 치환한다(§2.4~2.5). "어느 head가 표기를 나르는가"는
   이 실험이 답하지 않는다(후속 여지).
5. **fp16 정밀도.** 캐시 편집·평균이 반정밀도에서 일어난다. 층별 상대 비교에는 충분하지만
   미세 차의 절댓값은 정밀도 잡음을 포함한다.
6. **llama 판정불가.** 84 중 50개가 임계 미달 → RQ3 결론은 **코드 전용 3모델에 한정**된다.
7. **후보 2개로 닫은 채점.** 실제 생성에서 모델이 제3의 이름(한 단어 등)을 쓸 가능성은 이 지표에 안 잡힌다.
   step1(생성)이 그 축을 담당한다.

## 12. 한 장 요약

- **개입 지점:** 층 L의 KV 캐시, 지침 지시어 단어의 토큰 자리, KV group 단위.
- **개입 방식:** 반대 지침 프롬프트에서 같은 단어의 K/V를 평균 내 덮어쓰기. Key만 / Value만 / 둘다.
- **읽는 값:** 고정 후보 두 이름의 로그확률 차 S. 세 상태(base / 반대 지침 / 개입)로 전이율.
- **안 건드리는 것:** 텍스트, Query, FFN, 다른 층, 후보열거문의 같은 단어, 읽는 쪽 회로.
- **그래서 말할 수 있는 것:** *"지침의 영향은 그 단어가 후반 특정 층에서 내보내는 **내용(Value)** 을 타고 간다.
  어텐션(Key)을 바꿔도 행동은 거의 안 넘어간다."* → 어텐션 증폭 접근(Spotlight)은 부품을 잘못 겨눴다.
- **다음(step6):** 여기서 특정한 **그 층의 Value**에 조향 벡터를 더해(CAA) 준수율을 실제로 올린다.
