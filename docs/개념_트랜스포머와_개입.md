# 공통 개념 — 트랜스포머 구조와 우리가 건드리는 곳

> 모든 스텝이 공유하는 배경. 스텝별 문서(`docs/step<N>/방법론.md`)는 이 문서를 전제로 쓴다.
> **목표:** 이 문서만 읽으면 "우리가 모델의 **어디를** 만졌는지"를 그림으로 떠올릴 수 있게 한다.

## 0. 용어 — 먼저 읽는다

문서·코드·결과 JSON에서 계속 나오는 말들이다. **여기서 정의하고, 다른 곳에서는 쓰기만 한다.**

### 0-1. 실험 자극

| 말 | 뜻 |
|---|---|
| **선행 코드** | 모델에게 먼저 보여주는 함수 12개. "이미 있는 모듈" 역할 |
| **묶음**(block) | 이름 12개 한 세트. 504개를 12개씩 나눠 **42묶음**. 한 조건이 한 묶음을 쓴다 |
| **준수 / 위반** | 지침이 요구한 표기를 따르면 준수, 어기면 위반. 지침이 camel이면 snake가 위반 |
| **절벽**(cliff) | 위반 개수를 늘릴수록 준수율이 떨어지다 **어느 지점에서 0으로 무너지는 현상** |
| **절벽 바닥** | 그 무너진 상태(위반 12/12). step6의 출발점 |

### 0-2. 관측

| 말 | 뜻 |
|---|---|
| **토큰 / 자리** | 모델이 읽는 글자 덩어리. 프롬프트 하나가 185칸이 되는 식(→ §1-1) |
| **offset** | "원문 몇 번째 글자"를 "몇 번째 토큰"으로 옮기는 대응표(→ §1-1) |
| **구간**(span) | 프롬프트에서 **함께 묶어 재는 토큰 자리들**. 예: "camel 이름 6개의 이름 토큰" |
| **강제 접두** | 프롬프트 끝에 `"def "`를 붙여 **다음이 함수 이름 자리**가 되게 만드는 것 |
| **교사강제**(teacher forcing) | 모델이 고른 것을 쓰지 않고 **우리가 정한 다음 조각을 강제로 입력에 넣어** 그 확률을 읽는 것(→ §6) |
| **봉우리 층**(peak layer) | 그 지표가 가장 큰 층. "신호가 어디에 모이나"의 답 |
| **스윕**(sweep) | 층을 0부터 끝까지 **하나씩 훑는 것** |

### 0-3. 개입 — ★ 여기가 가장 헷갈린다

**개입**이란 텍스트는 그대로 두고 **모델 속 값만 몰래 바꿔치기**하는 것이다.
바꿔치기하려면 **어디서 가져올지**를 정해야 하는데, 그 출처를 **공여**라 부른다.

> **공여(donor)** = 덮어넣을 값을 **어디서 떠 왔는가**

```
위반 이름 format_matrix 의 내부 값을  ⟵ 덮는다
                    ↑
        무엇으로?  ← 이것이 공여
```

**코드에 개입할 때**(step3) 쓰는 공여 3종:

| 코드 이름 | 우리말 | 무엇을 떠 오나 | 왜 쓰나 |
|---|---|---|---|
| `compliant` | **같은 이름 준수판** | `format_matrix` → 같은 이름의 camel판 `formatMatrix` | **처치**. 표기만 바꾼 값 |
| `unrelated_camel` | **무관한 camel 이름** | 전혀 다른 이름의 camel판 (`parseHeader` 등) | "camel이면 아무거나 되나" |
| `unrelated_snake` | **무관한 snake 이름** | 전혀 다른 이름의 snake판 | **통제**. 표기 정보가 안 들어간다 |

**지침에 개입할 때**(step5) 쓰는 공여 3종:

| 코드 이름 | 우리말 | 무엇을 떠 오나 | 왜 쓰나 |
|---|---|---|---|
| `opposite` | **반대 지침** | 지침을 뒤집은 프롬프트의 `snake_case` | **처치** |
| `self` | **자기 통제** | **같은 지침의 같은 단어** `camelCase` | 새 정보가 0인 조건 |
| `unrelated_word` | **음성 통제** | 지침 속 무관한 단어 `project` | 표기와 상관없는 내용 |

### 0-4. 처치 · 통제 · 거품 · 순효과

| 말 | 뜻 |
|---|---|
| **처치**(treatment) | 우리가 검증하려는 진짜 개입. 표기 정보가 담긴 값을 덮는다 |
| **통제**(control) | **정보는 안 넣고 덮기만 하는** 비교 조건 |
| **거품**(bubble) | 통제에서 나오는 값. **"덮어쓰는 행위 자체"가 만든 가짜 효과** |
| **순효과**(net effect) | **처치 − 통제**. 거품을 걷어낸 진짜 몫 ← 논문에 쓰는 값 |

**왜 거품이 생기나** — 값을 덮으면 새 정보가 들어가는 **동시에 원래 있던 표현이 지워진다.**
게다가 우리는 조각들을 평균 내어 덮으므로 단어 내부 구조도 뭉갠다. 그래서 **아무 의미 없는
값으로 덮어도 점수가 움직인다.** 그 움직임이 거품이다.

```
처치(같은 이름 준수판)     0.536  ┐
                                 ├─ 차이 0.253 = 순효과 ← 표기 때문에 생긴 몫
통제(무관한 snake 이름)    0.261  ┘   (실제로는 다른camel − 다른snake로 계산)
                            └─ 이만큼은 무엇을 덮든 나온다 = 거품
```

step3에서 **거품이 원값의 절반 이상**이었다. 통제 없이 잰 값은 **상한**이다.

### 0-5. 재는 값

| 말 | 뜻 |
|---|---|
| **준수율** | 모델이 새로 쓴 이름이 지침 표기를 따른 비율 (0~1) |
| **선호 점수 S** | 후보 두 이름 중 어느 쪽을 더 좋아하는지 (§6). 양수면 지침대로 |
| **되돌림 정도 / 전이율**(recovery) | 개입으로 행동이 목표까지 **얼마나 돌아왔나**. 1 = 완전 회복 |
| **영향력**(effect size) | 문맥·지침이 애초에 행동을 **흔든 정도**. 되돌림의 분모 |
| **판정 불가**(undecidable) | 영향력이 너무 작아(< 1.0) 되돌림을 해석할 수 없는 조건 |

> **되돌림의 분모가 영향력**이다. 문맥을 바꿔도 모델이 안 흔들리는 조건에서는
> 분모가 0에 가까워 비율이 잡음이 된다. 그런 조건은 **빼고** 본다.

## 1. 모델이 글을 읽는 과정

```
   "def split_config(value):"
              │
              ▼  토큰으로 쪼갬
   ["def", " split", "_", "config", "(", "value", "):"]
              │
              ▼  각 토큰 → 숫자 벡터 (임베딩)
   ┌──────────────────────────────────────────┐
   │  층 0   ──▶ 층 1 ──▶ … ──▶ 층 L ──▶ …    │   ← 층을 하나씩 통과
   └──────────────────────────────────────────┘
              │
              ▼
        다음 토큰 확률
```

층을 통과할 때마다 각 토큰 자리의 벡터가 조금씩 바뀐다. 이 **자리마다 하나씩 있는 벡터**를
**잔차(residual)** 라고 부른다. 층은 잔차를 "덮어쓰지" 않고 **더한다**.

```
   잔차_다음층 = 잔차_이번층 + (이번 층이 계산한 것)
```

→ **앞쪽 층에서 더한 것이 뒤까지 그대로 전달된다.** (step6에서 "엉뚱한 층에 밀어도 되는" 이유)

## 1-1. 원문 → 토큰 → 자리 번호 — offset이 하는 일

관측(step2·step4)의 절차를 읽으면 "offset으로 토큰 번호를 찾는다"가 나온다. 그게 무슨 말인지
**Qwen·블록 0 실측값**으로 짚는다. 아래 토큰 번호는 결과 파일 `extra.token_detail`에
그대로 저장돼 있는 값이다.

### ① 원문 — 그냥 긴 글자 문자열 하나

프롬프트 전체는 사람이 보는 그대로의 **글자 덩어리**다. 우리가 찾고 싶은 이름이
그 안 어디에 있는지는 **글자 번호**로 안다.

```
   글자번호  ... 227      231           243 ...
   원문      ... def      split_config  (value): ...
                          └──이 이름──┘
```

정규식으로 `def <이름>(` 을 찾아 앞 4자와 뒤 1자를 깎으면 **231~243글자**가 나온다.

### ② 토큰 — 모델은 글자가 아니라 덩어리를 읽는다

모델은 글자 단위로 읽지 않는다. 자주 붙어 다니는 글자 뭉치를 하나로 본다.

```
   split_config  →  [" split"] ["_config"]      2조각
   decodeNode    →  [" decode"] ["Node"]        2조각
```

프롬프트 전체가 이렇게 쪼개지면 **총 185조각**이다(`extra.seq_len = 185`).
모델 입장에서 이 프롬프트는 **185칸짜리 한 줄**이다.

```
   칸번호   0     1    ...  55        56        ...  64         65      ...  184
   내용   <시작>  You        " split"  "_config"      " decode"  "Node"       마지막 칸
```

### ③ offset — 글자 번호와 칸 번호를 잇는 대응표

여기가 핵심이다. 우리는 이름의 위치를 **글자로** 안다(231~243).
그런데 어텐션은 **칸 번호로만** 나온다. 둘을 이어야 한다.

토큰화할 때 조각마다 "**이 조각이 원문 몇 번째 글자에서 몇 번째까지냐**"를 함께 받는다.
그게 **offset**이다(HuggingFace의 `return_offsets_mapping=True`).

| 칸 번호 | 조각 | offset (글자 범위) |
|---|---|---|
| 55 | `" split"` | 230~236 |
| 56 | `"_config"` | 236~243 |

→ **"231~243글자"** 를 **"55번·56번 칸"** 으로 번역할 수 있다. 이것이 구간 확정이다.

이렇게 해서 실제로 저장된 구간이 이것이다:

```
   code_snake = 55, 56, 82, 83, 91, 92, 100, 101, 109, 110, 154, 155   ← 12칸
   code_camel = 64, 65, 73, 74, 118, 119, 127, 128, 136, 137, 145, 146 ← 12칸
```

| 말 | 가리키는 것 |
|---|---|
| **원문** | 프롬프트 전체 글자 문자열 |
| **토큰 / 자리 / 칸** | 모델이 읽는 덩어리. 이 프롬프트는 185칸 |
| **offset** | "몇 번째 글자"를 "몇 번째 칸"으로 옮기는 대응표 |
| **전체위치** | 185칸 전부 |
| **구간**(span) | 그중 우리가 고른 12칸 |

> **왜 굳이 이 번거로운 짓을 하나.** 모델마다 토크나이저가 달라서 같은 이름이 2조각이 되기도
> 3조각이 되기도 한다(DeepSeek·StableCode). **글자 위치는 모델과 무관하게 똑같으므로**,
> 글자로 먼저 찾고 offset으로 옮기면 4모델에 같은 규격을 적용할 수 있다.
> 결과 파일의 `token_detail`은 이 번역이 제대로 됐는지 **눈으로 검산하라고** 남긴 것이다.

> 위 글자 번호는 chat 템플릿을 씌우기 전 기준이라 실제 실행에서는 앞쪽으로 조금 밀린다.
> **토큰 번호가 실측값**이고, 밀리든 말든 offset이 같이 밀리므로 대응은 항상 맞는다.

## 2. 어텐션 — 어디를 보고 무엇을 가져오나

새 토큰을 쓸 때, 모델은 **앞의 모든 토큰을 둘러본다.** 이때 자리마다 세 가지를 만든다.

| 이름 | 무엇인가 | 비유 |
|---|---|---|
| **Query (Q)** | 지금 자리가 "무엇을 찾는지" | 검색어 |
| **Key (K)** | 각 자리가 "무엇에 관한 것인지" 알리는 꼬리표 | 색인 |
| **Value (V)** | 각 자리가 실제로 **가진 내용** | 본문 |

계산은 두 단계다.

```
① 얼마나 볼지 정하기        a = softmax( Q · Kᵀ / √d )      ← 비중, 합이 1
② 본 만큼 내용을 가져오기    출력 = Σ_j  a_j · V_j
```

### 2-1. 한 자리가 둘러보는 것 = **한 줄(행)**

프롬프트가 토큰 185개라 하자. 마지막 자리(`def ▮`)가 앞을 둘러본다.

```
마지막 자리의 query q ──┬── "You"의 key와 점수 → 2.1
                       ├── "are"의 key       → 0.4
                       ├── …
                       └── "config"의 key    → 5.7      (185개)
                             ↓ softmax
                    [0.003, 0.001, …, 0.013]   ← 185개 숫자, **합 = 1**
```

**이 185개 숫자 한 벌이 "한 행"이다.** query 하나가 모든 key를 훑어 만든 비중표.

**합이 1이라는 것이 결정적이다** — 구간 값이 곧 **비중**이 된다.
`code_snake = 0.16`은 "그 순간 모델 주의의 **16%**가 snake 이름 토큰들에 갔다"는 뜻이다.

### 2-2. 모든 자리가 각자 하면 = **행렬**

185개 자리가 **각자** 한 줄씩 만든다 → `[185 × 185]` 행렬.

```
             ← 열: 무엇을 보나 (key 쪽) →
             You   are   …   config   def
      You  [ 1.0    —    —     —       — ]   ← 1번째 자리가 본 것
 행   are  [ 0.6   0.4   —     —       — ]      (미래는 못 본다 = 인과 마스크)
누가   …   [  …     …    …     —       — ]
보나  def  [0.003 0.001  …   0.013   0.02]   ← ★ 우리가 쓰는 줄
```

- **행 = 누가 보나**(query 쪽) · **열 = 무엇을 보나**(key 쪽)
- 오른쪽 위 삼각형이 빈 것은 **미래 토큰을 못 보기 때문**(인과 마스크)

**우리는 마지막 행 하나만 쓴다.** 나머지 184줄은 다른 토큰이 쓰이던 순간이라
"이름을 어떻게 정하나"와 무관하다.

> step6에서 잡은 버그가 이 삼각형이었다. Spotlight를 재구현하며 마스크를 안 씌워
> **미래까지 보는 모델**을 재고 있었다(→ `step6/code.md` §4-3).

### 2-3. head — 같은 일을 **여러 벌 동시에**

위 과정을 한 번만 하는 게 아니다. Qwen의 토큰 벡터는 2048차원인데,
이를 **16조각(128차원씩)으로 쪼개** 각 조각이 자기 q·k·v와 **자기 행렬**을 만든다.

```
토큰 벡터 2048차원
   ├─ 헤드 0  (128차원) → 자기 q,k,v → 자기 [185×185] → 마지막 행 [합 1]
   ├─ 헤드 1  (128차원) → …                            → 마지막 행 [합 1]
   ├─ …
   └─ 헤드 15 (128차원) → …                            → 마지막 행 [합 1]
                                                   ↓ 16개 평균
                                                [합 1]  ← 우리가 쓰는 값
```

**왜 쪼개나** — 헤드마다 보는 것이 다르다. 바로 앞 토큰만 보는 헤드, 문법 짝(괄호·따옴표)을
보는 헤드, 반복 패턴을 보는 헤드… 한 벌로는 그 다양한 관계를 한 번에 담지 못한다.

**16개를 평균 내도 합은 1**이라 비중의 의미가 유지된다.
헤드별 분해("어느 헤드가 범인인가")는 이 연구의 범위 밖이다.

### 2-4. 값이 나오는 경로 — 한눈에

```
185자리 × 16헤드 = 16장의 [185×185] 행렬
        ↓ 마지막 행만
16개 × 185개 숫자 (각 줄 합 1)
        ↓ 헤드 평균
185개 숫자 (합 1)
        ↓ camel 이름 토큰 12개의 열만 더함
0.1144  ← "그 순간 주의의 11.4%가 camel 이름들에 갔다"
        ↓ 구간 토큰 수로 나눔
0.0095  ← "토큰 하나가 받은 몫"   ← 논문에 쓰는 값
```

> **Q헤드와 KV헤드 수가 다를 수 있다**(Qwen 16 vs 2). 어텐션과 `‖v‖`를 곱할 때
> `h ÷ group_size`로 짝을 맞춰야 하며, 틀리면 **에러 없이** 잘못된 값이 나온다 → §4-2.

**이 연구의 핵심 질문이 바로 여기서 나온다.**

```
   표기 규약 정보는  ①(얼마나 보나 = K)에 있나,  ②(무엇을 읽나 = V)에 있나?
```

- K를 바꾸면 → **어디를 얼마나 볼지**가 바뀐다
- V를 바꾸면 → **거기서 무엇을 가져올지**가 바뀐다

우리는 이 둘을 **따로 바꿔치기**해서 어느 쪽에 정보가 실려 있는지 가른다.

## 3. KV 캐시 — 우리가 실제로 편집하는 자료구조

이미 읽은 토큰의 K와 V는 매번 다시 계산하지 않고 저장해 둔다. 이것이 **KV 캐시**다.

```
KV 캐시  (층마다 하나씩)
┌─────────────────────────────────────────────┐
│ 층 L                                         │
│   K:  [B, 헤드수, 토큰수, 차원]              │
│   V:  [B, 헤드수, 토큰수, 차원]              │
└─────────────────────────────────────────────┘
              ▲
              └── step3·step5는 여기를 직접 덮어쓴다
```

**우리 개입의 정체:** 화면의 글자는 그대로 두고, **캐시 안 특정 자리의 K 또는 V만 다른 값으로 바꾼다.**
그러고 나서 모델의 출력이 어떻게 달라지는지 본다.

---

## 4. 두 가지 함정 (실제로 겪었다)

### 4-1. RoPE — Key에는 위치가 박혀 있다

**Key에는 "그 토큰이 문장 몇 번째였는지"가 회전 형태로 이미 적용돼 캐시에 들어간다.**
Value에는 그런 것이 없다.

```
   K_p  =  회전(p) · (원래 키)        ← p번째 자리라는 정보가 섞여 있다
   V_p  =  (원래 값)                  ← 위치 정보 없음
```

그래서 **다른 위치의 K를 가져다 넣으면 위치가 어긋난 값**이 들어가고,
**여러 위치의 K를 평균 내면 회전이 엇갈려 서로 지워질** 수 있다.

→ "K를 바꿔도 안 되네"가 **K 경로의 성질**인지 **우리가 K를 망가뜨린 탓**인지 구분해야 한다.
이걸 잰 것이 **진단 실험 A**(`docs/diag/results.md`)이고, **문제없음**으로 판정났다.

### 4-2. GQA — K/V는 여러 헤드가 나눠 쓴다

최신 모델은 Q 헤드는 많고 K/V 헤드는 적다(Grouped Query Attention).

```
   Q 헤드:  □ □ □ □   □ □ □ □
              ╲ ╲ ╱ ╱     ╲ ╲ ╱ ╱
   KV 헤드:     ■           ■        ← 하나를 여러 Q가 공유
```

**따라서 K/V를 바꿀 때는 KV 헤드 단위로 통째로** 바꿔야 한다. 한 Q 헤드만 노릴 수 없다.
(모델마다 그룹 구성이 다르므로 `handle.gqa_info()`로 매번 확인한다.)

## 5. 개입의 두 방식

이 연구는 서로 다른 두 가지 방법으로 모델을 건드린다.

### 방식 A — KV 캐시 덮어쓰기 (step3·step5)

```
   프롬프트를 한 번 통과시켜 캐시를 얻는다
              │
              ▼
   층 L의 특정 자리 K(또는 V)를 **다른 프롬프트의 값**으로 교체
              │
              ▼
   출력이 어떻게 달라졌나 측정  →  원상복구  →  다음 층으로
```

- **어디서 가져오나(공여)** 를 바꿔가며 통제를 세운다
- 여러 조각을 평균 내어 넣는다(**평균 덮어쓰기**) — 토크나이저가 달라도 쓸 수 있다

### 방식 B — forward 훅 (step6)

```
   층 L의 출력 잔차에  세기 × 방향벡터  를 **더한다**
```

- 정답 프롬프트가 필요 없다. 방향 하나만 있으면 어디든 걸 수 있다 → **처방**
- Spotlight는 어텐션 함수 자체를 갈아끼워 **비중 a를 재조정**한다

## 6. 우리가 재는 값

### 먼저 — logP가 무엇인가

모델은 다음 토큰을 **확률**로 답한다. 그런데 이름은 토큰 여러 개라 확률을 **곱해야** 한다.

```
P("removeDuplicates") = P(" remove") × P("Duplicates")
                      = 0.31 × 0.02  =  0.0062
```

토큰이 늘수록 곱이 쌓여 아주 작은 수가 되고 컴퓨터에서 0으로 뭉개진다(언더플로).
**로그를 씌우면 곱셈이 덧셈**이 되어 이 문제가 사라진다.

```
logP("removeDuplicates") = log(0.31) + log(0.02)
                         = −1.17    +  −3.91    =  −5.08
```

> 조각이 2개인 것은 **Qwen 기준**이다(결과 파일의 실측 분해가 `" decode"`+`"Node"`,
> `" split"`+`"_config"`처럼 2조각이다). DeepSeek·StableCode는 밑줄을 따로 떼어 3~4조각이
> 된다. 위 확률 숫자는 자릿수 감을 주기 위한 예시다 — **조각별 확률은 저장하지 않는다.
> 저장되는 것은 합인 `logP`와 그 차이인 `S`뿐이다.**

**값 읽는 법 — 항상 음수다**(확률이 1 이하이므로). **0에 가까울수록 좋아한다.**

| logP | 확률 | 뜻 |
|---|---|---|
| −0.1 | 0.90 | 거의 확실히 이걸 쓴다 |
| −2 | 0.14 | 그럭저럭 |
| −7 | 0.001 | 거의 안 쓴다 |

### 준수 선호 점수 S

생성을 시키지 않고, 후보 두 개를 **강제로 놓고 채점**한다(교사강제).

```
   프롬프트 + "def " 뒤에 후보를 붙여 확률을 잰다

   log P(이름) = Σ_k log p(토큰_k | 앞의 모든 토큰)

   S = log P(지침 목표 표기) − log P(반대 표기)
```

**로그끼리 빼면 원래 확률의 비율**이 된다 — 이것이 S를 쓰는 이유다.

```
S = log( P(목표 표기) / P(반대 표기) )
```

| S | 뜻 |
|---|---|
| **양수** | 지침을 따르는 쪽을 선호 |
| 0 | 딱 반반 |
| **음수** | 어기는 쪽을 선호 |

**단위는 nat**(자연로그)다. 크기도 의미가 있다 — **S=1이면 약 2.7배, S=2면 약 7.4배** 선호.

실제 값(Qwen, camel 지침. 42묶음 평균 — 결과 파일에서 다시 집계한 값이다):

| 문맥 | S_깨끗 (12개 전부 준수) | S_기준 (그 조건) | 차이 = 분모 |
|---|---|---|---|
| **위반 6/12** (step3·step5) | 3.69 → 목표 표기를 **40배** 선호 | **+0.08** → 거의 반반 | 3.60 |
| **위반 12/12** (step6 절벽 바닥) | 3.69 → 같음 | **−2.33** → 반대 표기를 **10배** 선호 ← 뒤집혔다 | 6.02 |

**`S_깨끗`은 두 줄이 같다** — 깨끗한 문맥은 위반 개수와 무관하게 같은 프롬프트이기 때문이다.
움직이는 것은 `S_기준`뿐이고, 그 차이가 **문맥이 행동을 흔든 정도**(회복률의 분모)다.

**왜 생성 대신 이걸 쓰나** — 생성은 이산적이라 개입을 걸어도 나오는 이름이 안 바뀌면
"효과 0"으로만 보인다. 로그 확률은 **0.001 차이도 잡는다.** 생성의 무작위성도 없앤다.

> ⚠️ **주의 1 — 부호 규약.** `logP(camel) − logP(snake)`가 **아니다.** 목표 표기 기준이므로
> snake 지침 조건에서는 부호 관계가 뒤집힌다.
>
> ⚠️ **주의 2 — 길이 정규화를 하지 않는다.** `removeDuplicates`(2조각)와
> `remove_duplicates`(3조각)는 더하는 항의 수가 다르므로 조각이 많은 쪽이 자연히 낮아진다.
> 그래서 **S의 절대값을 모델끼리 비교하면 안 되고**, 같은 조건 안의 **차이(회복률)** 만 쓴다.

### 교사강제 — "강제로 놓고 채점"이 기계적으로 무슨 일인가

**teacher forcing의 teacher는 정답을 쥔 사람이다.** 모델이 무엇을 고르든 무시하고,
**우리가 준비한 다음 조각을 강제로 입력에 넣는다.** 모델은 자리마다 "나라면 뭘 썼을까"를
여전히 계산하지만, 그 답이 다음 입력이 되지는 않는다.

#### 보통 생성과 무엇이 다른가

```
[생성]  모델이 고른 것을 다시 입력에 붙인다
        ...def ▮ → 모델이 " remove" 선택 → ...def remove ▮ → 모델이 "_duplicates" 선택 → 끝
        알 수 있는 것: "안 지켰다"(0).  알 수 없는 것: 아슬아슬했나, 압도적이었나

[교사강제]  우리가 정한 것을 붙인다
        ...def ▮        에서 " remove"의 확률을 읽고  →  " remove"를 **넣는다**
        ...def remove ▮ 에서 "Duplicates"의 확률을 읽고  →  거기서 멈춘다
        모델이 "_duplicates"를 원했더라도 **camel을 얼마나 싫어했는지가 숫자로 나온다**
```

#### 한 후보를 채점하는 절차

```
   후보 A: removeDuplicates → [" remove"] ["Duplicates"]

   자리 1:  ...def ▮                → log P(" remove")     읽고 → " remove"를 넣는다
   자리 2:  ...def remove ▮         → log P("Duplicates")  읽는다
                                      ─────────────────────────
                                      logP(A) = 두 값의 합
```

코드는 이 두 줄이다(`model.py:322 logp_candidate`):

```python
inp = torch.cat([last_tok, cand[:-1].unsqueeze(0)], dim=1)   # 후보를 입력에 통째로 넣고
...
return float(sum(lp[k, cand[k]].item() for k in range(cand.shape[0])))  # 후보 조각의 칸만 읽는다
```

`cand[:-1]`을 **입력**에 밀어 넣고 `cand[k]`의 확률을 **읽는다.** 모델이 고른 것을 쓰는 게
아니라 우리가 정한 것을 넣고 그 확률을 받아내는 것 — 이것이 "강제"다.

#### 확률표는 통째로 나오는데 한 칸만 읽는다

각 자리의 출력은 **어휘 전체(15만 개)에 대한 확률표**다. 우리는 그중 **후보 조각의 칸 하나만**
읽고 나머지는 버린다. 그래서 두 후보를 재려면 **각각 한 번씩, 총 두 번 통과**시킨다.

```python
def S(cache, last_tok):
    return preference_score(logp_candidate(cache, last_tok, cc),   # forward 1회 (준수 후보)
                            logp_candidate(cache, last_tok, cv))   # forward 1회 (위반 후보)
```

#### 그래도 싼 이유 — 긴 forward는 세 번뿐

| 무엇 | 몇 번 | 길이 |
|---|---|---|
| 긴 프롬프트 forward | **3번**(위반·깨끗·공여). 맨 처음 한 번만 | 185토큰 |
| 채점 forward | 36층 × 3방식 × 2후보 = **216번** | **2~4토큰** |

캐시를 만들어 두고 층마다 **일부만 덮었다 되돌리므로**(§5 방식 A), 216번은 전부 짧다.
전 층 스윕이 무료 티어에서 도는 이유가 이 구조다.

#### 자리 2가 사실상 S를 결정한다

두 후보는 **첫 조각이 같다**(`" remove"`). 앞 프롬프트도 글자 하나 안 틀리고 같으니
자리 1의 값도 **완전히 같고, 빼면 사라진다.**

```
             자리 1              자리 2
   후보 A:  logP(" remove")  +  logP("Duplicates")
   후보 B:  logP(" remove")  +  logP("_duplicates")
            └─ 같다 → 상쇄 ─┘
```

> **S ≈ log P("Duplicates" | …def remove) − log P("_duplicates" | …def remove)**

이건 정확히 우리가 묻고 싶은 것이다 — ***"`remove`까지 썼다. 대문자로 붙일래, 밑줄 치고 갈래?"***
**표기를 정하는 순간 그 자체**이고, 다른 것은 섞여 있지 않다.

*(Qwen·Llama는 첫 조각이 같아 깔끔하게 성립한다. DeepSeek·StableCode는 3~4조각으로
쪼개져 완전히 상쇄되지는 않지만, 공통 접두가 크게 겹치는 것은 마찬가지다.)*

#### 공짜가 아니다 — 실제로 물렸다

교사강제 점수는 **실제 생성을 대변하지 않는다.** S는 오직 *"이 둘 중 뭐가 나은가"* 만 묻는다.
**모델이 셋째 선택지로 도망가는 것은 이 자가 아예 못 본다.**

| step6 · Qwen · 조향 세기 4 | 값 |
|---|---|
| 점수 회복률 | **1.733** (최고) |
| 실제 준수율 | **0.000** |
| 나온 이름 | `RemoveDuplicates` ← camel도 snake도 아니다 |

그래서 step6은 **생성 검증(`steer_generate`)을 따로 돌린다.**
점수로 고른 처방이 실제로도 통하는지는 **반드시 생성으로 확인해야 한다.**

### 회복률 (되돌림 정도)

```
              S_개입 − S_기준
   R  =  ──────────────────────
              S_깨끗 − S_기준
```

- **0** = 개입해도 그대로
- **1** = 오염이 없는 상태(천장)까지 완전 회복
- **1 초과** = 천장을 지나쳤다. **위가 막혀 있지 않다** — step6에서 문제가 됐다

### 영향력과 판정 불가

> 임계 1.0의 단위도 **nat**이다 — "문맥·지침을 바꿔도 선호가 2.7배도 안 움직였으면
> 흔들리지 않은 것으로 본다"는 뜻이다.

```
   gap = |S_깨끗 − S_기준|          분모의 크기
   판정 불가  ⟺  gap < 1.0
```

분모가 작으면 비율이 폭주하므로 분석에서 뺀다. 이 값은 결과 파일에 함께 저장된다.

### 거품과 순효과

**덮어쓰기는 두 가지 일을 동시에 한다.**

```
   ① 원래 있던 것을 지운다      ← 이것만으로도 점수가 움직인다 (거품)
   ② 새로운 것을 넣는다         ← 우리가 알고 싶은 것
```

그래서 **통제**를 함께 돌린다 — 정보가 안 들어가는 값을 덮어보고, 그때 나온 값을 뺀다.

```
   순효과 = 처치 − 통제
```

step3에서 이 거품이 회복률의 **절반 이상**이었다. **통제를 안 뺀 값은 상한으로만 읽어야 한다.**

| 진단 A | `kv_diagnose` | 덮어쓰기가 K를 망가뜨리나 | 방법 점검 |

## 8. 하네스 구조

**모든 실험이 함수 하나를 통과한다.** RQ별로 스크립트를 나누지 않는다.

```
   Condition(조건 객체)  ──▶  run(condition, mode=...)  ──▶  RunOutput
        │                            │
        │                            ├─ generate          → 생성 후 표기 측정
        │                            ├─ observe           → 구간별 참조량
        │                            ├─ steer             → 처방
        │                            └─ kv_diagnose       → 방법 진단
        │
        └─ 모델 · 선행코드 · 지침 · 개입 · 시드 를 값으로 규정
```

| 파일 | 역할 |
|---|---|
| `conditions.py` | **조건 스키마 — 단일 진실 공급원.** 실험은 여기 값 조합으로 규정된다 |
| `prompt.py` | 프롬프트 조립 (모델 없이 동작, 테스트 가능) |
| `runner.py` | `run()` 단일 진입점. 조건 → 적절한 경로로 라우팅 |
| `model.py` | 모델 내부 접근 — KV 캐시 편집, 어텐션 관측 |
| `steer.py` | step6 처방 — forward 훅, Spotlight |
| `intervention.py` | 순수 계산 — 정렬·회복률·판정불가 (torch 불필요) |
| `results.py` | 결과 저장 규약. `results/<스텝>/<슬러그>.json`, 불변 |

**조건이 파일명이 된다.**

```
qwen2-5-coder-3b-instruct__pre-c6of12-pool-syn-b0__ins-pos-camel-w__int-value-sweep-compliant__tok-mean__s42.json
└─ 모델 ────────────────┘  └─ 선행코드 ──────┘  └─ 지침 ─────┘  └─ 개입 ──────────────┘  └정렬┘ └시드┘
```

## 9. 조용한 실패를 막는 장치

이 연구에서 가장 위험한 것은 **"효과 없음"과 "실험이 안 됨"이 같은 숫자로 저장되는 것**이다.
실제로 여러 번 겪었고, 지금은 전부 예외를 던진다.

| 상황 | 예전 | 지금 |
|---|---|---|
| 미지원 개입 종류 | 조용히 회복률 0 | `NotImplementedError` |
| 치환할 자리 0개 | 조용히 회복률 0 | `ValueError` |
| 관측 구간 못 찾음 | 값이 `None`으로 저장 | `ValueError` |
| 층 목록을 여러 개 줌 | **첫 층만** 돌고 나머지 버림 | `ValueError` |
| Spotlight 훅이 안 걸림 | 회복률 0 | `RuntimeError` |
| 인과 마스크 없음 | **미래 토큰까지 봄** | 직접 마스크를 씌움 |

마지막 항목이 특히 중요하다 — 그대로였으면 "Spotlight는 효과 없다"가 나왔을 텐데,
그건 Spotlight 탓이 아니라 우리가 모델을 망가뜨린 탓이었을 것이다.
