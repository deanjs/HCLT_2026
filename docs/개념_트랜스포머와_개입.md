# 공통 개념 — 트랜스포머 구조와 우리가 건드리는 곳

> 모든 스텝이 공유하는 배경. 스텝별 문서(`docs/step<N>/방법론.md`)는 이 문서를 전제로 쓴다.
> **목표:** 이 문서만 읽으면 "우리가 모델의 **어디를** 만졌는지"를 그림으로 떠올릴 수 있게 한다.

## 1. 모델이 글을 읽는 과정

```
   "def split_config(value):"
              │
              ▼  토큰으로 쪼갬
   ["def", " split", "_", "config", "(", "value", "):"]
              │
              ▼  각 토큰 → 숫자 벡터 (임베딩)
   ┌──────────────────────────────────────────┐
   │  층 0   ──▶ 층 1 ──▶ … ──▶ 층 L ──▶ …    │   ← 층을 하나씩 통과
   └──────────────────────────────────────────┘
              │
              ▼
        다음 토큰 확률
```

층을 통과할 때마다 각 토큰 자리의 벡터가 조금씩 바뀐다. 이 **자리마다 하나씩 있는 벡터**를
**잔차(residual)** 라고 부른다. 층은 잔차를 "덮어쓰지" 않고 **더한다**.

```
   잔차_다음층 = 잔차_이번층 + (이번 층이 계산한 것)
```

→ **앞쪽 층에서 더한 것이 뒤까지 그대로 전달된다.** (step6에서 "엉뚱한 층에 밀어도 되는" 이유)

## 2. 어텐션 — 어디를 보고 무엇을 가져오나

새 토큰을 쓸 때, 모델은 **앞의 모든 토큰을 둘러본다.** 이때 자리마다 세 가지를 만든다.

| 이름 | 무엇인가 | 비유 |
|---|---|---|
| **Query (Q)** | 지금 자리가 "무엇을 찾는지" | 검색어 |
| **Key (K)** | 각 자리가 "무엇에 관한 것인지" 알리는 꼬리표 | 색인 |
| **Value (V)** | 각 자리가 실제로 **가진 내용** | 본문 |

계산은 두 단계다.

```
① 얼마나 볼지 정하기        a = softmax( Q · Kᵀ / √d )      ← 비중, 합이 1
② 본 만큼 내용을 가져오기    출력 = Σ_j  a_j · V_j
```

### 2-1. 한 자리가 둘러보는 것 = **한 줄(행)**

프롬프트가 토큰 185개라 하자. 마지막 자리(`def ▮`)가 앞을 둘러본다.

```
마지막 자리의 query q ──┬── "You"의 key와 점수 → 2.1
                       ├── "are"의 key       → 0.4
                       ├── …
                       └── "config"의 key    → 5.7      (185개)
                             ↓ softmax
                    [0.003, 0.001, …, 0.013]   ← 185개 숫자, **합 = 1**
```

**이 185개 숫자 한 벌이 "한 행"이다.** query 하나가 모든 key를 훑어 만든 비중표.

**합이 1이라는 것이 결정적이다** — 구간 값이 곧 **비중**이 된다.
`code_snake = 0.16`은 "그 순간 모델 주의의 **16%**가 snake 이름 토큰들에 갔다"는 뜻이다.

### 2-2. 모든 자리가 각자 하면 = **행렬**

185개 자리가 **각자** 한 줄씩 만든다 → `[185 × 185]` 행렬.

```
             ← 열: 무엇을 보나 (key 쪽) →
             You   are   …   config   def
      You  [ 1.0    —    —     —       — ]   ← 1번째 자리가 본 것
 행   are  [ 0.6   0.4   —     —       — ]      (미래는 못 본다 = 인과 마스크)
누가   …   [  …     …    …     —       — ]
보나  def  [0.003 0.001  …   0.013   0.02]   ← ★ 우리가 쓰는 줄
```

- **행 = 누가 보나**(query 쪽) · **열 = 무엇을 보나**(key 쪽)
- 오른쪽 위 삼각형이 빈 것은 **미래 토큰을 못 보기 때문**(인과 마스크)

**우리는 마지막 행 하나만 쓴다.** 나머지 184줄은 다른 토큰이 쓰이던 순간이라
"이름을 어떻게 정하나"와 무관하다.

> step6에서 잡은 버그가 이 삼각형이었다. Spotlight를 재구현하며 마스크를 안 씌워
> **미래까지 보는 모델**을 재고 있었다(→ `step6/code.md` §4-3).

### 2-3. head — 같은 일을 **여러 벌 동시에**

위 과정을 한 번만 하는 게 아니다. Qwen의 토큰 벡터는 2048차원인데,
이를 **16조각(128차원씩)으로 쪼개** 각 조각이 자기 q·k·v와 **자기 행렬**을 만든다.

```
토큰 벡터 2048차원
   ├─ 헤드 0  (128차원) → 자기 q,k,v → 자기 [185×185] → 마지막 행 [합 1]
   ├─ 헤드 1  (128차원) → …                            → 마지막 행 [합 1]
   ├─ …
   └─ 헤드 15 (128차원) → …                            → 마지막 행 [합 1]
                                                   ↓ 16개 평균
                                                [합 1]  ← 우리가 쓰는 값
```

**왜 쪼개나** — 헤드마다 보는 것이 다르다. 바로 앞 토큰만 보는 헤드, 문법 짝(괄호·따옴표)을
보는 헤드, 반복 패턴을 보는 헤드… 한 벌로는 그 다양한 관계를 한 번에 담지 못한다.

**16개를 평균 내도 합은 1**이라 비중의 의미가 유지된다.
헤드별 분해("어느 헤드가 범인인가")는 이 연구의 범위 밖이다.

### 2-4. 값이 나오는 경로 — 한눈에

```
185자리 × 16헤드 = 16장의 [185×185] 행렬
        ↓ 마지막 행만
16개 × 185개 숫자 (각 줄 합 1)
        ↓ 헤드 평균
185개 숫자 (합 1)
        ↓ camel 이름 토큰 12개의 열만 더함
0.1144  ← "그 순간 주의의 11.4%가 camel 이름들에 갔다"
        ↓ 구간 토큰 수로 나눔
0.0095  ← "토큰 하나가 받은 몫"   ← 논문에 쓰는 값
```

> **Q헤드와 KV헤드 수가 다를 수 있다**(Qwen 16 vs 2). 어텐션과 `‖v‖`를 곱할 때
> `h ÷ group_size`로 짝을 맞춰야 하며, 틀리면 **에러 없이** 잘못된 값이 나온다 → §4-2.

---

**이 연구의 핵심 질문이 바로 여기서 나온다.**

```
   표기 규약 정보는  ①(얼마나 보나 = K)에 있나,  ②(무엇을 읽나 = V)에 있나?
```

- K를 바꾸면 → **어디를 얼마나 볼지**가 바뀐다
- V를 바꾸면 → **거기서 무엇을 가져올지**가 바뀐다

우리는 이 둘을 **따로 바꿔치기**해서 어느 쪽에 정보가 실려 있는지 가른다.

## 3. KV 캐시 — 우리가 실제로 편집하는 자료구조

이미 읽은 토큰의 K와 V는 매번 다시 계산하지 않고 저장해 둔다. 이것이 **KV 캐시**다.

```
KV 캐시  (층마다 하나씩)
┌─────────────────────────────────────────────┐
│ 층 L                                         │
│   K:  [B, 헤드수, 토큰수, 차원]              │
│   V:  [B, 헤드수, 토큰수, 차원]              │
└─────────────────────────────────────────────┘
              ▲
              └── step3·step5는 여기를 직접 덮어쓴다
```

**우리 개입의 정체:** 화면의 글자는 그대로 두고, **캐시 안 특정 자리의 K 또는 V만 다른 값으로 바꾼다.**
그러고 나서 모델의 출력이 어떻게 달라지는지 본다.

## 4. 두 가지 함정 (실제로 겪었다)

### 4-1. RoPE — Key에는 위치가 박혀 있다

**Key에는 "그 토큰이 문장 몇 번째였는지"가 회전 형태로 이미 적용돼 캐시에 들어간다.**
Value에는 그런 것이 없다.

```
   K_p  =  회전(p) · (원래 키)        ← p번째 자리라는 정보가 섞여 있다
   V_p  =  (원래 값)                  ← 위치 정보 없음
```

그래서 **다른 위치의 K를 가져다 넣으면 위치가 어긋난 값**이 들어가고,
**여러 위치의 K를 평균 내면 회전이 엇갈려 서로 지워질** 수 있다.

→ "K를 바꿔도 안 되네"가 **K 경로의 성질**인지 **우리가 K를 망가뜨린 탓**인지 구분해야 한다.
이걸 잰 것이 **진단 실험 A**(`docs/diag/results.md`)이고, **문제없음**으로 판정났다.

### 4-2. GQA — K/V는 여러 헤드가 나눠 쓴다

최신 모델은 Q 헤드는 많고 K/V 헤드는 적다(Grouped Query Attention).

```
   Q 헤드:  □ □ □ □   □ □ □ □
              ╲ ╲ ╱ ╱     ╲ ╲ ╱ ╱
   KV 헤드:     ■           ■        ← 하나를 여러 Q가 공유
```

**따라서 K/V를 바꿀 때는 KV 헤드 단위로 통째로** 바꿔야 한다. 한 Q 헤드만 노릴 수 없다.
(모델마다 그룹 구성이 다르므로 `handle.gqa_info()`로 매번 확인한다.)

## 5. 개입의 두 방식

이 연구는 서로 다른 두 가지 방법으로 모델을 건드린다.

### 방식 A — KV 캐시 덮어쓰기 (step3·step5)

```
   프롬프트를 한 번 통과시켜 캐시를 얻는다
              │
              ▼
   층 L의 특정 자리 K(또는 V)를 **다른 프롬프트의 값**으로 교체
              │
              ▼
   출력이 어떻게 달라졌나 측정  →  원상복구  →  다음 층으로
```

- **어디서 가져오나(공여)** 를 바꿔가며 통제를 세운다
- 여러 조각을 평균 내어 넣는다(**평균 덮어쓰기**) — 토크나이저가 달라도 쓸 수 있다

### 방식 B — forward 훅 (step6)

```
   층 L의 출력 잔차에  세기 × 방향벡터  를 **더한다**
```

- 정답 프롬프트가 필요 없다. 방향 하나만 있으면 어디든 걸 수 있다 → **처방**
- Spotlight는 어텐션 함수 자체를 갈아끼워 **비중 a를 재조정**한다

## 6. 우리가 재는 값

### 먼저 — logP가 무엇인가

모델은 다음 토큰을 **확률**로 답한다. 그런데 이름은 토큰 여러 개라 확률을 **곱해야** 한다.

```
P("removeDuplicates") = P("remove") × P("Dup") × P("licates")
                      = 0.4 × 0.05 × 0.9  =  0.018
```

토큰이 늘수록 곱이 쌓여 아주 작은 수가 되고 컴퓨터에서 0으로 뭉개진다(언더플로).
**로그를 씌우면 곱셈이 덧셈**이 되어 이 문제가 사라진다.

```
logP("removeDuplicates") = log(0.4) + log(0.05) + log(0.9)
                         = −0.92  +  −3.00   +  −0.11   =  −4.03
```

**값 읽는 법 — 항상 음수다**(확률이 1 이하이므로). **0에 가까울수록 좋아한다.**

| logP | 확률 | 뜻 |
|---|---|---|
| −0.1 | 0.90 | 거의 확실히 이걸 쓴다 |
| −2 | 0.14 | 그럭저럭 |
| −7 | 0.001 | 거의 안 쓴다 |

### 준수 선호 점수 S

생성을 시키지 않고, 후보 두 개를 **강제로 놓고 채점**한다(교사강제).

```
   프롬프트 + "def " 뒤에 후보를 붙여 확률을 잰다

   log P(이름) = Σ_k log p(토큰_k | 앞의 모든 토큰)

   S = log P(지침 목표 표기) − log P(반대 표기)
```

**로그끼리 빼면 원래 확률의 비율**이 된다 — 이것이 S를 쓰는 이유다.

```
S = log( P(목표 표기) / P(반대 표기) )
```

| S | 뜻 |
|---|---|
| **양수** | 지침을 따르는 쪽을 선호 |
| 0 | 딱 반반 |
| **음수** | 어기는 쪽을 선호 |

**단위는 nat**(자연로그)다. 크기도 의미가 있다 — **S=1이면 약 2.7배, S=2면 약 7.4배** 선호.

실제 값(Qwen, 절벽 바닥):

```
S_깨끗 =  3.93   ← 문맥이 깨끗하면 목표 표기를 51배 선호
S_기준 = −1.56   ← 문맥에 위반이 섞이면 반대 표기를 4.8배 선호   ← 뒤집혔다
             차이 5.49 = 문맥이 행동을 흔든 정도 (회복률의 분모)
```

**왜 생성 대신 이걸 쓰나** — 생성은 이산적이라 개입을 걸어도 나오는 이름이 안 바뀌면
"효과 0"으로만 보인다. 로그 확률은 **0.001 차이도 잡는다.** 생성의 무작위성도 없앤다.

> ⚠️ **주의 1 — 부호 규약.** `logP(camel) − logP(snake)`가 **아니다.** 목표 표기 기준이므로
> snake 지침 조건에서는 부호 관계가 뒤집힌다.
>
> ⚠️ **주의 2 — 길이 정규화를 하지 않는다.** `removeDuplicates`(2조각)와
> `remove_duplicates`(3조각)는 더하는 항의 수가 다르므로 조각이 많은 쪽이 자연히 낮아진다.
> 그래서 **S의 절대값을 모델끼리 비교하면 안 되고**, 같은 조건 안의 **차이(회복률)** 만 쓴다.

### 회복률 (되돌림 정도)

```
              S_개입 − S_기준
   R  =  ──────────────────────
              S_깨끗 − S_기준
```

- **0** = 개입해도 그대로
- **1** = 오염이 없는 상태(천장)까지 완전 회복
- **1 초과** = 천장을 지나쳤다. **위가 막혀 있지 않다** — step6에서 문제가 됐다

### 영향력과 판정 불가

> 임계 1.0의 단위도 **nat**이다 — "문맥·지침을 바꿔도 선호가 2.7배도 안 움직였으면
> 흔들리지 않은 것으로 본다"는 뜻이다.

```
   gap = |S_깨끗 − S_기준|          분모의 크기
   판정 불가  ⟺  gap < 1.0
```

분모가 작으면 비율이 폭주하므로 분석에서 뺀다. 이 값은 결과 파일에 함께 저장된다.

### 거품과 순효과

**덮어쓰기는 두 가지 일을 동시에 한다.**

```
   ① 원래 있던 것을 지운다      ← 이것만으로도 점수가 움직인다 (거품)
   ② 새로운 것을 넣는다         ← 우리가 알고 싶은 것
```

그래서 **통제**를 함께 돌린다 — 정보가 안 들어가는 값을 덮어보고, 그때 나온 값을 뺀다.

```
   순효과 = 처치 − 통제
```

step3에서 이 거품이 회복률의 **절반 이상**이었다. **통제를 안 뺀 값은 상한으로만 읽어야 한다.**

| step4 | `observe` | 지침 참조량 관측 | RQ3 |
| step5 | `generate`+개입 | 지침 KV를 덮어써 인과 확인 | RQ3 |

## 8. 하네스 구조

**모든 실험이 함수 하나를 통과한다.** RQ별로 스크립트를 나누지 않는다.

```
   Condition(조건 객체)  ──▶  run(condition, mode=...)  ──▶  RunOutput
        │                            │
        │                            ├─ generate          → 생성 후 표기 측정
        │                            ├─ observe           → 구간별 참조량
        │                            ├─ steer             → 처방
        │                            └─ kv_diagnose       → 방법 진단
        │
        └─ 모델 · 선행코드 · 지침 · 개입 · 시드 를 값으로 규정
```

| 파일 | 역할 |
|---|---|
| `conditions.py` | **조건 스키마 — 단일 진실 공급원.** 실험은 여기 값 조합으로 규정된다 |
| `prompt.py` | 프롬프트 조립 (모델 없이 동작, 테스트 가능) |
| `runner.py` | `run()` 단일 진입점. 조건 → 적절한 경로로 라우팅 |
| `model.py` | 모델 내부 접근 — KV 캐시 편집, 어텐션 관측 |
| `steer.py` | step6 처방 — forward 훅, Spotlight |
| `intervention.py` | 순수 계산 — 정렬·회복률·판정불가 (torch 불필요) |
| `results.py` | 결과 저장 규약. `results/<스텝>/<슬러그>.json`, 불변 |

**조건이 파일명이 된다.**

```
qwen2-5-coder-3b-instruct__pre-c6of12-pool-syn-b0__ins-pos-camel-w__int-value-sweep-compliant__tok-mean__s42.json
└─ 모델 ────────────────┘  └─ 선행코드 ──────┘  └─ 지침 ─────┘  └─ 개입 ──────────────┘  └정렬┘ └시드┘
```

## 9. 조용한 실패를 막는 장치

이 연구에서 가장 위험한 것은 **"효과 없음"과 "실험이 안 됨"이 같은 숫자로 저장되는 것**이다.
실제로 여러 번 겪었고, 지금은 전부 예외를 던진다.

| 상황 | 예전 | 지금 |
|---|---|---|
| 미지원 개입 종류 | 조용히 회복률 0 | `NotImplementedError` |
| 치환할 자리 0개 | 조용히 회복률 0 | `ValueError` |
| 관측 구간 못 찾음 | 값이 `None`으로 저장 | `ValueError` |
| 층 목록을 여러 개 줌 | **첫 층만** 돌고 나머지 버림 | `ValueError` |
| Spotlight 훅이 안 걸림 | 회복률 0 | `RuntimeError` |
| 인과 마스크 없음 | **미래 토큰까지 봄** | 직접 마스크를 씌움 |

마지막 항목이 특히 중요하다 — 그대로였으면 "Spotlight는 효과 없다"가 나왔을 텐데,
그건 Spotlight 탓이 아니라 우리가 모델을 망가뜨린 탓이었을 것이다.
