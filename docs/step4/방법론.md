## 1. 왜 이 실험을 하나

step1~3은 **코드 쪽**만 봤다. 이제 **지침 쪽**을 본다.

**RQ3(관측) — 모델은 지침을 얼마나 참조하나?**

이 스텝이 **Spotlight 계열 접근(지침에 어텐션을 더 주자)에 대한 반박의 출발점**이다.
"안 봐서 못 지킨다"면 어텐션을 키우는 게 맞다. 그런데 이미 보고 있다면?

---

## 2. 지침 문장의 구조 — 여기가 함정이다

지침은 표기어를 **두 곳**에서 언급한다.

```
규칙문   : In this project we generally write function names in camelCase.
                                                              ^^^^^^^^^ 실제 명령
후보열거 : Every function name uses one of two styles only: camelCase or snake_case.
                                                            ^^^^^^^^^    ^^^^^^^^^^
                                                            대칭 나열
```

| 표기어 | 등장 횟수 |
|---|---|
| 요구 표기어(camelCase) | **2회** (규칙문 + 후보열거) |
| 반대 표기어(snake_case) | **1회** (후보열거만) |

**그냥 합치면 요구어가 구조적으로 2배 부풀려진다.** 그래서 역할별로 분리해서 잡는다.

| 구간 이름 | 무엇 |
|---|---|
| `instr_rule_word` | **규칙문의 지시어 — 실제 명령. 이걸 쓴다** |
| `instr_cand_camel` / `instr_cand_snake` | 후보열거의 두 표기어 |
| ~~`instr_target_word`~~ | 초판 합산키 — **논문에 쓰지 않는다** |

---

## 2-1. 실제로 만들어지는 프롬프트

**프롬프트는 step2와 완전히 같다.** 개입이 없으니 하나뿐이고, 공여도 천장 기준도 없다.
다른 것은 **어느 열을 합치느냐**(=구간을 어떻게 나누느냐)뿐이다.

```
[system] You are helping extend an existing Python module.
         In this project we generally write function names in camelCase.
                                                             └───┬───┘
                                                        instr_rule_word ← 진짜 명령
         Every function name uses one of two styles only: camelCase or snake_case.
                                                          └───┬───┘    └────┬────┘
                                                   instr_cand_camel  instr_cand_snake
[user]   Here is the current module:

         ```python
         def split_config(value): ...      ← code_snake (6개)
         def decodeNode(value): ...        ← code_camel (6개)
         ... 12개 ...
         ```

         Add a function that removes duplicate items from a list, preserving order.
[assistant]
def ▮        ← **여기까지 강제로 붙인다.** 이 자리에서 관측한다
```

**step2와 달리 지침 방향 두 가지를 다 돌린다.** `snake` 지침 조건이면 규칙문이
`... in snake_case.` 가 되고, 그때 `instr_rule_word`가 가리키는 단어도 `snake_case`로 바뀐다.
**단어는 바뀌지만 역할은 같다**(그 조건이 요구하는 표기어). 후보열거 두 구간은 방향과
무관하게 늘 같은 단어다.

---

## 2-2. 측정 절차

step2와 **장치가 같다.** 프롬프트 끝에 `"def "`를 붙이고, 그 자리의 query 한 줄을 층별로
꺼내 구간별로 합친다. **다른 것은 3번 한 단계뿐이다.**

```
   1. 프롬프트 뒤에 "def " 를 붙인다
   2. 토큰화하면서 offset을 함께 받는다

   3. 구간을 잡는다  ← 여기만 step2와 다르다
        코드 이름 : `def <이름>(` 정규식 (step2와 동일)
        지침 표기어 : instruction_notation_spans()가 **지침 문장 내부 offset**으로
                      역할별 구간을 낸다 (prompt.py:77)
                        · 후보열거 문장의 고정 앵커 "one of two styles only:" 를 찾아
                        · 그 **앞** = 규칙문 → instr_rule_word
                        · 그 **뒤** = 후보열거 → instr_cand_camel / instr_cand_snake
                      그 다음 프롬프트에서 지침이 시작하는 위치를 더해
                      **프롬프트 전체 기준으로 재기준**한다

   4. 모델을 한 번 통과시킨다 (output_attentions=True, use_cache=True)
   5. 층마다 어텐션 마지막 줄 + ‖v‖ 를 꺼낸다
   6. 구간에 속한 열만 합치고 구간 토큰 수로 나눈다
```

**구간이 실제로 몇 토큰인가** (42묶음 × 지침 2방향 평균, 결과 파일 `span_token_counts` 실측):

| 모델 | `instr_rule_word` | `instr_cand_camel` | `instr_cand_snake` | `code_camel` | `code_snake` | **코드÷지시어** |
|---|---|---|---|---|---|---|
| Qwen | 2.00 | 2 | 2 | 12.67 | 12.67 | **6.3배** |
| Llama | 2.00 | 2 | 2 | 12.67 | 12.67 | **6.3배** |
| DeepSeek | 3.50 | 3 | 4 | 16.35 | 22.45 | **4.7배** |
| StableCode | 2.50 | 2 | 3 | 14.37 | 20.25 | **5.7배** |

**지시어는 2~4토큰, 코드 이름 6개는 12~23토큰이다.** 5~6배 차이 나는 두 구간의 합을
그대로 비교하면 긴 쪽이 무조건 이긴다. 이 정규화 하나로 **결론의 부호가 뒤집혔다**(§8).

**조건 수.** 모델 4개 × 42묶음 × 지침 2방향 = **336개**. 시드 42, 개입 없음.

## 2-3. 위 프롬프트와 구간을 직접 찍어 보기 (GPU 불필요)

```bash
python3 -c "
import sys, json, glob; sys.path.insert(0,'src')

## 3. 재는 값

step2와 **똑같은 장치**를 쓴다. 구간만 다르다.

```
   a_j  = (1/H) Σ_h a[h,j]                       어텐션
   av_j = (1/H) Σ_h a[h,j]·‖v[h÷g,j]‖            기여 상한

   토큰당 = 구간 합 / 구간 토큰 수
```

### 토큰 수로 나누는 것이 결정적이다

| 구간 | 평균 토큰 수 (Qwen) |
|---|---|
| 규칙문 지시어 | **2.00** |
| 코드 camel 이름 6개 | **12.67** |

**6배 차이 나는 두 구간의 합을 그대로 비교하면 긴 쪽이 무조건 이긴다.**
(모델 4개 전부의 토큰 수는 §2-2 표에 있다 — 4.7~6.3배.)
실제로 이 정규화 하나로 **결론의 부호가 뒤집혔다**(§8).

## 4. 파이프라인

```
Condition (개입 없음)
   │
   ▼
build_instruction_text()             지침 문장 조립
instruction_notation_spans()         **지침 문장 내부 offset**으로 역할별 구간 계산
   │                                   → {instr_rule_word: [(a,b)], instr_cand_*: [...]}
   ▼
observe_generation_query(
    groups={code_camel:[...], code_snake:[...]},
    instruction_text=...,            지침 전체 구간
    notation_spans=...               역할별 구간 (내부 offset)
)
   │
   ├─ 프롬프트에서 지침 문장이 시작하는 위치를 찾고
   ├─ 내부 offset에 그 시작점을 더해 **프롬프트 전체 기준으로 재기준**
   └─ 나머지는 step2와 동일
   │
   ▼
Metrics.per_layer[층]["instr_rule_word__attention_weight"] 등
```

함수 단위 해설·호출 사슬·실제 코드 발췌는 **[`code.md`](code.md)** 에 있다. 여기서는 방법만 다룬다.

코드_토큰당   = v["code_camel__attention_weight"]      / cnt["code_camel"]
```

## 8. 이 스텝의 한계

- **인과가 아니다.** 그 참조가 행동을 바꾸는지는 step5의 몫
- 합산키(`instr_target_word`)는 구조적 2:1이라 못 쓴다
- 코드 구간끼리의 비교는 **step2 결과를 인용**한다(step4에서는 프롬프트 구성이 달라 부호가 흔들린다)
- 앵커 문자열이 지침 조립과 분리돼 있어 문구를 바꾸면 조용히 오분류된다
