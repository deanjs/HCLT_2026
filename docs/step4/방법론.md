# step4 방법론 — 지침 관측 (RQ3 관측)

> **선행 지식:** `docs/개념_트랜스포머와_개입.md` §2(어텐션) · step2 방법론(같은 관측 장치)

---

## 1. 왜 이 실험을 하나

step1~3은 **코드 쪽**만 봤다. 이제 **지침 쪽**을 본다.

**RQ3(관측) — 모델은 지침을 얼마나 참조하나?**

이 스텝이 **Spotlight 계열 접근(지침에 어텐션을 더 주자)에 대한 반박의 출발점**이다.
"안 봐서 못 지킨다"면 어텐션을 키우는 게 맞다. 그런데 이미 보고 있다면?

---

## 2. 지침 문장의 구조 — 여기가 함정이다

지침은 표기어를 **두 곳**에서 언급한다.

```
규칙문   : In this project we generally write function names in camelCase.
                                                              ^^^^^^^^^ 실제 명령
후보열거 : Every function name uses one of two styles only: camelCase or snake_case.
                                                            ^^^^^^^^^    ^^^^^^^^^^
                                                            대칭 나열
```

| 표기어 | 등장 횟수 |
|---|---|
| 요구 표기어(camelCase) | **2회** (규칙문 + 후보열거) |
| 반대 표기어(snake_case) | **1회** (후보열거만) |

**그냥 합치면 요구어가 구조적으로 2배 부풀려진다.** 그래서 역할별로 분리해서 잡는다.

| 구간 이름 | 무엇 |
|---|---|
| `instr_rule_word` | **규칙문의 지시어 — 실제 명령. 이걸 쓴다** |
| `instr_cand_camel` / `instr_cand_snake` | 후보열거의 두 표기어 |
| ~~`instr_target_word`~~ | 초판 합산키 — **논문에 쓰지 않는다** |

---

## 3. 재는 값

step2와 **똑같은 장치**를 쓴다. 구간만 다르다.

```
   a_j  = (1/H) Σ_h a[h,j]                       어텐션
   av_j = (1/H) Σ_h a[h,j]·‖v[h÷g,j]‖            기여 상한

   토큰당 = 구간 합 / 구간 토큰 수
```

### 토큰 수로 나누는 것이 결정적이다

| 구간 | 평균 토큰 수 (Qwen) |
|---|---|
| 규칙문 지시어 | **3.00** |
| 코드 camel 이름 12개 | **12.60** |

**4배 차이 나는 두 구간의 합을 그대로 비교하면 긴 쪽이 무조건 이긴다.**
실제로 이 정규화 하나로 **결론의 부호가 뒤집혔다**(§8).

## 4. 파이프라인

```
Condition (개입 없음)
   │
   ▼
build_instruction_text()             지침 문장 조립
instruction_notation_spans()         **지침 문장 내부 offset**으로 역할별 구간 계산
   │                                   → {instr_rule_word: [(a,b)], instr_cand_*: [...]}
   ▼
observe_generation_query(
    groups={code_camel:[...], code_snake:[...]},
    instruction_text=...,            지침 전체 구간
    notation_spans=...               역할별 구간 (내부 offset)
)
   │
   ├─ 프롬프트에서 지침 문장이 시작하는 위치를 찾고
   ├─ 내부 offset에 그 시작점을 더해 **프롬프트 전체 기준으로 재기준**
   └─ 나머지는 step2와 동일
   │
   ▼
Metrics.per_layer[층]["instr_rule_word__attention_weight"] 등
```

**핵심 코드**

| 함수 | 파일 | 하는 일 |
|---|---|---|
| `instruction_notation_spans` | `prompt.py` | 규칙문/후보열거 분리 (지침 내부 offset 기준) |
| `observe_generation_query` | `model.py` | 내부 offset → 프롬프트 기준 재계산 + 관측 |

```python
# prompt.py — 후보열거 시작점을 앵커로 규칙문과 나눈다
_CANDIDATE_ANCHOR = "one of two styles only:"
ci = text.find(_CANDIDATE_ANCHOR)          # 이 앞 = 규칙문, 뒤 = 후보열거
```

> **취약점:** 앵커가 지침 조립 코드와 따로 하드코딩돼 있다. 지침 문구를 고치면
> `find`가 −1이 되어 **후보열거 단어가 전부 규칙문으로 분류된다.** 값이 조용히 2배가 된다.
> 지금은 관측 구간이 비면 예외를 던지지만, 앵커 불일치는 예외가 아니라 **오분류**라 안 걸린다.

## 5. 결과 JSON 읽는 법

`results/step4_instr-observe/*.json` — 모델당 84개(42묶음 × 지침 방향 2)

| 필드 | 뜻 |
|---|---|
| `per_layer["<층>"]["instr_rule_word__attention_weight"]` | **규칙문 지시어 어텐션 합 — 이걸 쓴다** |
| `..."code_camel__attention_weight"` | 코드 camel 이름 구간 |
| `..."instr_cand_camel__*"` / `"instr_cand_snake__*"` | 후보열거 |
| `..."instruction__*"` | 지침 문장 전체 |
| `..."instr_target_word__*"` | **초판 합산키 — 쓰지 않는다**(2:1 비대칭) |
| `extra.span_token_counts` | **정규화에 필수** |

```python
cnt = r["metrics"]["extra"]["span_token_counts"]
지시어_토큰당 = v["instr_rule_word__attention_weight"] / cnt["instr_rule_word"]
코드_토큰당   = v["code_camel__attention_weight"]      / cnt["code_camel"]
```

## 8. 이 스텝의 한계

- **인과가 아니다.** 그 참조가 행동을 바꾸는지는 step5의 몫
- 합산키(`instr_target_word`)는 구조적 2:1이라 못 쓴다
- 코드 구간끼리의 비교는 **step2 결과를 인용**한다(step4에서는 프롬프트 구성이 달라 부호가 흔들린다)
- 앵커 문자열이 지침 조립과 분리돼 있어 문구를 바꾸면 조용히 오분류된다
