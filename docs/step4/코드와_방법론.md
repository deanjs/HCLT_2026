## 1. 배경 개념 — 트랜스포머의 어디를 만지는가

우리 연구에서 **쓰든 안 쓰든 반드시 알아야 하는** 개념만, 우리 코드와 연결해서 정리한다.

### 1-1. 전체 그림: 잔차 스트림(residual stream)

디코더 전용 LLM(우리가 쓰는 4개 모두)은 토큰 하나마다 **하나의 벡터**를 들고 층을 통과시킨다.
이 벡터가 지나가는 통로를 **잔차 스트림(residual stream)** 이라 부른다. 층 L은 이 벡터를 갈아치우지 않고
**더한다**:

```
x_L+1[i] = x_L[i] + Attention_L(x_L)[i] + FFN_L( x_L[i] + Attention_L(x_L)[i] )
             └ 위치 i의 현재 표현        └ 다른 위치에서 가져온 것   └ 그 자리에서 변형한 것
```

여기서 두 부품의 역할이 **완전히 다르다**. 이 구분이 우리 연구의 뼈대다.

| 부품 | 하는 일 | 비유 | 우리 실험과의 관계 |
|---|---|---|---|
| **Attention** | **위치 사이**로 정보를 옮긴다. "저기 있는 걸 가져와 여기 더한다" | 자료 열람 | **우리가 관측·조작하는 곳** |
| **FFN (MLP)** | **같은 위치 안**에서 표현을 변형한다. 다른 토큰을 못 본다 | 가져온 자료를 자기 머리로 가공 | **직접 만지지 않는다** (§1-7, §8-9) |

토큰별 최종 벡터는 마지막에 정규화 후 **어휘 크기 벡터(logits)** 로 펼쳐지고, softmax를 거쳐 다음 토큰 확률이 된다.
우리 준수 선호 점수 S(§6-4)는 바로 이 logits에서 계산한다.

### 1-2. Query · Key · Value — "누가 무엇을 보고 무엇을 가져오는가"

어텐션 안에서 각 위치 i의 벡터는 세 가지로 투영된다(학습된 가중치 행렬 W_Q, W_K, W_V).

| 이름 | 만드는 식 | 직관 | 한 줄 정의 |
|---|---|---|---|
| **Query (질의) q** | `q_i = W_Q · x_i` | "내가 지금 **찾고 있는 것**" | 읽는 쪽의 검색어 |
| **Key (열쇠) k** | `k_j = W_K · x_j` | "나는 **이런 종류의 정보**요" | 읽히는 쪽의 색인표 |
| **Value (내용) v** | `v_j = W_V · x_j` | "내가 **실제로 건네줄 내용**" | 읽히는 쪽의 본문 |

계산은 두 단계다.

```
(1) 얼마나 볼까 :  a[i,j] = softmax_j ( q_i · k_j / √d_head  + 인과마스크 )    ← Q와 K만 관여
(2) 무엇을 받나 :  o_i    = Σ_j  a[i,j] · v_j                                  ← V만 관여
```

**이것이 우리 논문의 핵심 분리다.**

- **Key를 바꾸면** → 내적이 바뀌고 → **어텐션 분포 a가 바뀐다** = "**얼마나 보는가**"를 조작한 것.
- **Value를 바꾸면** → a는 **그대로**인데 → **받아오는 내용이 바뀐다** = "**무엇을 전달받는가**"를 조작한 것.

기존 접근(Spotlight 계열: "지침에 어텐션을 더 주자")은 (1)번 통로를 키우는 처방이다.
우리는 **(2)번이 진짜 손잡이**라고 주장하며, 그 검증이 K/V를 **따로 치환**하는 step3·step5다.

> **인과 마스크(causal mask):** 위치 i는 j ≤ i만 볼 수 있다(미래를 못 본다). 그래서 "이름을 쓰는 순간의
> query"는 그 앞의 지침·코드를 전부 볼 수 있고, 우리가 그 한 행만 봐도 되는 근거가 된다.

### 1-3. Multi-head — 여러 개의 독립적인 열람 창구

어텐션은 한 번이 아니라 **head 여러 개**가 병렬로 돈다. head마다 W_Q/W_K/W_V가 달라서 서로 다른 것을 본다
(어떤 head는 문법, 어떤 head는 직전 반복 패턴…). 각 head 출력을 이어붙여 W_O로 한 번 더 섞은 뒤 잔차에 더한다.

- 우리 지표는 head별로 계산한 뒤 **head 평균**을 낸다(`attention_probe._token_stats`).
- 한계: **W_O 이후**가 아니라 **직전** 값을 본다(§8-8).

### 1-4. GQA (Grouped Query Attention) — "질문은 16개, 서랍은 2개"

최근 모델은 메모리를 아끼려고 **Key/Value head 수를 Query head 수보다 적게** 둔다.
여러 query head가 **같은 KV 한 벌을 공유**한다.

우리 실측(Qwen2.5-Coder-3B):

```
num_attention_heads = 16   (Hq : query head 수)
num_key_value_heads = 2    (Hkv: KV head 수)
group_size          = 8    (= Hq / Hkv, KV 하나를 공유하는 query head 수)
```

그래서 `a`는 `[16, seq]`인데 `‖v‖`는 `[2, seq]`다. 곱하려면 **매핑**이 필요하다 —
query head `h`는 KV head `h // group_size`를 쓴다. 코드가 정확히 그렇게 한다:

```python
# src/harness/attention_probe.py:31
av_j = sum(attn_last[h][j] * vnorm_kv[h // group_size][j] for h in range(Hq)) / Hq
```

**CLAUDE.md §3의 "치환은 KV group 단위" 규칙도 여기서 나온다.** KV 텐서는 `[batch, Hkv, seq, head_dim]`이라
한 위치를 치환하면 **그 KV를 공유하는 query head 전부**에 동시에 반영된다. 모델마다 group 구성이 다르므로
매번 `handle.gqa_info()`로 확인하고, 결과 JSON의 `extra.gqa`에 박아 둔다.

### 1-5. KV 캐시 — 우리가 실제로 만지는 물건

생성할 때 매 토큰마다 앞부분을 다시 계산하면 낭비다. 그래서 트랜스포머는 각 층·각 위치의
**k와 v를 계산해 저장(cache)** 해 둔다. 이것이 `past_key_values`다.

```
past_key_values[layer].keys    : [batch, Hkv, seq, head_dim]
past_key_values[layer].values  : [batch, Hkv, seq, head_dim]
```

**우리 개입은 이 캐시를 직접 편집하는 것이다.** 텍스트는 한 글자도 안 바꾸고, "그 단어가 남긴 내부 흔적"만
반대쪽 것으로 갈아끼운다. 코드에서 꺼내는 지점:

```python
# src/harness/model.py:686  — transformers 버전별 레이아웃 흡수
def _cache_kv(cache, layer):
    if hasattr(cache, "layers"):        # 신형(4.54+)
        return cache.layers[layer].keys, cache.layers[layer].values
    if hasattr(cache, "key_cache"):     # 구형
        return cache.key_cache[layer], cache.value_cache[layer]
    return cache[layer][0], cache[layer][1]   # legacy tuple
```

> **중요한 성질 하나.** 캐시의 `values`는 **RoPE(위치 회전)가 적용되지 않은** 순수 내용 벡터인 반면,
> `keys`는 **RoPE가 이미 적용된** 상태로 저장된다. 즉 Key에는 "무엇"뿐 아니라 "어디(위치)" 정보가 섞여 있다.
> Key 치환 결과를 해석할 때 이 비대칭을 반드시 언급해야 한다(§8-5).

### 1-6. 토큰화(BPE)와 우리 문제의 특수성

모델은 단어가 아니라 **하위 토큰(subword)** 단위로 읽는다. 그런데 우리 연구 대상인 표기 규약은
**하필 토큰 경계에 직결된다**:

```
parseHeader   → [' parse', 'Header']        (2조각)
parse_header  → [' parse', '_', 'header']   (3조각)   ← 모델·토크나이저마다 다름
camelCase     → ['camel', 'Case']           (2조각)
snake_case    → ['snake', '_', 'case']      (3조각)
```

조각 수가 다르면 **1:1 짝짓기가 불가능**하다. 이 문제 하나 때문에 코드에 정렬 단위 축(`token_unit`)이 있고,
최종적으로 **평균 덮어쓰기(mean-pool)** 로 통일했다(§5-4, CLAUDE.md §3).

### 1-7. FFN(MLP) — 왜 안 만지는가

FFN은 위치 i의 벡터 하나를 받아 `W_down · σ(W_up · x)` 로 변형한다. 다른 위치를 보지 못한다.
"사실 기억이 저장되는 곳"이라는 연구(key–value memory 관점)가 많아 **후속 연구로는 당연히 후보**지만,
우리 RQ는 "**문맥의 코드 신호와 지침 신호가 이름 결정에 전달되는 통로**"이므로 **위치 사이 전달**을 맡는
어텐션이 정확한 조사 대상이다. FFN은 그 전달 이후의 가공 단계다.

→ 논문에서는 **"우리는 위치 간 전달 경로(attention read pathway)를 분리해 인과 판정했고, 위치 내 변환(FFN)은
범위 밖"** 이라고 명시한다. (§8-9 한계)

### 1-8. 우리가 안 쓰는 것들(그러나 물으면 답해야 하는 것)

| 개념 | 우리 코드에서 | 왜 |
|---|---|---|
| logit lens / tuned lens | 안 씀 | 중간 층 표현을 어휘로 투영해 보는 기법. 우리는 대신 **직접 치환 후 최종 logits 변화**를 본다(더 강한 인과 증거) |
| SAE / 특징 분해 | 안 씀 | 방향 자체를 해석하려면 필요. 우리 주장은 "K냐 V냐, 몇 층이냐"까지라 불필요 |
| 파인튜닝·프롬프트 최적화 | 안 씀 | 진단 연구지 개선 제안이 주가 아님 |
| 어텐션 증폭(Spotlight 재현) | **스키마에만 있고 미구현** | `InterventionKind.ATTENTION_AMPLIFY` 정의는 있으나 model.py에 경로 없음 → §8-10 |

## 2. 주장 지도 — 어느 실험이 무엇을 잘라내는가

```
      "모델이 지침을 어긴다"
                │
    ┌───────────┴────────────┐
    │                        │
 [가설 A] 지침을 덜 본다    [가설 B] 보긴 보는데 전달이 안 된다
 (= 어텐션 부족)              (= 내용/Value 통로 문제)
    │                        │
    │  step4(관측): 지침 지시어를 코드 이름만큼·때론 더 본다
    │      → 가설 A는 관측 단계에서 이미 약해진다
    ↓                        ↓
 Spotlight식 처방       step5(인과): 지시어의 K만 / V만 / 둘 다 치환
 (어텐션 키우기)          → V를 바꿔야 행동이 바뀌면 가설 B 확정
```

- **step2/step4 = 관측**: "어디에 신호가 보이나". 상관 증거. **인과 주장 불가.**
- **step3/step5 = 인과**: "무엇을 바꾸면 행동이 바뀌나". 개입 증거.
- 관측만으로 "어텐션이 원인이 아니다"라고 쓰면 안 되고, 반대로 인과 실험 없이 "충분히 본다"까지가
  step4가 말할 수 있는 전부다(`results.md` §3의 "뜻하지 않는 것" 절이 이 선을 지킨다).

## 3. 코드 구조 — 어떤 형식으로 짜여 있나

### 3-1. 설계 원칙 세 가지

1. **RQ별 스크립트 금지 (CLAUDE.md §7).**
   `run_rq1.py` 같은 파일이 없다. 실험은 **조건 객체(`Condition`) 하나**로 규정되고, 모든 실험이
   **단일 진입점 `run(condition)`** 을 통과한다. 새 실험 = 새 파일이 아니라 **스키마에 값 추가**.
2. **무거운 의존성 격리.**
   `torch`/`transformers`는 `model.py` 안에서 **함수 내부 지연 임포트**한다. 그래서 조건 조립·프롬프트 생성·
   지표 집계·결과 저장은 **GPU도 torch도 없이** 돌아가고, 단위 테스트가 가능하다(`tests/` 7개 파일).
3. **큰 텐서를 파이썬으로 안 옮긴다.**
   `model.py`가 필요한 최소 조각(마지막 query 행 `[Hq, seq]`, 토큰별 ‖v‖ `[Hkv, seq]`)만 리스트로 변환해
   넘기고, 집계는 순수 함수(`attention_probe.py`)가 한다.

### 3-2. 파일 지도

```
src/harness/
├── conditions.py     조건 스키마 — 실험의 단일 진실 공급원 (dataclass + Enum)
├── tasks.py          함수 이름 풀 504개 · 생성 과제 3개 (데이터)
├── naming.py         camel/snake 렌더링과 판정 (정규식)
├── prompt.py         선행 코드·지침 문장·사용자 메시지 조립 (순수 문자열)
├── runner.py         ★ 단일 진입점 run() + 모드별 배선
├── model.py          ★ 모델 로딩 · forward · 어텐션/KV 추출 · KV 캐시 편집 (유일한 torch 의존)
├── attention_probe.py 구간 집계 · 토큰 위치 찾기 · 코사인 (torch 없음, 테스트 가능)
├── intervention.py   토큰 정렬 · 회복률 · 선호 점수 (torch 없음, 테스트 가능)
├── metrics.py        지표 컨테이너 (자리와 의미 고정)
└── results.py        불변 저장 규약 (경로 = 조건 슬러그)
```

의존 방향은 **한 방향**이다 (순환 없음):

```
conditions ──> tasks ──> naming
     │           │
     └──> prompt ─┘
            │
runner ─────┴──> model ──> attention_probe
   │                  └──> intervention
   └──> metrics ──> results
```

### 3-3. 조건 스키마 — 실험 하나를 규정하는 5개 축

`Condition`(`conditions.py:198`)은 **frozen dataclass**(불변)다. 이 객체 하나면 실험이 재현된다.

| 축 | 클래스 | 주요 값 |
|---|---|---|
| **모델** | `ModelSpec` | HF ID, family, dtype, quantization |
| **선행 코드** | `PrecedingCode` | `n_compliant`(준수 개수), `n_functions`(12), `composition`(clone/distinct/**pool**), `source`(synthetic/repo), `pool_block`(0~41) |
| **지침** | `Instruction` | `form`(positive/negative), `target_notation`(camel/snake), `strength`(weak/strong), `candidates`(닫힌 두 후보) |
| **개입** | `Intervention` | `kind`(none/key/value/key_value/attn_amplify), `layers`(정수 리스트 또는 `"sweep"`), `donor`, `target`(**"code"/"instruction"**) |

### 4-3. 핵심 트릭 ①: teacher forcing으로 "그 순간"을 만든다

우리가 재고 싶은 건 **"모델이 이름을 쓰려는 바로 그 순간"** 의 상태다. 그런데 모델에게 그냥 생성시키면
서론("Sure, here's the function...")부터 나와서 그 순간이 언제인지 알 수 없다.

그래서 프롬프트 끝에 **`"def "` 를 강제로 붙인다**:

```python
# model.py:137
prompt_text = tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
prompt_text = prompt_text + forced_prefix        # forced_prefix = "def "
```

이러면 **다음에 예측될 토큰이 반드시 함수 이름의 첫 조각**이다. 그 위치(= 마지막 위치)의 query 한 행이
바로 "이름을 고르는 질의"다. 우리는 **그 한 행만** 본다:

```python
# model.py:191
attn_last = attentions[layer][0, :, -1, :]   # [Hq, seq]  ← 마지막 query 행만
```

전체 `[seq, seq]` 어텐션 행렬을 다 저장하면 파일이 수백 MB가 되지만, 우리에겐 이 한 행이면 충분하다.

### 4-4. 핵심 트릭 ②: 문자 위치 → 토큰 인덱스 (offset mapping)

"지침의 `camelCase`라는 단어"는 **문자 단위** 개념인데, 어텐션은 **토큰 단위**로 나온다. 이 둘을 잇는 게
`return_offsets_mapping`이다 — 토큰마다 `(문자시작, 문자끝)`을 알려준다.

```python
# model.py:140
enc = tok(prompt_text, return_tensors="pt", return_offsets_mapping=True, add_special_tokens=False)
offsets = [tuple(o) for o in enc.pop("offset_mapping")[0].tolist()]
```

> **왜 `apply_chat_template(tokenize=False)` 후 다시 토큰화하나?**
> 템플릿에게 바로 토큰을 받으면 offset이 안 나온다. **문자열로 받아 우리가 직접 토큰화**해야
> "모델이 실제로 본 입력"과 "offset"이 **완전히 일치**한다. `add_special_tokens=False`는 템플릿이 이미
> 특수 토큰을 넣었으므로 중복 삽입을 막는 것.

그 다음 겹침 판정으로 구간을 만든다(`attention_probe.py:93`):

```
토큰 [ts, te) 와 문자구간 [cs, ce) 가 겹치면(ts < ce and te > cs) 그 토큰을 구간에 포함
→ 이름이 몇 조각으로 쪼개지든 전부 포착된다
```

함수 이름은 `def <name>(` 로 찾은 뒤 **앞 4글자와 뒤 1글자를 잘라** 이름 부분만 남긴다(`model.py:156`).
이름만 검색하면 본문·호출부에서 우연히 겹치기 때문이다.

### 4-5. 핵심 트릭 ③: 지침 표기어를 **역할별로** 분리 (step4의 고유 기여)

지침 문장은 표기어를 **두 곳**에서 말한다.

| 역할 | 문장 | camel 지침일 때 등장 횟수 |
|---|---|---|
| **규칙문 지시어** | "...write function names in **camelCase**." | 요구어 1회 |
| **후보열거** | "...one of two styles only: **camelCase** or **snake_case**." | 각 1회씩 |

→ 요구어는 총 **2회**, 반대어는 **1회**. **그냥 합쳐 재면 요구어가 "많이 나와서" 부풀려진다.**

`instruction_notation_spans`(`prompt.py:66`)가 고정 앵커 문자열 `"one of two styles only:"` 를 기준으로
그 **앞이면 규칙문, 뒤면 후보열거**로 나눈다. 실측 offset:

```python
{'instr_rule_word': [(103, 112)],    # 규칙문의 camelCase — 진짜 명령
 'instr_cand_camel': [(163, 172)],   # 후보열거의 camelCase
 'instr_cand_snake': [(176, 186)]}   # 후보열거의 snake_case
```

이 offset은 **지침 문장 내부 기준**이라, `model.py:176`에서 프롬프트 전체 기준으로 재기준한다
(`inst_start + a`). 초판 방식(`instr_target_word`, 합산)도 **함께 저장**해 두어,
`합산 = 규칙문 + 후보열거` 가 산술적으로 맞는지 검증 가능하다 (qwen: 0.0076 = 0.0063 + 0.0013).

### 4-7. 집계 (`span_metrics`)

토큰 j 하나에 대해:

```
a_j  = (1/Hq)  Σ_h  a[h, j]                              "평균적으로 이 토큰을 얼마나 보나"
av_j = (1/Hq)  Σ_h  a[h, j] · ‖v[h÷gs, j]‖               "이 토큰이 잔차에 실제로 밀어넣는 양"
v_j  = (1/Hkv) Σ_k  ‖v[k, j]‖                            "이 토큰이 싣고 있는 내용의 크기"
```

구간(span) 단위로는:

| 지표 | 집계 | 왜 그렇게 |
|---|---|---|
| `attention_weight` | **합** `Σ_{j∈span} a_j` | 각 head의 어텐션 행은 전체에 대해 1로 합해진다 → 구간 합 = 그 구간이 가져간 **질량(0~1)** |
| `av_norm` | **합** `Σ_{j∈span} av_j` | 기여는 더해지는 양이므로 합이 맞다 |
| `v_norm` | **평균** `mean_j v_j` | 크기 지표라 토큰 수에 비례하면 안 된다 |
| `n_tokens` | 개수 | **토큰당 평균 환산용** — 구간 길이가 다르면 합끼리 비교는 불공정(§6-3) |

**`‖av‖ = a·‖v‖` 는 근사가 아니라 정확하다.** a는 음이 아닌 스칼라이므로 `‖a·v‖ = a·‖v‖`.
(계획서 §2.4의 항등식. 이걸 코드 주석에 못 박아 둔 이유는, 리뷰어가 "왜 노름을 곱셈으로 분리했나"를 반드시 묻기 때문.)

## 5. 실행 흐름 ② 인과 경로 (step3/step5가 쓰는 길, KV 치환)

step4는 관측만 하지만 **같은 코드베이스**가 치환도 한다. 논문의 핵심 실험이므로 여기 상세히 적는다.

### 5-1. 무엇을 하는 실험인가 — 한 문장

> **텍스트는 한 글자도 안 바꾸고**, "그 단어가 남긴 내부 흔적(K 또는 V)"만 **반대쪽 조건의 것으로 갈아끼운 뒤**,
> 모델의 이름 선택이 반대쪽으로 **얼마나 넘어가는지**를 층마다 잰다.

학술 용어로는 **반사실 활성 치환(counterfactual activation patching)**, 그중에서도 **KV 캐시 수준의
경로 특정 치환(path-specific patching)** 이다. K와 V를 따로 갈아끼울 수 있다는 점이 핵심이다(§1-2).

### 5-2. 세 개의 프롬프트, 세 개의 점수

step5(지침 인과)의 설정(`runner.py:207 _preference_setup_instruction`):

| 상태 | 프롬프트 | 점수 | 뜻 |
|---|---|---|---|
| **base** | 조건 지침 그대로 (예: "camelCase로 써라") | `S_base` | 손 안 댄 기준선 |
| **opp** (코드상 `comp_`) | **지침만** 반대로 (예: "snake_case로 써라"), 선행 코드는 **동일** | `S_clean` | **천장** — 지침을 통째 바꿨을 때 도달하는 값 |
| **int** | base 텍스트 그대로인데, **지시어 단어의 KV만** opp의 것으로 치환 | `S_int` | 개입 결과 |

**"딱 두 곳만 바꾼다"** 가 이 설계의 요점이다. step3(코드 인과)과 비교하면:

| | 치환 대상 | 공여(donor) |
|---|---|---|
| **step3 (코드)** | 선행 코드의 **위반 표기 이름들** (`def parse_header(` 의 `parse_header`) | 같은 이름의 **준수판**(`parseHeader`) — 또는 통제로 **무관한 이름** |
| **step5 (지침)** | 지침 규칙문의 **지시어 단어** (`camelCase`) | **반대 지침**의 지시어(`snake_case`) |

같은 `intervene_preference_sweep` 함수를 **`span_kind`("def_name"/"literal")와 `target`("code"/"instruction")
두 값만 바꿔** 재사용한다(CLAUDE.md §7 "스크립트를 나누지 않는다"의 실제 구현).

### 5-3. K와 V를 어디서 뽑아 어디에 넣나 (구체적 절차)

```
① 세 프롬프트를 각각 한 번씩 forward → past_key_values 확보          model.py:277
     viol_cache  = model(base_ids[:, :-1]).past_key_values
     comp_cache  = model(opp_ids [:, :-1]).past_key_values   ← donor_cache로도 재사용
   ※ 마지막 토큰은 캐시에 안 넣는다. 채점 forward에서 넣어야 그 자리의 logits이 나오므로.

② 치환 대상 토큰 위치 찾기                                            model.py:658 _locate_target_tokens
     base 프롬프트에서 "camelCase" 첫 등장 → 토큰 인덱스 [t1, t2]
     opp  프롬프트에서 "snake_case" 첫 등장 → 토큰 인덱스 [u1, u2, u3]
   ※ 첫 등장 = 규칙문(후보열거보다 앞) → 진짜 지시어를 집는다.

③ 층 L에서 KV 텐서를 꺼낸다 (원본 참조, 편집 가능)                     model.py:341
     ek, ev = _cache_kv(work_cache,  L)     # [1, Hkv, seq, d]  ← 편집 대상
     dk, dv = _cache_kv(donor_cache, L)     # [1, Hkv, seq, d]  ← 공여

④ 평균 덮어쓰기(mean-pool) — CLAUDE.md §3 통일 방식                   model.py:346
     v̄ = dv[:, :, [u1,u2,u3], :].mean(dim=2)      # 공여 조각들을 평균 내 한 벡터로
     ev[:, :, t1, :] = v̄ ;  ev[:, :, t2, :] = v̄   # 위반 단어의 모든 자리에 덮어씀
     (kind='key'면 k만, 'value'면 v만, 'key_value'면 둘 다)

⑤ 점수 측정 후 **원상 복구**                                          model.py:361
     s_int = S(work_cache)  →  백업해 둔 값으로 되돌림
     → 다음 층은 깨끗한 base 상태에서 시작(층 효과가 누적되지 않는다)
```

**이 절차의 결정적 성질 — 반드시 논문에 적어야 한다:**

> 층 L의 캐시를 고쳐도, **그 위치의 L+1층 KV는 다시 계산되지 않는다.**
> (L+1의 KV는 이미 원래 잔차 스트림에서 만들어져 캐시에 들어 있다.)
> 즉 이 개입은 **"층 L에서의 읽기 경로만"** 국소적으로 바꾼다. 효과가 위층으로 눈덩이처럼 불어나지 않는다.
>
> **장점:** "몇 층에서 결정이 굳는가"를 **층별로 깨끗이 분리**해 답할 수 있다(전체 재계산이면 층 효과가 뒤섞인다). 비용도 훨씬 싸다.
> **한계:** 여기서 측정되는 것은 "**층 L을 통과하는 전달 경로의 기여**"지 "그 단어의 총 인과 효과"가 아니다.

### 5-4. 왜 "평균 덮어쓰기(mean-pool)"인가

`camelCase`(2조각)와 `snake_case`(3조각)는 **조각 수가 다르다**. 정렬 전략은 셋이었다(`token_unit`):

| 방식 | 동작 | 문제 |
|---|---|---|
| `all` | 첫↔첫, 둘째↔둘째 1:1 | 조각 수가 다르면 **그 이름 통째로 스킵** → 모델에 따라 표본이 0이 됨 |
| `last` | 마지막 조각만 1:1 | 스킵은 없지만 단어의 **일부만** 덮음 → 신호 약함 |
| **`mean`** ★ | 공여 조각들을 **평균 내** 위반 단어의 **모든 자리**에 브로드캐스트 | 스킵 없음 + 단어 전체를 덮음 |

`mean`을 전 실험 표준으로 통일했다(CLAUDE.md §3). **토크나이저에 무관**하고 **코드 이름·지침 단어에 동일 적용**된다.
구현은 `align_name_groups`(`intervention.py:58`, 개수 불일치 허용)와 `_score_layer_kind`의 mean 경로.

> **평균이 만드는 부작용도 정직하게 적어야 한다.** 서로 다른 위치의 K를 평균하면 **RoPE 위상이 섞인다**(§8-5).
> V는 RoPE가 없어 이 문제가 없다 — 따라서 **V 치환이 K 치환보다 해석적으로 깨끗하다**는 점을 논문에 명시한다.

### 5-5. 행동을 어떻게 재나 — 준수 선호 점수 S

생성시켜서 이름을 보는 방법은 이산적이고(맞다/틀리다) 디코딩 잡음이 있다. 그래서 **연속 점수**를 쓴다:

```
S = log P("removeDuplicates" | 문맥)  −  log P("remove_duplicates" | 문맥)
       └ 준수 후보                          └ 위반 후보
```

- 후보 두 개는 **고정**이다(생성 과제 1번의 camel판/snake판). 후보를 닫았기 때문에 가능하다.
- 각 후보의 확률은 **토큰별 로그확률의 합**(`model.py:302 logp_candidate`). 프롬프트 마지막 토큰과
  후보의 앞 조각들을 캐시에 이어 넣어 한 번의 forward로 얻는다.
- `S > 0` = 준수 쪽 선호. 단위는 로그 확률 차(nat).

### 5-6. 되돌림 정도(회복률)와 "영향력"

```
              S_int − S_base
회복률  =  ───────────────────          intervention.py:87
              S_clean − S_base
              └──────┬──────┘
                  = 영향력 (effect size)
```

| 값 | 뜻 |
|---|---|
| **0** | 치환해도 base와 같다 = 그 통로는 관련 없다 |
| **1** | 지침을 통째 바꾼 것과 **같은 수준**까지 넘어갔다 = 그 통로가 손잡이다 |
| **음수** | 반대 방향으로 갔다(드묾, 보고 대상) |
| **None** | 분모 ≈ 0 → **판정 불가** |

**분모가 곧 CLAUDE.md §3의 "영향력"이다.** `|S_clean − S_base| ≈ 0`이면 그 모델은 애초에 지침을 바꿔도
행동이 안 바뀐다는 뜻 → **"속을 바꾸면 어떻게 되나"를 물을 대상 자체가 없다** → 그 조건은 **판정 불가로 분리**한다.
(비율의 분모가 0에 가까우면 값이 폭발하므로 통계적으로도 반드시 걸러야 한다.)

> ⚠️ **명명 주의(코드 읽을 때 헷갈리는 지점).** step5 경로에서 변수 이름은 `S_clean`이지만 그 내용은
> "**반대 지침** 상태의 점수"다(step3에서 물려받은 이름). 지침이 잘 먹히는 모델이면 `S_clean < S_base`라
> **분모가 음수**가 되고, 치환이 성공하면 분자도 음수가 되어 **회복률은 정상적으로 양수**가 된다.
> 논문·표에는 `S_opposite`(천장) / `S_base`(기준) / **전이율(transition rate)** 로 적는 것이 정확하다.

### 5-7. 층 스윕의 비용 설계

전 층 × 3종(key/value/key_value)을 다 재려면 순진하게 짜면 `층수 × 3` 번의 프롬프트 재계산이 필요하다.
코드는 다음으로 피한다(`model.py:427`):

1. 선행 프롬프트 forward는 **총 2~3회뿐**(base/opp/donor). 층이 바뀌어도 재계산 안 함.
2. `work_cache` **하나**를 만들어 층·kind마다 **편집 → 측정 → 복구**로 재사용.
3. 채점 시에는 캐시를 **복제해서** forward(`_clone_cache`) → 원본이 오염되거나 길이가 늘지 않는다.
4. `S_clean`, `S_base`는 층과 무관하므로 **한 번만** 계산.

무료 T4에서 전 층 스윕이 가능한 이유가 이 4가지다.

## 8. 함정·한계 — 이미 밟았거나, 리뷰어가 반드시 묻는 것

### 8-1. GQA 매핑을 틀리면 조용히 잘못된 값이 나온다
`a`는 `[16, seq]`, `‖v‖`는 `[2, seq]`. 인덱스를 그냥 맞추면 IndexError가 나거나(운 좋음) 엉뚱한 head를 곱한다.
`span_metrics`는 시작에서 `Hq == Hkv × group_size`를 **검증하고 안 맞으면 예외**를 던진다. 모델마다 다르므로
결과 JSON의 `extra.gqa`를 항상 확인할 것.

### 8-2. `output_attentions`는 eager 어텐션에서만 나온다
sdpa/flash 커널은 가중치 행렬을 만들지 않는다(그게 빠른 이유다). `load_model(..., attn_implementation='eager')`
없이 관측을 돌리면 어텐션이 `None`이다. **관측 노트북은 반드시 eager, 생성 실험은 불필요.**

### 8-3. 메모리 — 관측이 의외로 무겁다
`output_attentions=True`는 층마다 `[1, Hq, seq, seq]`를 뜬다. seq≈185인 우리 합성 프롬프트는 T4에서 감당되지만,
**deepseek-6.7b는 OOM 가능** → 노트북 셀 ④에 8bit 주석이 준비돼 있다. 실코드(긴 컨텍스트) 조건으로 확장하면
seq²이 커져 축약 경로가 필요하다.

### 8-4. chat template과 offset의 불일치
템플릿에서 바로 토큰을 받으면 offset이 없고, 문자열을 다시 토큰화할 때 `add_special_tokens=True`면
특수 토큰이 **이중 삽입**된다. 코드는 `tokenize=False` → 직접 토큰화 → `add_special_tokens=False`로 이 둘을 모두 피한다.
템플릿이 텍스트를 변형하는 모델이면 `instruction` 구간 검색이 실패할 수 있으므로, `span_token_counts`가 0이 아닌지
반드시 확인한다.

### 8-5. Key 치환은 RoPE 때문에 해석이 덜 깨끗하다
캐시의 K는 **위치 회전(RoPE)이 이미 적용된** 상태다. 그래서 K를 다른 위치의 것으로 갈아끼우면 "내용"뿐 아니라
"위치 신호"까지 함께 들어간다. mean-pool은 여러 위치의 K를 평균하므로 **위상이 섞인다**.
- 완화 요인: step5의 base/opp 프롬프트는 앞부분이 동일해 지시어의 **절대 위치가 거의 같다**(토큰 1~2개 차이).
- 그래도 **V 치환(RoPE 무관)이 해석적으로 더 깨끗**하다는 점을 논문에 명시하고, K 결과는 보조 증거로 다룬다.

### 8-6. 층 효과는 누적되지 않는다 (설계이자 한계)
§5-3 참조. 우리가 재는 것은 "층 L의 읽기 경로 기여"지 "총 인과 효과"가 아니다. 회복률이 어느 층에서도
1에 못 미치더라도 그 자체는 모순이 아니다 — 여러 층에 분산돼 있을 수 있다.

### 8-7. 회복률의 분모가 0에 가까운 조건
§5-6. **반드시 판정 불가로 분리**한다. 섞어서 평균 내면 비율 폭발로 결과가 오염된다.

### 8-8. `‖av‖`는 W_O 이전 값이다
head 출력은 이어붙여 `W_O`를 곱한 뒤 잔차에 더해진다. 우리 `av_norm`은 **그 직전** 크기이므로
"잔차 기여의 상한/대리 지표"이지 정확한 기여 벡터의 노름이 아니다. 비교 목적(구간 A vs 구간 B)엔 충분하지만
절대량으로 해석하면 안 된다.

### 8-9. FFN은 범위 밖
§1-7. "정보가 전달되는 통로"까지가 우리 주장이고, 전달된 뒤의 위치 내 가공은 후속 과제로 남긴다.

### 8-10. 코드에 남아 있는 미구현·미배선 (앞으로 손봐야 할 곳)
읽으면서 확인한, **지금 상태 그대로의 사실**:

| 항목 | 현재 상태 | 위험 |
|---|---|---|
| `InterventionKind.ATTENTION_AMPLIFY` | 스키마엔 있으나 `_score_layer_kind`에 경로 없음 | `kind="attn_amplify"`로 돌리면 **아무것도 안 바꾸고** `S_int = S_base`, 회복률 0을 **조용히** 반환. Spotlight 반박 실험을 하려면 여기 구현 필요 |
| `token_unit="mean"` | `intervene_preference(_sweep)`에서만 지원 | `intervene_generate`·`name_v_cosine_sweep`은 `align_name_tokens`를 부르므로 mean이면 **ValueError**. §3 통일 방침과 어긋남 |
| `intervene_generate`의 `span_kind` | 인자 없음(항상 `def_name`) | 지침 타깃의 **생성 기반 재확인**은 현재 불가 |
| `Metrics`의 스칼라 필드 | 관측 경로에선 `per_layer`만 채움 | 스칼라 필드(`attention_weight` 등)는 비어 있는 게 정상 — 분석 코드가 이걸 읽으면 안 됨 |

> 이 넷은 **step5 착수 전에 결정할 사항**이다(구현할지, 범위에서 뺄지). 특히 첫 항목은 조용한 실패라
> 실험을 돌려도 눈치채기 어렵다.

## 9. 재현 체크리스트

```
□ seed = 42, pool_block으로 504개 전부 커버, n_compliant=6 (camel 6 / snake 6 균형)
□ 관측이면 load_model(..., attn_implementation='eager')
□ 결과 JSON의 extra.gqa 로 GQA group 확인 (모델마다 다름)
□ span_token_counts 가 0인 구간이 없는지 확인 (0이면 위치 탐색 실패)
□ 어텐션 비교는 반드시 토큰당 평균으로 (합 비교 금지)
□ 개입이면 n_substituted_tokens > 0 확인 (0이면 그 실행 무효)
□ 개입이면 |S_clean − S_base| 확인 → 0에 가까우면 판정 불가로 분리
□ results/ 파일은 덮어쓰지 않는다 (save_result가 예외를 던지는 게 정상 동작)
```
