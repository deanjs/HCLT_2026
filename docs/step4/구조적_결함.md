## A. 조용한 오작동 — 예외 없이 틀린 결과가 저장된다

가장 위험한 부류다. 실험이 "성공"으로 끝나고 JSON까지 남기 때문에, **결과를 보고도 잘못됐다는 걸 알 수 없다.**

### A1. `attn_amplify`가 아무것도 하지 않고 "회복률 0"을 반환한다 `확정`

**근거**
```python
# src/harness/model.py:343
edit_k = kind in ("key", "key_value")
edit_v = kind in ("value", "key_value")
```
`kind="attn_amplify"`면 둘 다 `False` → 치환 루프가 전부 빈 동작 → `s_int = S(work_cache)` = `S_base` →
`recovery = 0.0`. 예외도 경고도 없다.

`conditions.py:61`에 `InterventionKind.ATTENTION_AMPLIFY`가 정의돼 있고, `Intervention.__post_init__`은
`amplify` 배율까지 요구하며 **정상 조건으로 통과시킨다**(`tests/test_scaffold.py:74`는 amplify 누락만 검사).
`runner._run_intervention`도 `iv.kind.value`를 그대로 넘긴다.

**왜 치명적인가**
"어텐션을 키워도 안 되고 Value를 바꿔야 된다"는 **논문의 반박 논지 자체**가 이 조건에서 나온다.
지금 상태로 돌리면 **회복률 0.0이 정확히 우리가 원하는 그림처럼 나온다** — 실제로는 아무것도 안 한 것인데.
검토자가 코드를 열어보면 결론 전체가 무너진다.

**수정 방향 (택1, 결정 필요)**
1. **구현한다** — `_score_layer_kind`에 어텐션 증폭 경로 추가. 단 KV 캐시 편집만으로는 불가능하다
   (a는 forward 중에 계산되므로 **어텐션 훅**이 필요: 대상 구간 열의 어텐션에 배율을 곱하고 재정규화).
   → `model.py`에 훅 기반 경로를 새로 만들어야 한다. 비용 있음.
2. **범위에서 뺀다** — Enum에서 제거하거나, `_score_layer_kind` 진입 시 `raise NotImplementedError`.
   최소한 **조용한 0 반환은 즉시 막아야 한다.**

> 어느 쪽이든 **지금 당장 해야 할 것**: 미지원 kind에 예외를 던지는 한 줄.

### A2. 생성 기반 개입이 `intervention.target`을 무시하고 코드 치환을 한다 `확정`

**근거**
`runner._run_intervention_generate`(`runner.py:360`)는 `iv.target`을 **한 번도 읽지 않는다.**
무조건 `preceding_specs(condition)`으로 선행 코드 이름을 뽑아 치환한다. `model.intervene_generate`
(`model.py:562`)에도 `span_kind` 인자가 아예 없어 항상 `def <name>(` 방식으로 위치를 찾는다.

**증상**
`target="instruction"` + `mode='intervene_generate'` 로 돌리면:
- 실제 수행: **선행 코드 이름** KV 치환 (지침은 손도 안 댐)
- 저장 파일명: `...__int-key_value-L25-instr-...` — **지침 타깃이라고 적힌다**
- `metrics.extra`에도 `intervention_target` 키가 없다(선호 경로에만 있음)

→ **파일명과 실제 실험이 어긋난 결과가 영구 저장된다.** §6 불변 규약 아래에서 특히 나쁘다.

**수정 방향**
`_run_intervention_generate` 시작부에서 `iv.target == "instruction"`이면 (a) `_preference_setup_instruction`
기반으로 배선하거나 (b) 최소한 `raise ValueError("생성 기반 개입은 아직 code 타깃만 지원")`.
그리고 `intervene_generate`에 `span_kind` 인자를 추가(선호 경로와 동일 형태).

### A3. 구간을 못 찾아도 조용히 "값 없음"으로 저장된다 `확정`

**근거 3중**
```python
# model.py:174  지침을 프롬프트에서 못 찾으면 → 빈 구간
elif inst_start is None:
    char_spans[span_name] = []
# attention_probe.py:69  빈 구간 → 모든 지표 None
out[name] = {"attention_weight": None, ...}
# runner.py:485  None인 지표는 per_layer에서 **키 자체가 사라짐**
if metric_name == "n_tokens" or v is None: continue
```

**증상**
chat 템플릿이 system 문장을 변형하는 모델(system 역할을 user에 합치거나 접두사를 넣는 계열)에서는
`find_char_spans(prompt_text, [instruction_text])`가 실패한다. 그러면:
- `instruction`, `instr_rule_word`, `instr_cand_*` 가 **전부 빈 구간**
- JSON `per_layer`에는 그 키들이 **아예 없다** (0이 아니라 부재)
- 노트북 요약은 `v.get(키, 0)` 이라 **0으로 출력** → "지시어를 안 본다"로 오독

step4 4모델에서는 `span_token_counts`가 정상(예: `instr_rule_word: 2`)이라 **이번 결과는 무사**하다.
문제는 **모델을 추가하거나 지침을 바꿀 때 조용히 깨진다**는 것.

**수정 방향**
`observe_generation_query` 반환 직전에 **필수 구간이 비면 예외**를 던진다(관측 실패는 실패로 남겨야 한다).
최소한 노트북·분석 코드에서 `.get(key, 0)` 을 금지하고 `span_token_counts`로 먼저 검사.

### A4. 후보열거 앵커가 지침 조립과 분리돼 하드코딩돼 있다 `확정`

**근거**
```python
# prompt.py:57   지침 문장을 만드는 곳
closed = f"Every function name uses one of two styles only: {c0} or {c1}."
# prompt.py:63   그 문장을 다시 찾는 곳 — 별도 문자열 상수
_CANDIDATE_ANCHOR = "one of two styles only:"
```
둘을 묶는 테스트가 없다(`grep _CANDIDATE_ANCHOR tests/` → 0건).

**증상**
지침 문구를 조금이라도 손보면 `text.find(_CANDIDATE_ANCHOR)`가 `-1`이 되고, `prompt.py:101`의 분기
`(cand_camel if ci >= 0 and a >= ci else rule_word)` 때문에 **후보열거 단어가 전부 규칙문 지시어로 분류된다.**
예외 없이, 값이 조용히 2배로 부풀려진다 — step4가 애써 분리한 그 불공정 비교로 되돌아간다.

**수정 방향**
`closed` 문장을 상수에서 조립하도록 바꿔 앵커를 **한 곳에서 파생**시키고, "합산 = 규칙문 + 후보열거"를
검증하는 테스트를 추가(이미 결과 문서 §1-1에서 수동으로 확인한 항등식을 테스트로 고정).

## B. 통일 규약(CLAUDE.md §3) 위반

### B1. `token_unit="mean"`이 경로 절반에서 예외를 던진다 `확정`

**근거**
```python
# intervention.py:35
if mode not in ("all", "last"):
    raise ValueError('mode는 "all" 또는 "last"만 허용한다')
```
`align_name_tokens`를 부르는 곳: `model.intervene_generate`(`model.py:615`),
`model.name_v_cosine_sweep`(`model.py:533`). 둘 다 `mode=token_unit`을 그대로 넘긴다.

**증상**
CLAUDE.md §3은 **"평균 덮어쓰기(mean-pool)로 전 실험 통일"** 인데, 그 설정으로는
- **v 코사인 관측**(step2 관측 측)
- **생성 기반 개입 재확인**(step3·5)

이 **ValueError로 죽는다.** 즉 통일 설정에서 돌아가는 건 선호 점수 경로뿐이다.

**추가 모순**: `conditions.py:216` 주석은 mean에 대해 *"v 코사인엔 쓰지 않는다"* 라고 적혀 있다.
그러면 **코사인 관측만 다른 정렬 단위**를 쓰게 되고, "관측 코사인 궤적과 인과 회복률 피크의 층을 맞춰 본다"는
교차검증(계획서 §2.4)이 **서로 다른 토큰 정렬로 비교**되는 셈이다.

**수정 방향 (결정 필요)**
- 코사인은 1:1 대응이 본질이므로 `last` 고정으로 **명시**하고, 문서에 "정렬 단위가 다름"을 못 박거나
- 코사인에도 mean 대응물(공여/대상 각각 평균 벡터끼리 코사인)을 정의해 **정말로** 통일한다.
어느 쪽이든 **지금처럼 예외로 죽는 상태는 안 된다.**

## C. 판정 기준이 코드에 없다

### C1. "영향력 0 → 판정 불가"가 사실상 발동하지 않는다 `확정`

**근거**
```python
# intervention.py:88
def recovery_rate(s_clean, s_base, s_int, eps: float = 1e-9):
    denom = s_clean - s_base
    if abs(denom) < eps: return None
```
CLAUDE.md §3·§4는 **"영향력이 0에 가까운 조건은 판정 불가로 분리"** 를 요구한다. 그런데 임계값이 `1e-9`다.
로그확률 차이가 정확히 1e-9 미만일 일은 없으므로 **이 가드는 실질적으로 절대 발동하지 않는다.**

**증상**
지침이 거의 안 먹히는 모델(예: `S_opp − S_base = 0.02`)에서 아주 작은 잡음성 변화가
`recovery = 0.5` 같은 큰 값으로 증폭돼 **평균에 그대로 섞인다.** 비율 통계의 전형적 오염이다.

**수정 방향**
1. **실질 임계값(τ)** 을 정한다 — 예: `|S_opp − S_base| < 0.5 nat` 이면 판정 불가.
   τ는 임의값이 되므로 **모델별 영향력 분포를 먼저 뽑아 보고** 근거를 남긴 뒤 고정할 것.
2. 회복률과 별개로 **`effect_size`(분모)를 `metrics.extra`에 명시적으로 저장**한다
   (지금은 S_clean·S_base로 사후 계산은 가능하지만, 필터링 기준이 결과에 안 남는다).
3. 집계 시 **판정 불가 조건 수를 반드시 함께 보고**한다(몇 개를 왜 뺐는지).

### C2. 치환 토큰이 0개여도 실행이 성공으로 저장된다 `확정`

**근거**
`_preference_context`는 `n_sub`(덮어쓴 자리 수)와 `skipped`를 계산해 반환만 하고, **0인지 검사하지 않는다**
(`model.py:292-300`). 호출부도 검사하지 않는다.

**증상**
이름·지시어를 못 찾으면 `pairs`/`groups`가 비고 → 치환이 0건 → `S_int = S_base` → `recovery = 0.0`.
**A1과 똑같이, "효과 없음"과 "실험 안 됨"이 구별되지 않는다.**

**수정 방향**
`n_substituted_tokens == 0`이면 예외를 던지거나, 최소한 `metrics.extra["invalid"] = True`로 표시해
집계에서 자동 제외되게 한다. (`skipped_names`가 전체 이름 수와 같은 경우도 동일.)

## D. 결과 저장·재현 규약의 결함

### D1. `results/` 실제 레이아웃이 저장 규약과 어긋난다 `확정`

**근거 (실물 확인)**
```
규약(results.py:60):  results/<step>/<slug>.json     →  results/step4_instr-observe/...
실제:                 results/step4_instr-observe_results_qwen/
                      results/step4_instr-observe_results_deepseek/
                      results/step4_instr-observe_results_stable/
                      results/step4_instr-observe_llama/          ← 이름 규칙도 제각각
$ ls -d results/step4_instr-observe   →  No such file or directory
```

**증상 (지금 당장 깨져 있음)**
- 노트북 셀 ④의 **재개 검사** `result_path(c, step=STEP).exists()`가 전부 False → **336개를 처음부터 다시 돌린다.**
- 노트북 셀 ⑥의 **결과 로드**가 0건을 반환한다 → 요약 셀이 아무것도 못 만든다.
- 즉 **현재 저장된 step4 결과는 하네스로 다시 읽을 수 없다.** (Colab zip을 모델별 폴더로 풀어 넣은 흔적)

슬러그 앞부분에 이미 모델 이름이 들어 있으므로(`qwen2-5-coder-3b-instruct__...`) **모델별 폴더는 애초에 불필요**하다.

**수정 방향**
- 정규 경로 `results/step4_instr-observe/`로 **합친다**(파일명이 이미 유일하므로 충돌 없음).
  기존 파일은 §6 불변 규약상 **내용 수정 없이 이동만**.
- 노트북 zip 셀이 **정규 경로 구조를 유지한 채** 묶이도록 하고, 언팩 절차를 문서화한다.

### D2. 모든 결과의 `meta`가 비어 있다 `확정`

```
$ 샘플 3개 확인 → meta: {},  prediction: null   (336개 전부 동일 구조)
```
`ResultRecord.meta`는 주석에 *"git sha, 실행 환경 등"* 이라고 적혀 있지만 노트북이 아무것도 넣지 않는다.

**증상**: 결과 JSON만 보고 **어느 코드 버전으로 뽑았는지 알 수 없다.** 결과가 불변(§6)인데
그 결과를 만든 코드가 가변이면 재현성이 성립하지 않는다. step4는 실험 도중 방법을 바꾼 이력
(`instr_target_word` 초판 → 규칙문/후보열거 분리, `bd3b0d3 qwen 결과 폐기 후 재실험`)이 있어 특히 필요하다.

**수정 방향**: 노트북 실행 셀에서 `meta={"git_sha": ..., "transformers": ..., "torch": ..., "gpu": ...}` 채우기.
`save_result` 쪽에서 비어 있으면 경고를 띄우는 것도 고려.

### D3. 실행 모드가 조건·파일명에 없다 `확정`

`run(condition, mode=...)`의 `mode`(generate/observe/vcosine/intervene_generate)는 **`Condition`의 축이 아니다.**
같은 조건을 다른 모드로 돌리면 **슬러그가 완전히 같다.**

지금은 스텝 이름이 달라 충돌이 안 났고, 충돌하면 `save_result`가 `FileExistsError`를 던져 **덮어쓰기는 막힌다.**
하지만 "파일명만 봐도 조건이 드러난다"(§6)는 규약은 이미 깨져 있다 — 무엇을 측정한 파일인지 이름으로 알 수 없다.

**수정 방향**: `mode`를 슬러그에 넣거나(예: `__m-observe`), 스텝 이름에 모드를 반드시 포함하는 규칙을 문서화.

## F. 방법론적 결함 — 실험 설계 결정이 필요

### F1. `forced_prefix = "def "` 의 끝 공백 `검증필요`

BPE 계열 토크나이저는 보통 **공백을 다음 토큰에 붙인다**(`" remove"`). 그런데 우리는 프롬프트를
`"...def "` 로 **공백에서 끊어** 토큰화한다. 그러면:

- **관측**: 우리가 읽는 "마지막 query 행"이 **홀로 떨어진 공백 토큰**의 행일 수 있다.
  모델이 후행 공백 상태에서 이상하게 행동하는 것은 알려진 병리다.
- **채점**: 후보를 `tok("removeDuplicates", add_special_tokens=False)`로 **공백 없이** 토큰화해 점수를 매기는데
  (`model.py:268`), 실제 생성에서는 `" removeDuplicates"` 형태로 나올 가능성이 높다.
  → **실제로 모델이 밟지 않을 토큰 경로에 확률을 매기고 있을 수 있다.**

S는 두 후보의 **차이**라서 상당 부분 상쇄되지만, 상쇄된다는 보장은 없다(camel/snake의 분해가 다르므로).

**검증 방법 (모델 하나로 5분)**
```
1) tok("...def ")  마지막 토큰이 무엇인지 출력
2) forced_prefix="def" (공백 없음) vs "def " 로 S_base를 비교
3) 실제 그리디 생성 첫 토큰이 " remove…"인지 "remove…"인지 확인
```
차이가 크면 접두를 `"def"`로 바꾸거나 후보를 `" removeDuplicates"`로 토큰화해야 한다.
**결과가 바뀔 수 있으므로 step5 착수 전에 확인해야 한다.**

### F2. 지침 치환이 첫 등장만 바꾼다 `확정`

`_locate_target_tokens(span_kind="literal")`은 `find_char_spans(...)[0]` — **첫 등장 하나만** 집는다
(`model.py:663`). 의도는 "규칙문의 진짜 지시어"를 겨냥한 것이고 그 자체는 옳다.

하지만 결과적으로 **후보열거의 같은 단어(`camelCase`)는 원본 그대로 남는다.** 개입 후에도 모델은
같은 표면형을 다른 위치에서 여전히 읽을 수 있어 **효과가 희석된다** → 회복률이 과소평가될 수 있다.

**수정 방향 (결정 필요)**: 세 조건을 별도로 돌려 비교하는 게 가장 안전하다.
① 규칙문만 치환(현행) ② 규칙문+후보열거 모두 치환 ③ 후보열거만 치환(통제).
최소한 현행이 **부분 치환**임을 논문에 명시해야 한다.

## G. 환경·성능 취약점

### G1. `load_in_8bit=True` 직접 전달 `검증필요`

```python
# model.py:752
if spec.quantization == "8bit": load_kwargs["load_in_8bit"] = True
```
최신 `transformers`는 이 인자를 폐기하고 `quantization_config=BitsAndBytesConfig(...)`를 요구한다
(버전에 따라 경고 또는 오류). 같은 함수의 `torch_dtype`도 `dtype`으로 이름이 바뀐 상태다(`model.py:747`).

**증상**: 노트북이 안내하는 **deepseek-6.7b OOM 대비책(8bit)** 이 최신 Colab 환경에서 먹통일 수 있다.
step5(전 층 스윕)는 step4보다 무거우므로 이 경로가 실제로 필요해진다.

**수정 방향**: `BitsAndBytesConfig` 경로로 교체하고, Colab에서 8bit 로드가 실제로 되는지 한 번 확인.
**추가 주의**: 8bit로 뽑은 KV에 치환을 하면 정밀도 문제가 생길 수 있다 —
계획서 §5가 요구하는 **양자화 정밀도 검증을 step5 전에** 해야 한다.

### G2. 채점마다 KV 캐시 전체를 deepcopy 한다 `검증필요`

```python
# model.py:305   후보 채점 1회당 깊은 복사 1회
c = _clone_cache(cache)
```
`S` 한 번 = 후보 2개 = **deepcopy 2회**. 전 층 스윕은 `층수 × kind 3종` 만큼 `S`를 부르므로
**qwen(36층) 기준 216회, deepseek(32층) 192회**의 전체 캐시 복사가 일어난다.

deepseek-6.7b는 GQA가 아닌 MHA(KV head가 query head와 동수)라 캐시가 크다 —
`32층 × 2 × 32head × 200 × 128 × 2byte ≈ 100MB/회` 수준. 모델 13GB가 이미 올라간 T4에서
100MB 할당·해제를 200회 반복하면 **단편화·속도 저하·OOM 위험**이 있다.

**수정 방향**: 복사 대신 **캐시 자르기(crop)** 를 쓴다 — 채점 forward가 늘려 놓은 길이만큼 되돌리면
원본을 재사용할 수 있다(`DynamicCache.crop(n)` 또는 텐서 슬라이스). step5 실행 전에 벤치마크할 것.

## H. 사소하지만 오해를 부르는 것

- **`Metrics`의 스칼라 필드가 관측 경로에서 항상 비어 있다.** `attention_weight`, `v_norm`, `av_norm`,
  `v_cosine` 자리는 `per_layer`만 채우는 관측·스윕 경로에서 영원히 `None`이다(`runner.py:490`).
  분석 코드가 이 필드를 읽으면 조용히 `None`을 얻는다. → 주석으로 "층별 경로에서는 미사용" 명시 필요.
- **`prediction`이 전부 `null`.** §6은 "실행 전 예측을 기록했으면 보존"이라 위반은 아니지만,
  step5는 예측을 먼저 적어 두는 편이 결과 해석의 신뢰도를 높인다.
- **`RESULTS_DIR = Path("results")` 가 상대 경로**(`results.py:22`)라 실행 위치에 의존한다.
  노트북은 `%cd HCLT_2026` 덕에 맞지만, 다른 곳에서 부르면 조용히 엉뚱한 폴더에 쓴다.
