# step A-2 — 실제 저장소 코드 (원래 step 4)

**한 줄:** 선행 코드를 합성이 아니라 **진짜 소스 파일**로 바꿔, 언어마다 정해진 표기 관습을 **자연 실험**으로 이용해 "형태 신호가 지침을 이기나"를 실코드에서 본다.

대응: **RQ1 외적 타당성** — 대조군. 합성에서 본 현상이 실제 코드에서도 성립하는지.

## 무엇을 방어하나

step A·A-1은 선행이 **합성 코드**였다. 반론:

> "합성 코드라서 생긴 인공물 아니냐."

실제 저장소 파일로도 같은 패턴이면, 효과는 합성 아티팩트가 아니라 **실제 코드의 표기 형태**에 있다.

## 핵심 설계 — 언어 관습 2×2

언어마다 관습이 고정돼 있다. 이걸 조작 없이 이용한다.

| 선행 파일 | 지침=camelCase | 지침=snake_case |
|---|---|---|
| **Python** (관습 snake) | **충돌** | 일치 |
| **JavaScript** (관습 camel) | 일치 | **충돌** |

- 실제 코드는 **손대지 않고**, **지침만 camel/snake 무작위 배정** → 2×2 완성.
- **충돌 칸**에서 준수율이 떨어지면 → 모델이 지침보다 **언어 관습(형태)**을 따른다는 증거. step A의 바닥(camel-on-Python)과 직결.

## 바꾸는 것 / 재는 것

| 축 | 값 |
|---|---|
| 선행 `source` | **repo** (실제 파일) |
| 선행 `repo_lang` | python / javascript |
| 지침 | camel / snake (무작위 배정) |
| 개입 | none |

- 재는 것: 새 함수 첫 이름의 표기 → **준수율**(2×2 각 칸). **생성률만**, 내부 개입 없음(실코드는 대응쌍 불가).
- 반복: 언어별 실파일 여러 개 × 생성 과제 몇 개로 표본 확보(정확한 수는 노트북 파라미터).

## 예상과 해석 (§4: 그대로 기록)

| 결과 | 해석 |
|---|---|
| 일치 칸 높음 / 충돌 칸 낮음 | 언어 관습(형태)이 지침을 압도 → 실코드에서도 형태 지배, RQ1 외적 타당성 확보 |
| 충돌 칸도 준수율 유지 | 합성에서만 생긴 인공물일 수 있음 → 주장 범위를 합성으로 축소 |
| 언어별로 방향 다름 | 언어·모델별 prior 강도 차이 → 별도 서술 |
