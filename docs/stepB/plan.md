# step B — RQ2 기반 관측 (어텐션·‖v‖·‖av‖)

**한 줄:** RQ1에서 "형태가 지배, 지침 불활성"을 **행동**으로 봤다. step B는 이름을 생성하는 **바로 그 시점**에 모델이 어디를 보고 무엇을 실어 나르는지를 **내부에서** 관측한다.

대응: **RQ2** — 매개 신호가 형태인가, 그리고 그 신호가 내부 어디에 있는가(관측). 개입(인과)은 step C.

## 두 축 (계획서 §2)

| 축 | 무엇 | 지표 |
|---|---|---|
| **축 A** 얼마나 보는가 | 어텐션 배분 | 구간별 어텐션 가중치 |
| **축 B** 무엇이 담겨 있는가 | 읽히는 표현 | ‖v‖(크기) · ‖av‖(잔차 기여) |

핵심 가설: **실패는 "지침을 안 봐서(축 A 결핍)"가 아니라 "보고 있는 코드 안의 형태 토큰이 더 센 경쟁 신호(축 B)"다.**

## 무엇을 바꾸나 / 재나

**조건:** 합성 clone, 선행에 camel·snake 이름이 **둘 다 존재**하도록 균형 배치(예: 6 camel / 6 snake). 지침 = camel / snake 2종. seed 반복.
(균형 배치 이유: 두 표기 토큰 그룹에 대한 어텐션을 **비교**하려면 둘 다 있어야 한다.)

**측정 시점:** 새 함수 **이름 토큰을 예측하는 디코딩 시점의 query 한 행**(계획서 §2.7 — 전체 어텐션 행렬은 저장 불가, 생성 시점만 계산). 비교 가능하도록 이름 위치를 **teacher-forcing으로 고정**(예: `def `까지 강제 후 이름 토큰 위치에서 관측).

**구간·그룹:**
- 지침 구간 / 코드 구간
- 코드 내 **camel 이름 토큰** vs **snake 이름 토큰**

## 두 관측(view)

**View 1 — flip 2×2 (선행 6/6 균형).** 코드를 6/6으로 고정하고 지침만 뒤집어 '위반'을 만든다. 충돌 표기 토큰을 더 보는가.

| 지침 | camel 토큰 어텐션 | snake 토큰 어텐션 | 기대 |
|---|---|---|---|
| camel | (준수) | (충돌) | **충돌(snake) 더 봄** |
| snake | (충돌) | (준수) | **충돌(camel) 더 봄** |

지침을 뒤집었을 때 "더 보는 쪽"이 특정 표기가 아니라 **위반 쪽을 따라 뒤집히면** → 신호가 "snake라는 글자"가 아니라 **지침 위반 형태**임이 증명된다(그냥 snake prior와 분리).

**View 2 — 위반 개수 스윕 (지침 camel 고정, 선행 camel 6/4/2/0).** 위반이 늘어도 **지침 구간 어텐션이 평탄**한가. 평탄이면 실패가 '지침 결핍'이 아님(어텐션 증폭 기법 전제와 충돌). 지침 텍스트는 n_compliant와 무관하게 동일하므로 지침 어텐션 합은 정규화 없이 층·조건 간 비교된다. (stepA의 절벽 축을 내부 지표로 잇는 관측.)

## 예상과 해석 (§4: 그대로 기록)

| 관측 | 뜻 |
|---|---|
| 지침 어텐션이 조건 간 **평탄** | 실패가 어텐션 결핍이 아님 → 기존 "지침 증폭" 기법의 전제와 충돌 |
| **충돌 표기 토큰을 더 봄** | 경쟁 신호가 코드의 **형태 토큰**에서 옴 (축 A) |
| 충돌 토큰의 **‖av‖ 증가** | 그 토큰이 잔차에 실제로 더 기여 (축 A×B) |
| ‖v‖ 자체는 평탄 / 방향(코사인)만 다름 | 크기가 아니라 **방향**에 형태 정보 (→ step 1 코사인 궤적) |

→ 종합: **"지침은 보고 있는데, 코드 안의 형태가 더 세게 끈다"**를 내부에서 확인. RQ1 행동의 기제.

## 표본 설계 (승인됨)

**외부 데이터셋을 쓰지 않는다 — 합성 이름 짝 풀이 데이터다.** RQ2 관측은 어텐션·‖v‖·‖av‖·코사인을 **camel판 토큰 vs snake판 토큰의 짝**으로 비교하므로, 같은 함수의 두 표기가 대응쌍으로 존재해야 한다. 실제 저장소 코드는 이 대응쌍을 만들 수 없다(그래서 실코드는 step 4에서 생성률만 잰다).

**이름 짝 풀 (데이터셋).** 외부 벤치마크를 쓰지 않는다. `tasks.py`의 `NAME_PAIR_POOL`이 데이터다 — **두 단어 함수 이름 짝 80개**(동사×명사, 예: `parseHeader`/`parse_header`).

- **어떻게 80개인가:** 동사 20개 × 명사 20개에서, 동사 `verb[i]`를 명사 `noun[i..i+3]`(shift 0~3)와 짝지어 **20 × 4 = 80개**. 같은 (동사,명사)가 두 번 나오지 않는다(동사가 다르면 다르고, 같으면 명사 shift가 다르다). 전부 두 단어라 camel/snake가 항상 구분되고, 본문·매개변수는 **전 항목 동일**(값 반환)이라 선행 함수 사이에서 변하는 것은 오직 이름 표기다.
- **한 조건당 몇 개 쓰나:** 매 (지침 × seed)마다 80개 중 **12개를 seed로 뽑아** 선행에 배치(camel 6 / snake 6). seed가 다르면 다른 12개 → 여러 seed에 걸쳐 80개 이름이 두 표기로 고루 관측된다.
- 예비(A2)의 "80쌍 × 3 seed" 규모를 이 하네스에서 재현한다(§0: A2를 직접 재현·생성).

- 풀 출처: **합성 조합만** (통제 깔끔). 실코드 이름 혼입은 step 4에서 별도.
- 현재 하네스 이름 풀(clone 1 + distinct 12 + generation 3 ≈ 고유 16개)은 짝비교에 부족 → 풀 확장이 stepB 선행 작업.

**표본 단위.** 한 이름 생성 시점에서 (camel 그룹 어텐션 합 vs snake 그룹 어텐션 합)의 **짝 비교 1건**. 같은 forward pass 안의 paired 비교라 통계 효율이 높다.

```
총 표본 = 지침 2종(camel·snake) × 관측 이름 짝 N(~80) × seed 반복
          (층은 표본이 아니라 축)
```

seed만 늘리면 배치 순열만 바뀌고 이름 정체성은 고정 → **서로 다른 이름 N을 확보**해야 효과가 특정 단어의 우연이 아님이 드러난다.

**선행 6/6 균형 배치.** 선행 12함수를 camel 6 / snake 6으로 **개수까지 고정**. 두 표기 그룹의 어텐션을 공정 비교하려면 둘 다, 같은 수로 있어야 한다(개수 편향 제거). 배치 위치는 seed로 셔플.

**이름 위치 teacher-forcing.** 비교 가능하도록 이름 토큰 위치를 강제 고정한다(`def `까지 강제 후 그 위치의 디코딩 query에서 관측). §2.7대로 전체 어텐션 행렬은 저장하지 않고 **생성 시점 query 한 행만** 계산해 구간·그룹별 합을 저장한다.

## GQA 주의 (stepB 관측)

Qwen2.5-Coder-3B는 query head 16 / KV head 2 → **query 8개가 KV 1개 공유**(group 8). 매핑 규칙: `KV head = query head ÷ group_size(=8)` 내림. 예) query head 5 → KV head 0. 곱셈은 `av[h,j] = a[h,j] · v[h÷8, j]` (a는 query head별 16종, v는 KV head별 2종).

**repeat 후 정렬로 계산한다.** HF의 `repeat_kv`로 v를 2개 → 16개로 복제해 늘리면 query head와 인덱스가 1:1 정렬된다. 이후 `av[h,j] = attn[h,j] * v_exp[h,j]`로 곱하면 `h÷8` 매핑을 repeat 함수가 대신 처리 → **수동 매핑 실수 여지 없음**. stepB는 관측만 하고 v를 건드리지 않으므로 이 방식으로 충분하다.

**‖v‖ 보고 시엔** 반대로 **고유 KV head 2개로 접어서** 낸다(head 0~7의 ‖v‖는 동일 원본이라 16개 평균은 독립 측정 16개인 척 오해를 부른다).

group 구성은 모델마다 다르므로 `num_attention_heads`·`num_key_value_heads`를 **런타임에 config에서 읽어** group_size를 계산한다. 하드코딩·추정 금지(§2.6). (개입 시의 치환 단위 주의는 step C 계획에서 다룬다.)

## 한눈에 보는 예시 — 관측 한 번이 어떻게 도는가

지침 = camelCase, 선행 6/6 조건을 예로 든다(이름은 실제 풀에서 뽑힌 것).

**1) 모델에 넣는 것**
```
[지침]  In this project we generally write function names in camelCase.
        Every function name uses one of two styles only: camelCase or snake_case.
[선행]  def formatMatrix(value): return value        # camel (준수)
        def validate_stream(value): return value     # snake (충돌)
        def decode_node(value): return value         # snake (충돌)
        ... (총 12개: camel 6 / snake 6)
[요청]  Add a function that clamps a number ...
```

**2) 재는 순간** — 답을 `def ` 까지 강제로 쓰게 하고, **다음 토큰(=새 이름)을 예측하는 그 query 한 줄**을 붙잡는다.
```
... def ▮      ← 이 ▮ 의 query가 앞을 얼마나 보는지 잰다
```

**3) 세 그룹으로 나눠 잰다** (이름 식별자 토큰만, 본문·`def`·괄호 제외)

| 그룹 | 토큰 | 재는 값 |
|---|---|---|
| 지침 | 지침 문장 전부 | 어텐션 합 |
| camel | `formatMatrix, ...` 6개 이름의 하위 토큰 | 어텐션 합·‖av‖·‖v‖ |
| snake | `validate_stream, ...` 6개 이름의 하위 토큰 | 어텐션 합·‖av‖·‖v‖ |

각 값은 **층별로** 나온다(36층). `‖av‖ = a·‖v‖`는 GQA 방법 A로 query head를 KV head에 매핑해 계산.

**4) per-token 상세도 함께 저장** — 그룹 값과 별개로 토큰 하나하나의 (a, ‖av‖, ‖v‖)를 남긴다.
예: `validate_stream` → `validate` / `_stream` (또는 `_`) 조각별 값. 나중에 **밑줄 `_` 토큰이 어근보다 av가 큰가**를 본다(형태 마커가 신호인가).

**5) 결론 두 갈래**
- **View 1(flip):** 지침을 camel→snake로 뒤집었을 때 "더 보는 쪽"도 snake→camel로 뒤집히면 → 신호는 "글자"가 아니라 **지침 위반 형태**.
- **View 2(스윕):** 위반을 6→0으로 늘려도 **지침 어텐션이 평탄**하면 → 실패는 "지침을 안 봐서"가 아니라 "코드 형태가 더 세게 끌어서".

이 두 개가 나오면 RQ1(행동)의 내부 기제 = **RQ2 관측 답**이고, 인과는 step C에서 KV 치환으로 확인한다.
