# step A-2 결과 — 실제 저장소 코드 (1차 실행)

**실행:** Qwen2.5-Coder-3B-Instruct (fp16). 12조건 = 2 언어 × 3 실파일 × 2 지침(camel/snake).
선행 = **실제 파일 원문**(CPython PSF · axios MIT, `data/repo_files/`). 개입 없음.
결과 원본: `results/stepA-2/*.json` (불변, §6).

**대응 RQ:** RQ1 외적 타당성 — 합성이 아닌 실코드에서도 성립하는가.

## 예측 (실행 전)

> 일치 칸(파일 관습=지침) 높음, 충돌 칸 낮음이면 언어 관습(형태)이 지침을 압도.

## 관측 결과 — 준수율 2×2

| 선행 파일 | 지침=camel | 지침=snake |
|---|---|---|
| **Python** (자연 snake) | 0.00 | 0.67 |
| **JavaScript** (자연 camel) | 0.67 | 0.00 |

**0.67의 정체 (100%가 아닌 이유).** 한 조건은 함수 3개(clamp/count/merge)를 생성한다.
`clamp`는 모델이 한 단어 `clamp`로 지어 **항상 "other"(판정 불가)**, `count`/`merge`는
`countVowels`·`mergeDictionaries`처럼 **항상 관습대로**다. 그래서 aligned 칸은
파일당 `[other, camel, camel]` → 6/9 = **0.67**. **clamp를 빼면 정확히 1.0(만장일치).**
0.67은 어떤 파일이 지침을 따라서가 아니라 clamp가 1/3을 갉아먹은 것이다.

## 핵심 관측 — 지침은 완전히 불활성 (우연 준수 ≠ 인과)

조건별 원문에서 **지침이 camel이든 snake이든 출력이 글자까지 동일**하다:

- **Python 파일** → 지침과 무관하게 항상 `count_vowels`, `merge_dictionaries` (**snake**)
- **JavaScript 파일** → 지침과 무관하게 항상 `countVowels`, `mergeDictionaries` (**camel**)

같은 파일이면 지침 camel/지침 snake의 생성 결과가 **바이트까지 같다.**

**"준수"가 나온 칸(Python+snake, JS+camel)은 지침을 따른 게 아니라 우연의 일치다.**
판별법은 2×2가 **행으로 갈리는가 열로 갈리는가**이다:

- 지침이 원인이라면 → 출력이 **열**(지침)로 갈려야 한다: camel 열은 camel, snake 열은 snake.
- 실제 → 출력이 **행**(언어)으로 갈린다: Python은 무조건 snake, JS는 무조건 camel.

즉 Python+snake의 "준수"는 **모델이 어차피 Python이라 snake를 내는데 그게 snake 지침과 맞아떨어진 것**일 뿐이다. 이것이 인과가 아님을 증명하는 것은 **반대 칸**이다: 같은 Python에서 지침만 camel로 바꿔도(`Python+camel`) 출력은 **바뀌지 않고 여전히 snake**다. 지침이 원인이라면 camel로 뒤집혔어야 한다. → **지침은 출력을 전혀 바꾸지 못한다(불활성).**

따라서 "준수율"이라는 지표는 여기서 오해를 준다(우연 정렬을 준수로 셈). 더 정직한 지표는 **"지침을 바꾸면 출력이 바뀌는가?" → 아니오(동일)**이다.

## 해석

1. **지침(논리 제약)이 이름 결정에 기여하는 바가 0.** camel 지침 vs snake 지침 → 동일 출력.
2. **"snake prior 탓"이 아니다.** JS 코드에선 모델이 **camel**을 낸다. 고정 편향이 아니라 **주변 코드의 관습을 따라가는 것**(form-matching): Python→snake, JS→camel.
3. **A·A-1·A-2가 하나로 합쳐진다:**
   > 모델은 함수 이름 짓기를 **"주변 코드의 표기 관습에 맞추는 일"**로 처리한다. 지침은 불활성.
   - step A(clone): 문맥이 snake 다수 → snake 바닥
   - A-1(distinct): 베낄 같은-과제 예시 없음 → prior(snake) 회귀, camel 0
   - **A-2(실코드): 파일 관습이 곧 출력** — Python→snake, JS→camel, 지침 무시

실코드 + JS 헤드룸 덕분에 "prior냐 관습이냐" 혼동이 제거된, **가장 깨끗한 형태-지배 증거**다.

## RQ1 답

준수 실패의 정체는 "지침을 못 따름"이 아니라 **"주변 형태 관습을 따름"**이다(실코드에서도 성립). 지침은 불활성. → 매개 신호가 형태라는 RQ2로 자연 연결.

## 한계

- **약한 지침 하의 결과.** 지침은 system 한 줄·약한 어조("we generally write…")다. "형태로 처리돼 불활성"인지 "약해서 무시"인지는 이 데이터만으론 못 가른다. 단, 이는 CLAUDE.md류 **현실적 약한 규약**을 모델화한 것이며, "지침이 **형태로** 처리된다"의 직접 증명은 이 데이터 범위 밖이다(어조 통제·부정형 지침은 부록 후보).
- **표본:** 언어당 파일 3개(셀당 3). 결과가 완전 이분적(지침 무관 동일 출력)이라 방향은 확정적이나, 논문용으론 파일 수를 늘려 만장일치를 재확인하는 것이 좋다.
- **과제 설계 ("other"의 의미):** 생성 과제 1을 모델이 한 단어 `clamp`로 지어 "other"가 됐다(1/3 턴). **이 "other"는 위반이 아니라 판정 불가다** — 한 단어 이름은 camelCase로 써도 `clamp`, snake_case로 써도 `clamp`로 **동일**하므로, "camel 또는 snake만 써라"는 규칙을 어긴 게 아니라 **양쪽을 다 만족**한다. 대문자·밑줄 같은 표식이 없어 스타일을 **구분할 수 없을 뿐**이다(스타일 중립 이름 = 측정 사각지대). 따라서 "지침 불활성"의 근거는 clamp가 아니라 명확히 스타일이 찍히는 **count/merge의 행-분리**에 있다. 다음 실행에서 첫 과제를 두 단어가 강제되는 것으로 교체하면 "other"가 사라진다.
- 부수 관측: `merge`를 한 파일에선 `mergeObjects`로 지음(파일 문맥이 **의미어 선택**까지 물들임) — 형태뿐 아니라 어휘도 문맥에 좌우.
