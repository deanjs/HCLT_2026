# step B — pool-500 (RQ2 관측, POOL 50×50 확장 + 500 커버리지)

> 파일럿(`docs/stepB/plan.md`, 이름 80풀에서 seed 랜덤 표집)의 **확대 재실행**이다.
> 이름 창고를 50×50(504개)으로 키우고, 조건들이 **서로 다른 이름 500개를 블록으로 덮게** 바꾼다.
> **이 브랜치가 POOL 확장 코드를 도입**한다(stepC·step1이 여기서 분기). 파일럿 결과는 `results/`에 불변 보존(§6).

---

## 1. RQ2 — 무엇이 궁금한가

**대응: RQ2 (관측).** 매개 신호가 형태인가, 그 신호가 내부 어디에 있는가. (인과 개입은 stepC)

**무엇이 궁금한가:** 모델이 새 이름을 만드는 **바로 그 순간**, 어디를 보고(어텐션) 무엇을 실어 나르는지(‖v‖·‖av‖)를 내부에서 본다. 핵심 가설 — 실패는 "지침을 안 봐서"가 아니라 **"보고 있는 코드 안의 형태 토큰이 더 센 경쟁 신호"** 다.

---

## 2. 어떤 실험을 하는가

측정·관측 설계는 파일럿과 **동일**하다(아래). scaleup에서 바뀌는 건 **이름을 몇 개·어떻게 고르나**뿐.

### 두 축
| 축 | 무엇 | 지표 |
|---|---|---|
| **축 A** 얼마나 보는가 | 어텐션 배분 | 구간별 어텐션 가중치 |
| **축 B** 무엇이 담겨 있는가 | 읽히는 표현 | ‖v‖(크기) · ‖av‖(잔차 기여) |

### 두 관측(view)
- **View 1 — flip 2×2:** 선행을 camel 6 / snake 6 균형 배치로 고정하고 지침만 뒤집어, "더 보는 쪽"이 **위반 표기를 따라 뒤집히는가**. (뒤집히면 신호는 "snake라는 글자"가 아니라 **위반 형태**)
- **View 2 — 위반 개수 스윕:** 지침 camel 고정, 선행 준수 개수를 바꿔가며 **지침 구간 어텐션이 평탄한가**. (평탄이면 실패가 '지침 결핍'이 아님)

### 재는 것
구간별 어텐션 가중치, ‖v‖, ‖av‖ (camel 토큰 vs snake 토큰, 지침 구간 vs 코드 구간). **지표는 파일럿과 동일.**

### 결과 해석 (어느 쪽이든 그대로 기록, §4)
| 관측 | 뜻 |
|---|---|
| 지침 어텐션이 조건 간 **평탄** | 실패가 어텐션 결핍 아님 → "지침 증폭" 전제와 충돌 |
| **충돌 표기 토큰을 더 봄** | 경쟁 신호가 코드의 **형태 토큰**에서 옴 (축 A) |
| 충돌 토큰의 **‖av‖ 증가** | 그 토큰이 잔차에 실제로 더 기여 (축 A×B) |

## 3. 쓰는 데이터셋

| 항목 | 값 |
|---|---|
| 데이터 종류 | **합성(SYNTHETIC)** |
| 선행 구성 | `POOL` — 이름 짝 풀에서 뽑은 서로 다른 이름 |
| 이름 풀 | `NAME_PAIR_POOL` — 동사 50 × 명사 50 → **서로 다른 이름 504개** (`src/harness/tasks.py`) |
| 이름 선택 | **블록 커버리지** — 504 ÷ 12 = **42블록**이 500+ 이름을 중복 없이 덮음 (`pool_block`) |
| 시드 | 블록당 **3** (위치·문맥 강건성; 다양성은 seed 아닌 풀에서 나옴, §3) |
| 조건 | 42블록 × 3시드 = **126조건** → 이름 504 × 3문맥 = **≈1,512 관측** |
| POOL 크기 | **504** (500 정의 = "서로 다른 이름 500개") |

> **500의 정의:** POOL 단계에서 500은 **조건 수가 아니라 서로 다른 이름 수**다. 이름 12개짜리 조건(블록) 42개가 504개를 덮고, seed는 수량이 아니라 같은 이름을 **다른 자리·이웃**에서 재확인하는 용도(§3).

## 4. 데이터를 어떻게 구성했는가

### 이름 창고 50×50 (504개)
- 동사 50 × 명사 50. **앞 20동사·20명사는 원래 순서 그대로** 두고 30개씩 덧붙였다.
- `_build_name_pool()`은 **원래 80개**(앞 20×20, shift 0~3)를 그대로 앞에 두고, 50×50 공간에서 중복 없이 504까지 채운다.
  → 파일럿 이름 80개가 **새 풀의 부분집합**으로 보존된다(연속성).
- 본문·매개변수는 전 항목 공통(`return value`) — **이름 표기만 변수**로 남긴다(stepB 통제).

### 블록 커버리지 (seed = 위치 변주)
- 조건 하나 = **블록 인덱스 b + seed**. 블록 b는 풀의 `[b*12, (b+1)*12)` 이름 12개를 덮는다.
- 42블록이 504개를 **중복 없이 완전히** 덮는다 → 500+ 이름 전부 사용.
- seed는 **블록 내 순서(자리·이웃)와 표기 배치**만 섞는다 → 같은 블록/다른 seed = **같은 이름, 다른 배치**.

### 파일럿과 달라진 점 (승인된 설계)
| | 파일럿 | scaleup (pool-500) |
|---|---|---|
| 이름 창고 | 80 (20×20) | **504 (50×50)** |
| 이름 선택 | seed로 12개 **랜덤 표집** | **블록**으로 500+ 커버, seed는 위치 변주 |
| 다양성 출처 | seed | **50×50 풀** |

## 5. POOL 코드 확장 (이 브랜치가 도입, stepC·step1 공유)

`src/harness/` 3파일을 바꿨다. stepC·step1은 이 브랜치에서 분기해 같은 코드를 쓴다.

| 파일 | 변경 |
|---|---|
| `tasks.py` | 동사·명사 20→50개(앞 20 순서 불변). `_build_name_pool(size=504)` — 원래 80 보존 + 50×50 확장 |
| `conditions.py` | `PrecedingCode.pool_block` 필드 추가. 슬러그에 POOL이면 `-b{block}` (블록별 결과 파일 분리) |
| `prompt.py` | POOL 이름 선택을 `_pool_indices()`로 중앙화(블록 커버리지). build/preceding_specs/unrelated_specs가 공유 |

### 검증 (통과)
- 풀 **504개 distinct**, 동사·명사 각 50
- **앞 80개 == 원래 공식** (파일럿 이름 보존, 부분집합)
- **42블록이 504를 중복 없이 완전 커버**, 블록 42는 범위초과 에러
- 슬러그에 블록 반영(`...-pool-syn-b3...`), CLONE/DISTINCT 슬러그 불변
- 같은 블록/다른 seed → 같은 이름집합·다른 배치
- 단위 테스트 80개 전부 통과 (`tests/test_stepB.py` 블록 계약으로 갱신)

## 6. 재현성 (stepA와 다름 — 명시)

POOL은 이름을 **풀에서 뽑기** 때문에 풀 크기·선택 방식이 바뀌면 파일럿 stepB/C/1은 **글자 그대로 재현되지 않는다**(승인: 새 500 샘플로 진행). 파일럿은 `results/`에 불변 보존(§6)하고, scaleup은 **500개 이름 일반화 실행**으로 새로 쌓는다. 원래 이름 80개는 새 풀의 부분집합으로 남아 연속성은 유지된다. scaleup 결과는 `results/stepB_scaleup500/`에 분리 저장.
